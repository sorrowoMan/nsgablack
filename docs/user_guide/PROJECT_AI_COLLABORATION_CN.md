# 与 AI 协作已有 Project

实验台的“已有 Project 协作”用于继续已有的正式项目。它与“自由装配”共用页面风格，但直接复用 Project／Case 的问题、数据、管线和求解器，不受演示表达式入口的变量数量限制。

## 新会话默认知道什么

两个 AI 入口现在都通过 `lab_knowledge.read_framework_basics()` 自动加载同一份[框架基础说明](../../catalog/skills/framework-experiment-guide/FOUNDATIONS.md)。它包含 Pool、Unit、Adapter、候选管线、偏好、成员维护、局部精修、方向投影与跨 Case 的共同认识。每个入口再叠加自己的工具和交付要求；自由装配的在线选项与表达式限制不成为 Project 的能力上限。

Project 入口会自动读取当前版本中已保存的 `DESIGN.md`、README、Project 配置与部分 Case 的配置/装配片段。清空聊天历史或重建助手仍可读取这些保存事实；源码摘要、基础说明版本和请求绑定，准备后或模型调用期间发生变化会明确拒绝旧上下文。大工程只自动加载有界摘要，缺失或截断会标出，再由工具定向读取；不会为读取说明执行 builder 或创建 Unit。

两个入口也按问题检索同版本的框架事实，例如父代选择器的真实签名、成员槽位映射、方向投影契约。Project 中当前装了什么与框架支持什么分别提供；静态事实中的 `online_bound=False` 只表示没有网页装配绑定，不能据此断言框架不支持。默认 Project 摘录最多涉及四个 Case、十段正文、24 KB；未载入和截断位置明确标出，仍可继续使用原有只读工具。

因此可以直接提出“从 GA 最终成员挑精英，再用 VNS 精修”，随后继续问“只改变第二父代来源，保留交叉公式”。基础职责预先提供，具体接口仍查当前源码。用户已保存的设计、AI 建议、当前采用方案和真实运行结果分别解释，未保存聊天及浏览器中的采用记录不会自动成为持久决定。

这属于每次调用自动准备的上下文，没有改变模型权重，也不保证模型所有判断正确。格式合法、同一份基础成功加载和回答正确是三项不同验收。可通过[新会话验收脚本](../../catalog/assistant_session_acceptance.py)对两个入口提出同类算法问题，记录空历史、深入追问、实际模型调用和逐回答语义审阅。

2026-11-23 的实际检验已证明空历史能取得已保存设计，也能继续追问，但严格语义验收尚未全部通过：模型仍会混淆底层池与调用期 Pool 方法，或写错预算和字段归属。详见[实际记录](PROJECT_AI_COLLABORATION_ACCEPTANCE_CN.md)。源码级深入目前提供具体开发位置与修改建议；应用源码补丁仍需开发工具执行，不能将网页助手的文字建议视为已修改代码。

同日后续修复了调用类型和工具协议，并用原模型完成两道固定算法任务的开发续验：一题首次执行通过，另一题实际失败后由原模型查接口修改、重新测试通过。它们验证了开发闭环，不替代上述全部讨论题的语义评估，也不表示已训练模型权重；最新证据列在实际记录开头。

## 从算法想法深入到具体修改

继续直接描述想改变的行为即可，不需要记工具名称。Project AI 可在服务内调用三个源码工具：

- `framework_api`：从当前 Python 源码的语法树查类、函数、方法签名、字段、继承来源和相应正文。也能查询当前 Project 文件中的配置类；不导入模块，不创建 Unit。结果带源码摘要与位置，歧义和动态部分会明确标出。
- `project_config_values`：按配置源码中的有限纯表达式计算派生值。例如步骤预算直接取实际属性的计算结果，不能由 AI 猜一个公式。它不执行构造器、`__post_init__` 或参数验证器，仍须遵守原 Case 参数契约；不支持的表达式返回未完成。
- `check_project_edit`：提交一个目标文件的完整 Python 源码，检查语法及可静态识别的框架方法、字段和调用参数。返回与工程版本、源码字节绑定的 `edit_digest`；最终交付必须引用本轮未被拒绝的摘要，才能形成页面可见的源码方案。它不写文件或执行代码。

当前 API 查询覆盖随 NSGABlack 包提供的白名单源码目录、所选 Project，以及安装的 BlackBase 的公开 `types.py`。例如 `CandidateBatch.numeric_matrix` 必须查实际拥有者 `blackbase.types`，而不是猜它可直接迭代。查询通过定位源码进行，不导入依赖或执行构造器；其他外部依赖、未解析基类和运行时动态扩展明确保留为未知。

例如直接说：“保留 GA 的生存选择和交叉公式，重新定义父代怎么配对，给出对应文件的完整修改。”AI 应先查真实父代接口与调用方传入的池类型，再给出源码方案，根据工具诊断修正；不能把底层 `SolutionPool` 当成调用期 `Pool`。`nr` 这类参数也应查明属于配置还是 Unit。

接口查询也解析 `Pool = ChangeSelection` 这类静态别名与公开导出，返回实际对象和别名来源；不能因短名称未直接定义一个 class 就判不存在。类查询先交付签名摘要，需要正文再按方法查。上下文收缩会保留已查到的签名、字段和来源，减少重复扫描。服务端还保留最后两轮：倒数第二轮仅开放方案检查、参数方案与结果回读，最后一轮不再发送工具定义，要求交付回答或明确缺口。这是请求预算的控制，不是算法生命周期的新机制，也不保证模型一定能交付代码。

定向查询类字段时，还可取得 `member.value_contract`：若默认值调用的工厂在真实源码中明确声明返回类型，工具沿导入和返回注解给出该类型、工厂签名及相关文件摘要。例如 `ClassVar` 只说明字段归属，不能据此猜测字段存的是字符串。这个结果标记 `runtime_validated=false`，不执行工厂；动态赋值、无法唯一解析或缺少注解时返回未知，仍须查证或运行验收。这里补的是通用类型证据，没有替模型补写算法。

静态检查只检查已解析的部分。变量的显式类型绑定仍是假设；外部库、动态属性、未注解的返回值和算法数学可能无法判断，工具会列出未检查项。即使没有已知错误，状态也是 `needs_runtime_validation`，不是“算法已验证”。页面展示正文与检查结果；源码方案不会自动覆盖已采用的参数配置或启动试跑。实际应用与行为检查需要开发入口，当前网页运行器不会执行模型生成的任意 Python。

开发入口可以在构造 `ProjectAssistantRuntime` 时另外提供可信的 `edit_validator` 回调；浏览器请求和模型工具参数不能安装验证器。它接收精确源码方案，在预先指定的临时工程中验收，返回同一 `code_sha256` 的结果。失败信息会随 `check_project_edit` 返回给 AI，供它修正后重新检查；已知失败的摘要不能作为最终源码方案。返回其他代码的收据会拒绝，验证器异常只交付失败，不泄露异常中的凭据。原工程版本在前后再次核对。

默认网页没有该回调，不增加源码执行权限。回调及其隔离、时间限制、资源授权和验收条件由可信开发端负责，这不是任意 Python 的安全沙箱。临时源码行为验收与原参数试跑结果分开记录，即使临时验收通过，也不表示已将修改应用到原 Project。

### 同一个模型完成查接口、测试与修复

开发端可在上述回调基础上启用严格模式：`require_validated_edit=True`，并提供非空 `validation_identity`，标识这一次固定的验收条件。两项均在构造 `ProjectAssistantRuntime` 时设置，不能由浏览器或模型临时启用。模型始终使用同一配置和返回的模型身份，错误工具结果回到这一份会话中，不由另一个模型代写修复。

这个模式将一次开发请求分成有限的查证、源码验证、失败后修复与最终交付。发现阶段有预算；到提交阶段仅开放 `check_project_edit`，Provider 使用指定函数的原生工具选择。执行失败后允许定向补查，随后重新提交完整源码。阶段已关闭和参数格式错误分别返回 `project_tool_phase_closed`、`project_tool_arguments_invalid`，并说明当前允许工具和字段，避免只收到一句“工具无效”而反复猜测。

最终交付必须匹配本轮最后一份通过执行的源码：`status=passed`、`executed=True`、`executed_source_sha256` 与源码 SHA 一致，且 `validation_identity` 一致。模型文字宣称成功、只有静态通过、旧版本通过、重新检查已失败的同一份代码，都不能生成有效交付。页面进度分别显示当前阶段、实际执行次数与通过次数。

可信回调需要自行决定如何建立临时工程和预先固定行为断言。不能把“能运行两代”当成算法正确，也不能在模型失败后改数学期望来放行。当前开发验收脚本 [assistant_closed_loop_acceptance.py](../../catalog/assistant_closed_loop_acceptance.py)提供两个预设算法任务，在 `check_project_edit` 调用期间实际执行行为检查和正式 Case；源码、错误、下一次请求与最终收据分别保存。

```powershell
python -m nsgablack.catalog.assistant_closed_loop_acceptance --model-config C:/private/model.json --allow-paid --allow-code-execution --maximum-requests 24 --out .pytest_cache/same-model-acceptance.json
```

这条命令会真实调用付费模型，并在临时工程执行其源码。它是开发验收入口，默认网页没有开放该能力。报告分别记录初次执行通过、源码审查后修改，以及“实际执行失败 → 错误进入下一次模型请求 → 模型修改源码 → 重新执行通过”。只有最后一种才算运行错误后的自行修复。请求预留、实际 HTTP 和未发送的本地拒绝也分别计数。

受控开发门禁支持可静态确认的 Unit dataclass 子类在自身初始化钩子中调用标准 `super().__post_init__()`；需要能解析装饰器、正式基类和名称绑定。未知装饰器、遮蔽或动态继承不能借此放开，`__dict__` 等反射仍被拒绝。这项规则来自真实 Unit 改动中的误拦，不要求用户改写正常继承代码。允许策略升级会产生新的验收身份，旧报告仍按原策略保留；新策略下同字节补验必须单列，不能倒改模型当轮的失败或最终交付。

若开发驱动本身有错误，必须封存原报告后另开开发续验，明确累计调用预算。续接只恢复留存的公开消息，重新绑定当前工程、模型与验证身份；原收据不继承通过权威。压缩记录保存恢复前和实际发送消息的摘要及字节数。没有保留的私有推理不能称为已恢复，同题续验也不能称为新的独立泛化测试。当前真实结果见[验收记录](PROJECT_AI_COLLABORATION_ACCEPTANCE_CN.md)。

长对话续接时，原始宿主输入继续完整保存；只读背景正文可在发送前转为带路径、来源摘要和正文摘要的显式指针，后续可重新读取。算法要求、当前工程身份、调用契约、最近源码和真实错误不能借此删除。发送尺寸还须通过实际 Provider 序列化检查，不能只估算工具消息的长度。

同一回复可以查询多个接口，因此最新一轮只读 API 结果也不能无限保留重复正文。达到预算时，对过长正文保留精确来源指针，并去重同一响应中的来源和成员信息；签名、值类型契约和返回类型契约保留，短的定向函数正文仍可读取。源码提交、执行收据和最近错误不使用这条只读收缩规则。完整原始响应留在宿主记录中，不把省略后的指针冒充完整原文。

这套机制也不要求先微调模型。频繁变化的接口应从当前源码取证，具体修改用检查和行为测试验证；微调可在积累可信示例后改善稳定的工作方式，但不能代替版本查证。OpenAI 的[优化说明](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy)区分了上下文不足与行为一致性问题，并要求保留独立评估集；此处借用这一方法，不表示当前 DeepSeek 模型已训练或支持某个微调服务。

### 接口类型和工具协议如何变得可靠

开发端现在可以用 `edit_call_contracts` 声明真实调用入口的参数类型，按目标文件和 `函数.参数` 定位。例如完整 change 接收 `ChangeRequest`，生存选择回调接收调用期 `ChangeSelection`。这是一份宿主调用约定，随本轮源码位置及摘要进入上下文；不是根据变量叫 `pool` 就猜类型。检查器据此检查未注解回调，模型的 `bindings` 不能覆盖相同入口。它仍不保证任意 Python 调用者真的传入该类型，可信调用者和行为测试负责这一点。

真实池 API 补充明确的返回类型注解。对其余缺少返回注解的方法，源码查询可在有限、单义的构造或委托路径中给出 `return_contract`，带推导依据及依赖源码摘要；涉及无法判定的自定义构造或多路径时仍返回未知。模型可以沿实际返回类型继续查询，属性与方法也分别检查。候选形状依赖调用位置与算法规则，继续由运行验收判断，不为某一道题在通用检查器里硬编码维度。

Provider 另有显式的 `protocol="json"` 模式：将可用工具、参数 schema、允许阶段和历史调用作为 JSON 资料交给同一个配置模型。回复必须是完整的工具调用或最终回答对象；校验成功后才转换为内部调用。历史正文保留原值，不靠提取 DSML、Markdown 或正文中的 Python 来执行。非法回复可以作为一次已消耗的模型回合反馈给原会话；未知 HTTP 失败仍不自动重试。

服务端通过 `--project-tool-protocol json` 选择该模式，或在构造 `ProjectAssistantRuntime` 时传入 `tool_protocol="json"`。原生模式仍可显式选择；不因一次失败自动换协议或模型。DeepSeek 的 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/)与[工具调用](https://api-docs.deepseek.com/guides/tool_calls/)是不同输出机制，客户端仍须核对参数与本轮权限。该能力属于协议适配，未新增 Solver、Pool 或 L0 执行机制。

本轮优先采用三项技术：由源码支撑的接口检索、明确的调用参数类型、同模型收到真实测试反馈后继续修正。结合已观察到的类型和协议错误，这是当前可直接验证的路线。微调更适合在接口和协议稳定后，使用经过验收的成功轨迹学习“何时查证、如何用工具、怎样修复”；另留未见过的算法任务评估泛化。当前的少量失败轨迹尚不能证明需要微调，也不能证明微调会修复传输协议。判断方法参考 [模型优化流程](https://developers.openai.com/api/docs/guides/model-optimization)，当前没有发起训练任务。

## 一次完整协作

1. 在实验台切换到“已有 Project 协作”，选择服务提供的项目。
2. 描述业务意图，例如“沿用这个排程模型与数据，先以小预算跑一次；保持原始目标与约束”。AI 可以列文件、读取源码和说明、检查 CSV／XLSX 结构，并读取 Case 实际声明的参数。
3. AI 通过工具提出结构化配置。页面展示方案、来源与工具记录。点击“采用这个方案”后，该方案成为当前配置。
4. 点击独立的运行按钮。运行器核对方案摘要和项目版本，在隔离副本中调用原 Project／Case 入口，由 L0 发放资源；原项目与数据不被修改。
5. 完成后查看本轮原始反馈、业务审计与实际数据。继续向 AI 提问时，页面只传试跑身份，AI 从独立的只读通道回读真实结果。

长文件可以按关键词定位后再读相关行。对话达到上下文预算时，服务显式收缩较早的只读正文，保留来源、文件摘要与行号；需要细节时重新读取，不生成一份未经核对的“记忆事实”。页面显示模型和工具进度。

采用方案不会自动运行。修改方案后，旧结果仍可查看，但不会作为新方案已经运行的证据。失败与超时也可以交给 AI 分析。

模型可能误述“已校验”，实际以右侧工具交付的结构化方案为准。没有该方案时，页面会明确提示本轮未交付新配置，文字建议不会替换已采用配置。运行后可下载经过大小与摘要核对的实际导出 ZIP；整数 CSV 和浮点审计的统计口径应分别核对。

## 与已有模型的关系

一个新的业务偏好不自动意味着新建 Problem、Unit 或 Adapter。先读取实际实现，再决定调整原始目标、选择偏好、候选构造还是算法决策。已有多目标不能因为用户概括了两个诉求就被删成双目标。

以排程为例，日产量平滑、某机种连续生产、机种覆盖和总产量各有具体定义。参数有类似名字，不代表这些指标等价。数值建议只是下一次实验配置，效果必须依据本轮数据和收据判断。

## 当前支持范围

- 只读取部署者明确提供的可信正式 Project。模型使用项目句柄和相对路径，不配置宿主目录或外部地址。
- 数据结构检查支持有界 CSV／XLSX／JSON 预览，保留文件 SHA 与版本；不执行工作簿公式。
- 配置复用 Case 可静态核对的参数类型、默认值与 choices。未声明的参数、任意文件路径、Python 和 shell 命令不作为执行输入。
- 首版试跑使用单 CPU 线程、无 GPU、有限步骤和时间。资源继续属于正式 L0，AI 不自行申请额外设备。
- 日志、临时目录和产物与源码分离。运行依据包含实际项目版本、读取的数据摘要、原始反馈与正式结果发布收据。
- 新算法实现、任意源码编辑、缺少参数契约的 Case 和额外后端安装仍是明确的开发工作；助手不能将建议写成已执行。

## 部署

助手服务负责资料读取和模型调用，运行服务负责正式 Project 执行。模型凭据不进入运行器。

运行器可以配置独立 `result_token`。该令牌只允许读取 `/project/jobs/<id>`，不能提交运行、读取旧装配任务或调用其他接口。助手通过部署者配置的 `NSGABLACK_PROJECT_RESULT_CLIENT_CONFIG` 使用此只读通道；浏览器不能指定模型地址、文件根或运行服务。

默认源码发布包不携带业务数据。需要真实 Case 数据时，部署者通过 `package_context.py --project-asset <正式Case内的CSV或XLSX>` 逐文件显式选择，并将其 SHA 记入发布清单。没有相应资产时不得用生成的模拟数据冒充真实输入。

## 验收口径

分别记录：模型实际读取的资料、经校验的方案、独立试跑、结果回读、需求变更后的新方案和运行。工具调用次数与用户请求预留次数分别记录；请求去重不等于重试模型，服务不会自动重试不确定的模型 HTTP 请求。

小预算验收证明协作链路、来源与执行成立，不直接证明达到历史长预算结果或全局最优。
