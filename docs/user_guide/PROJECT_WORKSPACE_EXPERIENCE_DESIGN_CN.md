# Project 工作区：从写代码出发的交互设计方案

日期：2026-10-28。

**状态：设计提案。** 本文与配套界面草图用于讨论下一版体验；不代表相关能力已经实现或上线。本轮只阅读现有实现、整理方案与展示交互草图，不调整现有服务、不运行工程、不调用 DeepSeek。

2026-10-28 首轮实施覆盖：完整工作区与独立编辑器主题、精简文件工具、浏览和运行目标分离、组件先开小窗并可固定、试跑保留编辑现场。本文其余选区协作、多文件 AI 修改、新文件创建等仍是待实施设计；实际可用范围见 [工作区手册](PROJECT_CODE_WORKSPACE_CN.md)。

## 1. 工作区应该替用户接住什么

用户进入这里，一般带着具体意图：“改一下这个变化函数”“在 GA 后接一段精修”“这个组件到底怎么放进我的工程”“这里报错了”“上一轮结果为什么变了”。页面应该接住这个意图，持续保留代码位置、工程上下文、改动与验证结果。

建议把产品定位为：**一个了解当前 Project 的代码工作台，能陪用户完成一次改动。**

平时直接写代码；需要帮助时，可以在代码旁查用法、问原因、提出修改、查看差异。普通 Python、已有自定义算法和正式脚手架都能继续使用。组件目录负责提供可查证的材料，AI 负责结合当前工程解释和提出改动，正式运行器负责验证实际行为。

用户不需要为了一次小改动重新填问题定义、挑一遍算法配方、阅读所有框架术语，或者离开代码去另一个完整页面找资料。

## 2. 当前页面为什么仍然别扭

以下结论来自本轮静态阅读与已有隔离界面截图，不是本轮真实账号体验验收。

### 2.1 功能入口齐了，任务还需要用户自己连接

当前顶部提供“保存、审查、查组件、试跑设置、实验结果”。每个入口有用，但“发现错误 → 理解错误 → 找到正确接口 → 修改相关文件 → 验证这次改动”仍需要用户手工串起来。

右侧一次只能显示 review/reference/run，虽然已有输入保留，工具之间仍难以持续对照并延续同一次任务。代码里的符号、侧边组件资料与实际修改之间还缺少直接联系。

### 2.2 页面有多层重复工具条

顶部动作、职责分类、文件标签、文件路径、定位/差异/选项、编辑器自己的工具条，都在争首屏。用户已经理解的文件名和保存状态重复出现，真正写代码的区域被向下推。

新设计应把命令放在合适的位置：应用级命令留顶部；文件命令留标签或快捷键；错误操作贴着错误；组件用法贴着符号。减少同时展开的控件。

### 2.3 浏览文件会影响运行目标

`catalog/lab_workspace_ui.py` 的 `_open_file`、`_jump_to_file` 会在打开另一个 Case 的文件时更新所选运行 Case。查阅参考代码与选择下一次运行对象因此发生耦合。

新设计要求：**打开文件只改变编辑位置；运行目标通过显式选择改变。** 跨 Case 时显示一条紧凑提示：“正在查看 case_b，运行目标仍为 case_a”，并提供“切换运行目标”。

### 2.4 现在的“审查”需要说清范围

`catalog/lab_workspace_review.py` 复用静态语法和装配调用位置；确定性修复只处理严格匹配的缺冒号。它没有实现任意组件兼容检查、算法审查或多文件 AI 修改。

已有 `PROJECT_AI_COLLABORATION_CN.md` 描述的是另一条“读取正式 Project → 提出配置 → 独立试跑 → 回读结果”的协作路径。不能据此声称工作区已支持源码级 AI 编辑。下一版需要把这些已有读取与证据能力接到编辑任务中，并新增受版本约束的改动交付。

### 2.5 运行视图的口径需要统一

当前 `_render_run` 在提交作业后会把主面板切到 results。使用指南同时提到“提交后进入实验结果视图”和运行不强行切换编辑现场。下一版明确采用：提交后在底部显示运行进度，保留当前文件和光标；用户主动打开完整结果。

## 3. 推荐的主布局

### 3.1 顶部：我在哪，准备对谁做什么

第一行只保留：Project、运行 Case、全局搜索、检查、运行。

- Project 显示实际工程名称。副本、修订编号和连接细节放进名称旁的详情。
- 运行 Case 有清楚的文字和独立选择。查其他 Case 文件时不偷偷变化。
- 全局搜索支持文件、符号、已装配组件及 Catalog；结果按类型分组。
- “检查”默认执行当前支持的轻量检查。菜单清楚列出静态、装配与行为验证，显示各自是否执行代码。
- “运行”旁显示 Case 与预算摘要。普通再次运行沿用本 Case 设置；首次运行、设置不完整、资源或目标变化时展开配置。

有草稿改动时，提供明确的“保存并检查”或“保存并按当前预算运行”。点击本身表达这组动作的意图；目标、预算与资源没有变化时不再弹第二次确认。检查失败就在底部继续修，不要求用户把保存、设置、检查、运行拼成四段流程。

第二行是用户已经要求的顶部职责导航：**全部代码 / 问题与数据 / 候选处理 / 搜索与编排 / 偏好与能力**。

这些标签帮助找位置，不创建另一套文件分类权威，不改变工程内容或运行目标，也不关闭已打开文件。Unit 的自定义实现仍归实际所属文件；不因为顶部有某种分类而重新归档源码。runtime、evaluation、solver 和 Project 公共文件始终能从全部代码与文件树找到。

### 3.2 左侧：安静的工程导航

默认只有当前 Case 的展开树、Project 公共文件、其他 Case 的折叠入口。修改点用小圆点或数量提示，不堆复制的状态卡。

查文件使用全局搜索或快捷打开。版本历史、连接设置与来源管理放进紧凑工具入口。打开工程不应占一整列顶部的主要注意力。

文件树可以收起；当前位置、展开状态和文件标签在查组件、看结果之后保留。

### 3.3 中央：连续的代码空间

- 顶部文件标签显示路径后缀与未保存标记；相同文件名必须能分辨。
- 路径面包屑和符号定位合成一行，不再叠多层大按钮。
- 行号、语法颜色、缩进辅助、查找替换、撤销重做是默认体验。
- 新建文件、全工程搜索、跳到定义、查看签名与参数提示属于基础编辑。搜索默认限定当前 Project。能写一个新算子并找到装配位置，应由编辑器和工程工具直接支持，不依靠一次模型对话来替代。
- 点击诊断定位实际文件与行；错误划线和提示与当前草稿内容对应。
- 选中代码可直接“解释”“检查”“修改”。这是同一个协作入口的不同意图，不开三个新模块。
- 查组件采用短暂停留的小窗；需要持续对照时固定到右侧。
- 查看多文件差异时，中央切为本次改动预览；关闭后回到原代码位置。

保存保留常用快捷键；状态条明确区分“草稿已暂存”“已保存修订”“正在运行哪个修订”。去掉多个同样醒目的保存按钮。

### 3.4 右侧：围绕当前任务的协作区

默认收起，或按用户上次状态恢复。打开时保留一个持续任务：用户意图、当前上下文、解释、改动提议、验证结果。

组件资料可以固定在同一区域，并保留任务输入。关闭资料后回到原任务，不丢搜索条件、不重置对话、不改变文件。

常态不同时展示 AI、完整组件目录、审查表单和运行设置四列。长组件文档可临时展开为更宽阅读区；代码区仍可一键返回。

### 3.5 底部：问题、日志、结果

默认是一条紧凑状态条。出现错误或用户主动打开时，展开“问题 / 运行日志 / 结果 / 本次改动”。

这里的日志是正式作业日志。首版不需要开放任意 shell 终端。

点问题跳到对应代码；点日志错误可以带该作业与对应修订进入协作区分析。旧结果始终显示所属修订，避免拿旧运行替新草稿背书。

## 4. 两种工作状态，共享一个工程

### 4.1 代码优先：默认状态

用户知道要改哪一段：中央代码占主位置，树较窄，右侧按需展开。AI 帮用户解释当前位置、查符号、提出局部或多文件改动。

### 4.2 方案预览：复杂需求时展开

用户说“GA 停滞后取最终成员中的精英交给 VNS，再送回 GA”。中央先展示这次任务的输入、触发、交接和预计修改文件，右侧保留需求及尚未确定的问题。明确后生成改动预览。

这是同一次任务的展开状态，不是另一套隐藏配置，也不要求所有用户先走向导。可以从任何已有文件进入，也可以直接跳回代码修改方案。

推荐以代码优先作为默认。方案预览用于降低复杂装配的理解成本，不取代普通 Python 的自由表达。

## 5. 五条必须做顺的使用路径

### 5.1 我只想改一个变化函数

1. 搜索函数，打开源码，直接修改。
2. 轻量语法诊断在原位置更新，不调用模型、不重建页面。
3. 不确定时选中代码，输入“保留双后代和池输出，只减小扰动”。
4. AI 明确指出理解的函数、调用处和限制，给出针对当前草稿的差异。
5. 有依赖的多文件改动默认成组采用；也可查看和选择部分改动，部分采用后重新校验，不声称整体方案仍成立。撤销不覆盖随后手写的内容。
6. 保存后检查或沿用上一轮预算运行，日志在底部出现，代码仍在原处。

这里不要求重新填写 Problem、创建新 Unit，或者先把普通函数做成一整套组件。

### 5.2 我知道用途，不知道组件叫什么

1. 在代码处查“停滞后局部搜索”，结果结合当前 Case 和组件真实能力显示。
2. 小窗首先回答：它做什么、这个工程能否接、要准备什么、具体放在哪。
3. 参数先显示必须提供的几项，默认值和高级参数按需展开。缺上下文的对象必须解释来源。
4. 点击“帮我接到当前工程”后，协作区读取真实工厂和必要调用，给出预计改动与依据。
5. 采用差异后，在原代码位置看得到实际装配；检查状态与真实运行状态分开。

“复制通用片段”继续保留，但不把复制完成当作装配完成。没有足够资料或接口不支持时，指出具体缺口。

### 5.3 我想在 GA 后接 VNS

用户可以直接说完整想法。AI 先复用现有 Problem、Pipeline 与已装配组件，读取当前工作区的具体实现。

第一份回应应该是可以核对的任务理解：

- 从哪个已发布视图取解；最终成员与全部接纳提案不能混称“最好解”。
- 何时启动，例如固定阶段或已声明的停滞信号。
- 每个精修实例处理多少起点，比较规则从哪里来。
- 返回候选由哪个接收方比较、接纳、替换。
- 哪些文件需要调整，哪些已有实现可以复用。

只追问会改变算法意义的缺失选择。可以一次给出有理由的建议默认值，标出假设，避免一连串小表单。

Pool 视图展示为“从谁取、按什么规则、交回谁”，高级详情才展开引用、创建者路径和投影版本。不能在网页里另造一套 Pool 调度器，也不能暗示任意两个 Adapter 都能无条件交接。

### 5.4 我有复杂业务问题，想用自然语言开始

先判断用户在继续已有模型还是创建新 Case。已有排程模型优先读取实际实现与业务说明，不因为一句口头概括就改写变量形状、删除目标或简化多产品生产语义。

创建新问题时，AI 生成可编辑的问题说明与对应代码草稿；变量、目标、约束、数据来源与尚未确认的假设可在一起核对。复杂问题允许直接用普通 Python，不限制为演示用表达式。

例如“20 台机器、31 天、每天可切换多产品”不足以决定是 620 个整数、带产品维度的分配结构还是序列表示。缺失的产品切换、物料与产能语义应向用户确认，不能自行把真实模型降维。

生成源码、多文件新增、数据绑定与后端支持需要分步交付。未安装的依赖与不支持的运行能力必须明确显示，不能用一段成功提示代替实际接入。

### 5.5 运行失败，或者结果和预期不同

1. 底部保留失败作业、对应修订、报错位置和原始日志。
2. “分析这个错误”携带精确作业身份，而非只复制一段报错。
3. AI 读取运行时实际使用的代码；若用户已有新草稿，同时显示新旧差异。
4. 提议修复针对当前版本生成，不能把旧运行的行号直接套到新代码。
5. 修复后新检查、新运行各有记录；历史失败仍保留。

结果不好时，先核对问题定义、预算、数据和实际指标，再提出下一次实验。多目标不默认求和；不同问题定义的分数不自动排优劣。

## 6. “智能”具体出现在哪里

### 6.1 不要求用户手工重复交代工程

协作默认知道当前 Project、显式运行 Case、当前文件、选区、草稿基线和本次意图。需要时读取实际调用文件、相关组件说明及用户指定的作业。

修改范围默认跟随显式选区或当前文件所属 Case；运行 Case 只表示执行目标。二者不一致时显示各自范围，不因用户查看文件或向 AI 提问而默默改变其中任一项。

上下文以可见摘要呈现：“当前选区 + 2 个相关文件 + 组件接口”。用户能查看展开内容、增加文件或移除无关材料；查看组件说明不等于把该组件加入工程。

当前编辑器传输尚无选区或符号字段，工作区保存也只允许修改已有文本；这些是后续需要扩展的真实接口。新建算子、多文件补丁及采用/撤销必须作为一组有基线校验的改动交付，不能只在聊天里返回代码。

### 6.2 回答要落到可以采取的动作

解释附实际文件位置；检查附问题、依据与影响；修改附差异、涉及文件和验证计划。“理论上可以”后面要能看到需要怎样接入当前工程。

每次交付保留一个连续任务，后续“只保留前两个改动”“改成从最终成员取”“先别运行”都应修改同一任务，而不是从头再生成工程。

### 6.3 自动纠错按证据分层

语法与明确的机械错误可以即时指出，并提供快速修复。组件参数、缺少依赖、接入位置等需结合接口和工程检查。算法、业务约束和指标语义需要阅读、解释、测试与运行证据。

用户可以一次授权本任务在指定 Case 的草稿内修改，随后连续小修正沿用授权；保存、执行和扩展修改范围仍是明确动作。避免每改一个字符都再问一次，也避免把“帮我解释”当成自动改代码。

### 6.4 AI 提议不改变验证事实

界面使用可点开的状态文字：“已生成改动”“语法已检查”“装配未检查”“试跑未执行”。模型说“这样没问题”不能点亮检查通过。

无法检查的数学性质、任意 Python 副作用与算法正确性要说明证据边界；用户不需要浏览一页底层术语才知道下一步该做什么。

## 7. 组件审查应该怎么用

### 7.1 当前工程的接入检查

从实际装配符号进入，回答此处是否缺参数、消费什么候选、需要哪些声明、返回什么、与所选接收方有何边界。可跳转到相关调用，提出多文件改动和可执行的检查计划。

静态引用只是线索；动态工厂与实际装配以对应检查或运行证据为准。未知时显示“尚未确认”，不声称已完整理解。

### 7.2 组件自身的实现与资料审查

框架开发者可从同一组件入口进入专门任务：核对公开接口、实现、用法示例、声明能力与测试证据。结果按“问题 / 建议改动 / 未验证项”呈现，每项保留源码位置与版本。

建议的资料更新先形成待审内容。资料生成、人工采用、源码检查和示例实际运行分别有记录；不让 AI 改写资料后自动变成已验证事实。

此任务按需展开，不把组件治理功能全部铺在普通写代码的首屏。

## 8. 好看应该落实到哪些细节

- 中性色承担背景与层次，一个主色表示当前操作；错误和差异颜色各有固定用途。
- 代码采用舒服的等宽字、正常字号、清晰缩进和克制的语法配色。中文说明用清楚的无衬线字。
- 文件树、代码、协作区由细分隔线形成连续工作面，减少一层层圆角卡片。
- 顶部命令紧凑，当前文件和任务有明显主次；不放与本次编辑无关的统计大卡。
- 1440 宽时可同时看树、代码与协作；1280 宽时优先保留可写代码宽度，按需收起树；更窄时协作作为临时抽屉。
- 用户可拖动区域宽度，关闭后不丢上下文；参数、组件长文与完整结果可临时展开。
- 键入、选区和光标在编辑器本地响应。查资料与模型请求不能使编辑器重挂载、闪烁或抢焦点。
- 每个交互有真实状态：正在检索、正在生成、已取消、连接中断。取消后部分草稿和已完成证据可以查看。

草图只用于讨论区域关系和任务路径；它不证明最终编辑器手感、缩放、拖动分栏或真实模型效果。

## 9. 费用、等待和草稿恢复

普通键入、语法诊断、文件导航、查询已有组件说明与查看旧结果不发起付费模型请求。AI 在用户开始任务、继续任务或明确开启协助时调用；不因切换标签反复整理整个 Catalog。

框架资料按版本缓存；当前任务补充必要源码、差异和运行证据。界面可查看本次模型、已发送材料范围与实际用量；不虚构 token 估计，也不新增任意“每日编辑次数”。

当前模型服务尚未把供应商 usage 完整交给页面，用量展示属于待接入。供应商没有返回实耗时显示“未提供”；不能拿请求次数当 token，也不能把未知费用写成 0。

任务级取消、去重与已生成结果复用可以避免无意重复调用。失败是否重试要明确；网络不确定时不悄悄重放付费请求。

拟增加的草稿恢复按用户、Project、基线修订隔离。自动暂存只表示草稿可恢复，不表示已保存成正式修订或参与运行。断线可继续编辑已加载文本，重连后核对基线；冲突时保留两份差异。

当前实现的未保存草稿仍主要位于会话，因此持久恢复属于待实现项。不能用“草稿已同步”让用户误以为刷新后一定不会丢失。

## 10. 复用什么，新增什么

已有编辑器行号/高亮/查找与草稿、修订 CAS、组件资料读取、有限静态审查、正式试跑、结果收据都继续复用。已有 AI Project 协作的资料读取、配置建议和结果回读也可以接入连续任务。

需要新增的关键能力是：符号/选区上下文、就地用法、多文件改动预览与安全采用、任务连续性、底部统一证据、草稿恢复，以及显式分离浏览位置与运行目标。

复杂交互需要稳定的编辑器页面状态。后续实施应评估独立前端外壳，继续复用现有服务与正式运行契约；先用关键路径原型验证手感，再确定技术迁移范围。单纯增加样式规则不能保证这些体验成立。

工作区属于框架工具层。这里不新增 Solver 生命周期、Pool 权威或资源授权者，不把 ML 运行支持写成打开网页即可获得的能力。simon 专属访问和现有服务边界继续保留。

## 11. 实施顺序与验收

第一步：确认代码优先布局、分类/文件/运行 Case 的分工、组件小窗和改动预览。用真实任务走通，不先追求全功能页。

第二步：把组件查阅、语法诊断、正式检查和运行结果串到同一编辑现场。补草稿恢复与跨文件导航，解决切换造成的状态意外。

第三步：接入按需 AI，从“解释当前位置”“修改一个函数”“接入一个已有组件”开始，逐步支持跨文件任务与复杂方案。

第四步：补组件自身审查、自然语言新问题与更深的多 Case 协作。对尚无运行后端的场景提供代码和待验证状态，不伪装能运行。

验收必须亲自按任务走，而不是只统计按钮、组件数或通过的测试数：

1. 不读教程，能找到并修改现有变化函数，查组件后光标和未保存内容仍在。
2. 看另一个 Case 的代码后，原运行目标不变；运行前能看清具体目标和修订。
3. 从代码符号直接找到用途、实际参数与在当前工程的接入位置。
4. 一次 AI 任务能解释多个相关文件、预览改动、部分采用并撤销；新手写内容不被旧建议覆盖。
5. 错误能回到精确版本的代码；修复后检查和试跑结果分别更新。
6. 运行时可以继续编辑，结果明确绑定旧修订；打开结果再回来，现场保留。
7. 断线、取消、刷新与并发保存后，草稿、任务和验证状态符合界面承诺。
8. 普通编辑和导航无模型账单；一次任务的付费调用可查，失败与重试不隐蔽。
9. GA、VNS、MOEA/D 与自定义函数都通过各自真实契约展示能力，没有为了界面整齐强行统一算法流程。

本轮交付的是设计讨论输入。后续实现按确认后的任务路径推进。
