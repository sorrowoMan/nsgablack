# Project AI 协作实施与真实排程验收

日期：2026-10-26。范围是让现有 DeepSeek 助手读取可信 Project、提出可检查配置、经独立采用与运行后读取真实收据。本轮不修改排程业务模型，不训练或微调模型，不把短预算试跑当成历史长预算效果。

## 实现结果

实验台新增“已有 Project 协作”，保留原自由装配入口。使用流程见 [使用指南](PROJECT_AI_COLLABORATION_CN.md)。

- `catalog/lab_project_sources.py` 提供可信项目发现、版本清单、源码读取、字面关键词定位与 CSV/XLSX/JSON 结构检查。路径、链接、敏感内容和响应预算在服务端检查；读取不执行导入或 builder。
- `catalog/lab_project_assistant.py` 用真实模型工具调用执行“读资料、检查参数、提出方案、读取结果”。长文件可以定向定位，旧只读正文达到预算后显式移出上下文并保留出处。结构化方案与真实结果收据仍由服务持有。
- `catalog/lab_project_trial.py` 静态核对实际 Case 参数，在隔离副本中经正式 Project/Case 与 L0 执行，绑定源码版本、数据摘要、运行身份与发布收据。参数来源也使用资料清单白名单，不扫描隐藏/secret parser。
- `catalog/lab_project_ui.py` 将讨论、采用、运行分开；显示进度、原始报告和已核验的结果 ZIP。没有工具交付的新方案时，文字建议不能覆盖原配置。新方案也不能继承旧方案“已验证”状态。
- 继续使用原 AssistantManager、JobManager 与请求预留账本。助手的独立结果令牌只可 GET 项目结果，不能启动运行。模型凭据不进入运行进程。

本轮没有新增求解器控制面，也没有用网页表达式或模拟数据替换原生产 Case。当前发现列表有 50 项；没有据此宣称全部 Case 都已经执行验收。

## 真实模型调用与失败记录

证据目录：`.pytest_cache/project-collaboration-20261026/`。上一轮“2 次请求、0 个可应用方案、0 次运行”的基线保留在原目录，未覆盖。

本轮共有 6 个用户级模型任务，合计 58 次实际 DeepSeek HTTP 请求，另有一次在 HTTP 发出前被请求大小检查拒绝。没有自动重试不确定的模型请求；每个任务的身份、工具记录和失败均保存。不能把 6 条预留当成只有 6 次模型调用。

1. v1：12 次请求，读取真实源码和两份数据，生成合法方案 A，状态为 `not_run`。
2. v1：12 次请求，读取 A 收据及源码，因单轮工具循环上限未能交付新方案；失败保留。
3. v2：2 次请求，正确读取 A，但文字声称“已通过 propose_project_trial 校验”，实际没有调用该工具、没有返回方案。此项属于模型误述，不能判为新方案成功；运行器没有执行该文字建议。
4. v2：12 次实际 HTTP 请求，下一次在发出前因累计源码正文超过 128 KiB 被拒绝；失败保留。
5. v2：11 次请求，核对真实 Bias/Pipeline 实现后生成方案 B，只有 `variance_penalty: 0.03 → 0.15`，状态为 `not_run`。部署刷新前置检查曾失败，因此这份成绩明确属于 v2。
6. v3：9 次请求、16 次工具调用，包括真实 `project_find` 与 B 结果回读；只解释本轮事实，未提出新方案，状态为 `verified_trial`。

据实际失败补了源码定位、显式上下文收缩、工具范围与剩余单轮预算提示，以及“本轮无经校验新方案”的页面提示。每日 AI 使用上限仍为 `null`，没有恢复旧的每日编辑额度。

v3 回复仍不等于所有表述正确。例如它把 CV 与 CV²称为“不同量纲”，实际上两者均无量纲；步骤记录中的求值计数是累计值，也应与每步新增次数区分。源码和收据工具解决可核查性，不能代替对模型文字判断的审核。

## 两轮正式排程试跑

两轮均使用原 `production_scheduling` Case，22 机种、156 物料、31 天，完整候选维度 682；BOM 为 22×156、供料为 156×31。实际数据文件摘要一致：

- `machine_material_mapping.csv`：`2aef063f7085b71f08ffb4c9544b83f76e4b392ad3215fa5a751d7c4b3eadd7f`。
- `SUPPLY.xlsx`：`d2d2cb65649b29125e4002295c67f9ee110b956b7fa7607acd7f5d1fffadd192`。

A：`project-trial-d1d24bd1c0a34092b34511ae3e218598`，45.37 秒。

B：`project-trial-64c818fae7ce4ba0a4706df93d15069a`，42.61 秒。

两轮各 8 个逻辑步、104 次求值，5 步 explore、3 步 exploit；L0 为 1 线程、0 GPU、`current=true`。原始四目标保留，五项硬约束审计均为零，物料短缺为零。

### 主方案没有改善

两轮 production 主方案的审计和整数 CSV 完全相同：

- 浮点审计产量 70,395.90432；整数 CSV 复算 70,386。两种口径相差 9.90432，不能混称整数交付量。
- 日产 CV 0.7815458233；机种开/停状态相邻日变化合计 89 次，不是产品切换次数。
- 软偏差仍存在：最低活跃机种数累计缺口 11、低于单机最小产量累计 369.624。`feasible=true` 不表示所有软偏好为零。
- 最后 16 个 accepted 候选及其原始目标、约束逐项相同；跨运行引用身份不同。

Pareto 档案有变化：4 个点中 3 个相同，另一个由产量 66,321.41248、CV 0.848478、开停 56 次，变为产量 68,074.892736、CV 0.793923、开停 55 次；但活跃机种软缺口由 12 增至 14。这是权衡变化，不能称全面改善，也不能说整个搜索完全相同。

现有实现能解释这个结果：Variance Bias 是 `weight × CV`，向选择目标加入偏好；VNS 采用目标求和时，约 −70,000 的产量轴占很大比重。本次调权对四目标总分的变化约 0.38，不保证翻转选择。日志中偏好分数已改变而产量路径相同。production 导出按第一目标选择，也不是选 CV 最小项。这里没有修改原模型或默认算法来制造改善。

两轮 ZIP 各有 15 个导出文件，压缩包与每个文件摘要均核对成功、没有截断。提案摘要、源码版本、运行身份及正式发布收据一致。
