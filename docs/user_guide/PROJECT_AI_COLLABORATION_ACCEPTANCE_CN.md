### 为什么前轮会反复失败，以及实际改了什么

接口错误存在可定位的类型断点：生成的回调参数未注解、检查工具未得到调用者的真实参数类型；`ChangePool.read/subpool` 等方法又缺少返回类型注解，检查器因此只能把后续对象记为未知。现在开发端按目标文件及 `函数.参数` 声明实际 caller ABI，随源码身份进入上下文；类型检查按函数作用域生效，不把同名 helper 参数也强行当成该类型。模型可用别名，但不能换掉宿主声明的实际入口类型。

真实 `ChangePool._selection/read/subpool` 仅补三处返回注解。旧源码完整保存；[注解变更证明](evidence/ai-closed-loop-20261123.change_pool.annotations-proof.json)记录前后 SHA 与差异，移去这三处注解后 AST 一致。源码查询也可对有限、单义的返回路径给出带依据的 `return_contract`，对自定义构造、多路径与动态值保持未知。旧的 `refs()` 和“选择集合直接转数值”用法现在能被提前拒绝；依赖调用位置的候选形状继续由原行为测试检查。

协议侧，旧原生调用实测不遵从指定工具和 `none`。本轮采用显式宿主 JSON 应用协议：不向 Provider 发送原生 tools/tool_choice，将允许工具及参数 schema 作为宿主约定；只接受完整、符合本轮工具范围的 JSON，校验后转换为内部调用。原始公开正文保留并绑定摘要；DSML、Markdown 或正文中的伪工具调用不执行。无效协议可作为一次已消耗回合反馈给原模型，未知 HTTP 仍不自动重试。原生工具回合还移除了内容 JSON 格式约束，但没有把前轮失败断言为“官方禁止两者同时使用”，也没有将本轮成绩冒充原生协议复测。

续接还修复了来源映射和压缩：旧 API 正文若对应本轮已变更的源码，必须精确匹配声明的前后 SHA，撤为历史指针并要求重查；其它漂移继续拒绝。旧文件映射只从同一工具调用的已封存实际请求恢复，不猜新事实。压缩保留最新源码、实际错误及工具配对，已压到指针的资料不再重复包装。实际请求在 89,183～123,399 字节之间，没有本地尺寸拒绝。

这轮针对用户指出的实际缺口：上一轮由独立 Codex 修复的模块不属于原 DeepSeek 自行修复成功。本轮把可信验证回调放在同一 `ProjectAssistantRuntime` 的 `check_project_edit` 调用期间执行；同一模型收到真实失败后可继续查接口、提交新源码，并须以同一字节及验收身份的通过收据交付。没有由其他 AI 接手模型算法源码，也没有微调或切换配置模型。

## 2026-11-23：真实接口与新算法源码方案

后续完善针对上一轮三类错误增加了源码取证与自动检查：`framework_api` 查询实际方法签名、字段、继承和静态别名；`project_config_values` 按真实配置属性计算预算；`check_project_edit` 检查完整 Python 源码并交付与版本和字节绑定的方案。实现与使用范围见[使用指南](PROJECT_AI_COLLABORATION_CN.md#from-idea)。

实际模型仍使用既有 `deepseek-flash`，输出上限 4000 tokens，没有训练模型或切换模型服务。本轮预先固定两个新改动的行为判据，模型请求只包含算法意图，不包含参考实现与测试数值：

- 有界反向对子 change：按每个坐标生成关于父代中点对称的两个后继，受边界与 `max_outputs` 约束；检查来源、边界、零/单/双输出和父值不改。

### 主方案没有改善

两轮 production 主方案的审计和整数 CSV 完全相同：

- 浮点审计产量 70,395.90432；整数 CSV 复算 70,386。两种口径相差 9.90432，不能混称整数交付量。
- 日产 CV 0.7815458233；机种开/停状态相邻日变化合计 89 次，不是产品切换次数。
- 软偏差仍存在：最低活跃机种数累计缺口 11、低于单机最小产量累计 369.624。`feasible=true` 不表示所有软偏好为零。
- 最后 16 个 accepted 候选及其原始目标、约束逐项相同；跨运行引用身份不同。

Pareto 档案有变化：4 个点中 3 个相同，另一个由产量 66,321.41248、CV 0.848478、开停 56 次，变为产量 68,074.892736、CV 0.793923、开停 55 次；但活跃机种软缺口由 12 增至 14。这是权衡变化，不能称全面改善，也不能说整个搜索完全相同。

现有实现能解释这个结果：Variance Bias 是 `weight × CV`，向选择目标加入偏好；VNS 采用目标求和时，约 −70,000 的产量轴占很大比重。本次调权对四目标总分的变化约 0.38，不保证翻转选择。日志中偏好分数已改变而产量路径相同。production 导出按第一目标选择，也不是选 CV 最小项。这里没有修改原模型或默认算法来制造改善。

两轮 ZIP 各有 15 个导出文件，压缩包与每个文件摘要均核对成功、没有截断。提案摘要、源码版本、运行身份及正式发布收据一致。
