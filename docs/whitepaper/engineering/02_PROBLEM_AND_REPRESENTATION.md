# 第二章 把实际问题写成目标与候选管线

假设现在要决定两台设备的生产量。教学模型使用两个连续变量 x0、x1，范围都是 0 到 10；希望它们分别接近 3 和 4，同时总量不超过 8。目标可以写为 `(x0-3)^2 + (x1-4)^2`，约束写为 `x0+x1-8 <= 0`。这个例子暂时不处理整数工件、时段与库存，目的在于逐步解释不同组件应得到哪些信息。

首先写清候选含义。`[3,4]` 是两台设备的生产量，不是两项评价值，也不是两台设备的 ID。若实际业务要求整数，就必须把整数语义落实到编码、生成和修复中；仅在文档中称它为“工件数量”不会改变浮点算子的行为。若第三维以后表示设备类别，也不能继续未经解释地使用连续变异。候选表示决定了搜索操作的含义。

Problem 接收解释一致的候选并返回评价。下面是教学组件，应放在一个标准 Case 的 problem 模块；它没有新建私有运行循环：

```python
import numpy as np
from nsgablack.core.base import BlackBoxProblem

class AllocationProblem(BlackBoxProblem):
    def __init__(self):
        super().__init__(dimension=2,
                         bounds={"x0": (0, 10), "x1": (0, 10)})

    def evaluate(self, candidate):
        x = np.asarray(candidate, dtype=float)
        return np.array([(x[0] - 3) ** 2 + (x[1] - 4) ** 2])

    def evaluate_constraints(self, candidate):
        x = np.asarray(candidate, dtype=float)
        return np.array([x.sum() - 8])
```

这里的约束返回值保留符号：负值与零表示满足约束，正值表示违反。后续的违背量投影可以把满足项截为零，再汇总用于算法比较。目标和违背量需要分别解释，因为某个不可行候选可能目标很好。是否优先选择可行解、使用惩罚或其他接纳规则，要看实际装配的方法，不能默认所有 Adapter 使用完全相同的比较规则。

现在看候选 `[7,4]`。它在各变量边界内，因此 ClipRepair 不会改变它；但总量为 11，违反总量约束 3。这个计算说明：单变量 bounds 与组合约束是不同的限制。只给管线安装 ClipRepair，不等于已经处理所有业务约束。

如果业务允许按比例缩减产量，可以给问题管线提供专门 repair：先截到非负与上界，再在总量超过 8 时按比例缩放。它会把 `[7,4]` 变为大约 `[5.09,2.91]`，使总量为 8。若业务规定某台设备的最低量必须优先保证，这个比例修复就未必正确，需要另一种明确的可行化方法。

修复还可能改变搜索的统计性质。许多不同输入被投影到同一个边界区域，候选分布便不再等于原始变异分布。因此，repair 的选择应随建模一起讨论；它不能默默承担“挑选最佳设备”“偏向高收益工单”等完整搜索职责。否则，更换 Adapter 时会发现真正决定结果的规则藏在修复器里。

Problem 保留约束评价仍然有价值。一方面，评价可以检查 repair 之后是否真的可行；另一方面，有些约束无法通过便宜的局部修复保证。例如仿真后才知道温度是否超限，或运行外部模型后才知道延误风险。此时，应在评价中表达相应结果，而不是为了坚持“所有约束都在 repair”而把昂贵求值藏入候选流转。

初始化、变异、修复、编码和解码又各有不同职责。初始化给出搜索起点；变异根据已有候选产生新候选；修复处理可行性；编码决定算法看到的数据形式；解码把数据解释回领域对象。在最简单的连续向量问题里，编码和解码可以接近恒等映射。在排列、图、表达式或模型问题里，它们会成为重要组件。

例如把任务顺序编码为 `[2,0,1]`，含义是先执行任务 2，再执行任务 0，再执行任务 1。对这串数直接加高斯噪声，得到 `[2.2,-0.1,0.8]`，并不自动成为合法排列。问题管线必须选择能维持排列性质的操作，或提供明确定义的映射。这里应该更换的是表示与算子，不是把“排列必须不重复”写进所有搜索算法。

若一个候选是模型参数，数组还需要模型规格、参数布局或来源信息才能解释。同样的 `[1,2]`，可以是线性模型的截距与斜率，也可以是两个特征权重。框架允许语义状态与数值视图一起流动，第七章会解释这套协议。当前先记住：编码应当让算法能够操作，解码应当让 Problem 能够正确评价。

多目标问题需要固定评价维度。若同时比较成本和延期，单候选返回两个目标，批量目标为 N 行两列。不能因为某个候选没有延期就只返回成本，也不能把“缺失测量”静默解释为零。复杂指标首先要有稳定的定义，再决定如何参与 Pareto 比较或聚合。

即使两个目标都是数值，也不能随意合并。把成本与分钟数相加等于引入一个具体权衡，使用者需要知道单位、归一化及权重。Pareto 方法可以保留多个目标间的折中，但最终如何选择业务方案仍然需要规则。框架能承载这些选择，不能替代问题所有者决定何种结果值得采用。

实际配置中还要避免重复定义相互冲突的边界。Problem 的 bounds 写 0 到 10，Initializer 却在 -5 到 5 取样，Repair 再截到另一个范围，会让实际可搜索区域偏离预期。最好从同一组领域配置派生这些组件，并用几个手算候选检查编码、修复和评价是否一致。

一个低成本的检查顺序是：先用已知可行点检查目标，再用边界点和明确不可行点检查约束；接着观察 repair 前后的候选，确认变化符合业务含义；最后检查初始化和变异能否覆盖希望搜索的区域。这类检查比直接跑很多代以后只看一个最优值，更容易定位建模错误。

对于前面的教学例子，`[3,4]` 应有目标 0、约束返回 -1；`[7,4]` 应有目标 16、约束返回 3；把后者按比例修复后，总量约束应为零，但目标通常不会为零。这三个结果分别验证目标、约束和修复。它们是手工演算的检查值，并不依赖某个随机搜索是否恰好找到最优点。
