# Black Framework Stack 中文开发白皮书 V6：分卷体系与总目录（主目录）

## 一、为什么开发白皮书必须分卷

V5 已经解决了一个很难的问题：它为整套框架建立了比较严密的论证主线。从“可信运行”出发，依次定义形式本体、共享运行底座、优化语义、机器学习语义、跨框架组合、可靠性和扩展治理。沿着这条主线读下去，读者能够理解框架为什么这样设计，也能判断一个组件应当属于 blackbase、nsgablack、mlblack，还是外部 Provider/Bridge。

但 V5 仍然把三种性质完全不同的技术表达放进了同一个全局章号：

1. 架构论证：解释为什么存在这些边界，以及边界被破坏后会发生什么。
2. 工程剖面：展示架构怎样落实到目录、配置、公共协议、运行路径和故障处理。
3. 技术查询：在结论已经明确时，快速定位字段、命令、Schema、源码锚点和排障路径。

三种内容不能靠同一种行文同时完成。架构论证如果不断插入完整配置，会失去推导连续性；工程剖面如果只给最终代码，又无法说明为什么采用这种装配；参考手册如果写成长篇叙事，则难以检索。此前目录中的“构建方法”更接近高层方法摘要，还不足以记录从需求、设计决策到可验证运行的完整工程路径。

因此，V6 的基本决定是：

> 整套内容改为一组相互引用的开发白皮书分卷，而不是一份不断增长的巨型说明书。每一卷回答一个稳定的工程问题，明确其入口假设、架构结论、实现剖面、证据边界和对其他分卷的依赖。

这不是把内容简单按仓库切成三份说明。仓库只是工程归属，分卷仍然按论证依赖组织。第一卷建立共同语言；第二至第六卷分别闭合运行、优化、学习、组合和可靠性；第七至第十一卷提供工程实施与故障验证剖面；第十二卷面向框架扩展与治理；配置、API 和故障词典独立成为参考手册。

新体系仍然保留 V5 的论证成果，也保留已经写成的章节。变化的是出版和引用结构：原来的“第 55 章”在新体系中成为“第五卷第 1 章”。跨框架协议可以直接引用其所属分卷，不必继续依赖一个越来越大的全局章号。

## 二、开发白皮书由三组分卷构成

### 2.1 第一组：架构与语义卷，回答“为什么成立”

架构与语义部分共有六卷：

- 第一卷《可信复杂计算与统一框架原理》
- 第二卷《blackbase：共享运行底座》
- 第三卷《nsgablack：优化工程》
- 第四卷《mlblack：机器学习工程》
- 第五卷《完整 Case 的组合与跨框架系统》
- 第六卷《可靠运行、恢复与证据》

这六卷承担原理、概念、状态机、协议和架构推导。它们不追求把每个配置字段都写进正文，而是要形成可引用的开发结论：为什么存在某项能力，什么时候不该使用，谁拥有状态，谁拥有资源，哪里是提交点，失败由谁处理。

### 2.2 第二组：工程实施与验证卷，回答“怎样落地并证明”

工程部分共有五卷：

- 第七卷《标准 Project 的建立与审计》
- 第八卷《优化项目工程实施》
- 第九卷《机器学习项目工程实施》
- 第十卷《跨框架系统工程实施》
- 第十一卷《生产运行与故障验证》

这些分卷不是入门教程，而是开发白皮书中的参考实施。每项能力都从真实工程困难开始，展示直接实现为什么会失控，再给出目录、配置、公共面、运行路径、证据读取和故障注入，说明架构结论怎样变成可复核的实现。

所谓“逐步配置”在这里不是教学打卡，而是要求工程论证不能跳过中间状态。每个实施剖面必须包含：

- 这一节开始时项目目录是什么状态；
- 新增或修改哪个文件；
- 为什么代码属于这个目录而不是另一个目录；
- 完整的最小配置是什么；
- 运行什么命令；
- 正常输出中应该看到哪些字段；
- 如何证明配置确实进入了生效运行，而不是只存在于文件里；
- 故意写错以后框架在哪里拒绝；
- 换一种业务问题或运行后端时，哪些协议保持不变，哪些语义实现必须替换。

### 2.3 第三组：开发治理卷与参考手册，回答“怎样演进和查询”

第十二卷《框架扩展与架构治理》面向修改框架公共面的开发者。它讨论组件归属、共享协议、兼容迁移、Doctor、Catalog、测试与发布证据。

此外另设一组非叙事性的参考手册：

- 《配置字段全书》
- 《CLI 与运行模式速查》
- 《公共 API 与协议 Schema》
- 《组件与源码锚点索引》
- 《故障症状与诊断路径》
- 《版本迁移与兼容说明》
- 《验证资产、基准输入与验收矩阵》

参考手册不承担架构概念的首次论证。白皮书正文负责说明结论怎样产生；参考手册只负责准确、完整、便于检索。

## 三、开发白皮书的共同写作规则

### 3.1 概念必须在问题之后出现

正文不能这样写：“框架有 Adapter，Adapter 提供 propose/update。”这种写法要求读者先接受一个陌生名词，再自己猜它解决什么问题。

正确顺序应当是：Solver 如果同时承担生命周期、候选生成、选择策略和状态恢复，任何算法变化都会改动控制平面；我们需要把“运行怎样继续”和“下一批候选怎样产生”分开；在完成这个推导后，才给后一种角色命名为 Adapter。

同理，Context、Snapshot、Artifact、Case、ResourceContext、Controller 和 Provider 都必须由问题自然引出。第一次出现时解释它为什么存在；第二次出现时展示它怎样工作；工程实施卷再给出配置和运行剖面。不能在一段开头突然列出一串框架专有名词。

### 3.2 同一知识出现多次，但每次承担不同任务

“避免重复”不能理解成一个概念在整套白皮书中只能说一次。同一结论会在不同技术文档中承担不同责任：

- 原理卷解释它为何存在；
- 语义卷解释它在本领域承担什么责任；
- 工程实施卷展示它怎样装配并产生运行证据；
- 参考手册列出完整参数和 API。

四次内容不能互相复制。它们分别回答“为什么”“属于谁”“怎么做”和“怎么查”。

### 3.3 工程实施章节遵循因果链，而不是堆砌代码

工程实施章节内部使用一条稳定的论证链：

~~~text
真实任务
→ 直接做法
→ 暴露的困难
→ 需要保持的边界
→ 框架选择
→ 目录与配置
→ 第一次运行
→ 读取证据
→ 故障注入
→ 扩展与收益
~~~

这条链是写作纪律，不要求每章都使用十个同名小标题。正文仍应像完整文章一样承上启下。简单章节可以自然地把几个环节合并；复杂章节可以用一个阶段性问题带出下一部分。

### 3.4 不用一个案例贯彻全部分卷

一个案例无法同时自然地证明所有边界。为了“统一故事”而强迫同一个业务案例承担数据泄漏、Pareto、嵌套资源、外部 Worker、序列化和故障恢复，最终只会让案例变形。

V6 使用“案例梯度”：

- 极小数值问题负责暴露最基本的运行链；
- 工程设计或调度问题负责展示约束与多目标；
- 表格和时间序列任务负责展示数据、训练与 Artifact；
- 超参数搜索负责展示外层优化、内层训练；
- 决策聚焦学习负责展示外层训练、内层求解；
- 交替系统负责展示轮次提交和收敛；
- 符号正交案例负责综合验证组合闭包；
- 外部仿真和 Worker 案例负责验证系统边界；
- 故障实验负责验证异常路径。

每个案例都有明确的证明任务，不承担整套框架的全部概念。

### 3.5 所有操作性内容必须绑定版本和证据

理论命题可以在代码重构期间继续打磨，但命令、配置字段和期望输出只能基于稳定公开面编写。每一个可运行章节都必须说明其证据等级：

- 设计要求：架构上应该成立，尚无稳定实现；
- 源码事实：通过静态阅读确认路径存在；
- 合同验证：聚焦测试已经执行并通过；
- 标准运行：正式 Case 按标准脚手架实际运行；
- 生产证据：真实外部后端或长期运行记录已经验证。

源码中“看起来支持”不能写成“已经验证”。工程实施卷发布时，参考实现、命令、输出和测试证据必须绑定同一个版本。

# 第一组　架构与语义卷

## 第一卷　《可信复杂计算与统一框架原理》

### 本卷定位

这是整套开发白皮书的共同基础。它不从 blackbase、nsgablack 或 mlblack 的名字开始，而从一个更一般的问题开始：为什么“某次得到了正确答案”并不足以证明一个复杂计算系统可信。

本卷要形成一组能够被后续设计直接引用的基础结论：怎样用闭包、不变量、权威状态、身份、版本和生命周期分析复杂计算任务；怎样判断一项计算究竟负责形成未知状态、提供领域事实，还是治理另一个运行；以及为什么“被框架调用”不等于“必须属于优化或学习”。

### 章节目录

#### 第 1 章　从“得到答案”到“运行一个可信的计算过程”

从一次成功运行的不充分性出发，引出可复现、可解释、可恢复、可组合和可治理的要求。解释框架的目标不是包住算法，而是管理一条能够被证明的因果链。

#### 第 2 章　六类复杂性怎样相互放大

区分问题复杂性、算法复杂性、状态复杂性、资源复杂性、组合复杂性和组织复杂性。说明很多工程事故不是某一种复杂性过高，而是几种复杂性在未声明边界处相乘。

#### 第 3 章　五种闭包：怎样判断一个框架是否真正完成

建立语义闭包、运行闭包、状态闭包、组合闭包和证据闭包。运行闭包并不要求框架重新实现语言运行时、操作系统、容器、驱动或 Backend 已有的物理回收；它要求当前边界关闭或正式转交自己拥有的未决责任。证据闭包则被限定为相对于 claim、provenance policy 与 trust boundary 的有限证明闭合：必要关系有见证、边界外假设显式、上游可按引用继续展开，而不要求追到世界因果链的绝对起点。以后每一卷都回到这五个问题，而不是靠“功能很多”证明框架成熟。

#### 第 4 章　十条架构不变量

把全书最重要的保持条件提前给出：唯一权威状态、资源授权单调收窄、预算不能复制、运行入口唯一、生命周期恰好一次、跨边界只传公开合同，以及结果必须声明证明范围并携带与声明强度相称的有界因果证据。特别强调清理服从 ownership：关闭自有资源、归还共享权利、委托底层回收、保留正式产物，不能对所有可见对象统一 `close()`。

#### 第 5 章　谁拥有正在形成的答案：从通用反馈系统到计算角色

前四章的结论同样适用于数据库事务、增量编译、Web 背压和设备控制，所以这里不能立刻宣布“接下来只讨论 OR 与 ML”。本章先提出真正的分界问题：在一条反馈链中，谁拥有尚未确定的状态，谁提出下一次变化，谁只提供观测或领域事实，谁负责批准资源和终止运行。

同一个系统可以同时出现三类责任。第一类负责形成答案，它持有未知状态并根据反馈更新；第二类负责产生事实，它接受稳定请求，执行仿真、数值计算、查询、实验或远程推理，再返回证据；第三类负责治理运行，它安排顺序、发放资源、传播取消并记录结果。三者都会迭代、失败和消耗资源，但不能因为“都有循环”就被归为同一种语义。

本章的出口不是框架类名，而是一条判断准则：**先确定当前边界内谁拥有待求状态，再决定它属于领域闭环、外部求值，还是共享运行治理。**

#### 第 6 章　求值不是学习，调用也不是编排：外部计算处在什么位置

本章专门处理物理仿真器、有限元程序、数学规划器、数据库、对象存储、实验设备、远程模型和第三方服务。它们可能在内部极其复杂，甚至拥有自己的迭代和 checkpoint；但相对于调用它们的父任务，它们首先表现为“请求到领域事实”的边界，而不是自动成为父框架的优化或学习状态。

这里建立相对角色而非产品分类。同一个数值求解器，如果最终解就是项目交付物，可以成为独立 Solver Case；如果它只为一个候选计算可行性或物理响应，则是评估 Provider；如果它具有独立生命周期、资源和恢复要求，又可作为完整子 Case 被调用。数据库通常是存储 Backend 或查询 Provider，却不会因为被 Trainer 调用就变成 ML 组件。

在完成这些推导后，才引入 Provider、Backend、Bridge 和外部 Case 四种工程落位，并比较原子能力、独立运行单元与跨协议适配的边界。

#### 第 7 章　为什么优化与学习成为两种一等闭环

现在才从一般计算角色收束到本框架重点拥有的两类“答案形成语义”。优化拥有待选择的决策或候选及其搜索更新；学习拥有待形成的模型状态及其数据反馈。二者都能把仿真器、数据库、远程模型和外部求解器作为事实来源，但外部能力不因此获得父层状态所有权。

本章从“未知状态—形成可评价对象—取得反馈—更新权威状态”推导二者的统一运行骨架，再分别说明行动、模型、目标、约束、数据和最终产物的差异。运筹优化只是优化语义中的重要问题族，而不是整套框架唯一允许的计算对象。

#### 第 8 章　统一而不混同：共享控制为什么不等于共享领域语义

解释优化搜索与机器学习共享资源、预算、状态载体、生命周期和组合协议，却不能共享全部领域对象。外部求值能力共享的则是调用与治理合同，而不是被强行改造成第三种 Adapter。由此给出“共享运行、分离答案语义、显式外部边界”的完整结论。

#### 第 9 章　三仓一边界：统一框架怎样落到工程

在计算角色、一等闭环和外部求值边界均已说明以后，才正式引入 blackbase、nsgablack、mlblack 和外部 Provider/Bridge。逐层解释为什么共享底座、优化语义、ML 语义和外部领域后端需要分别归属。

#### 第 10 章　工作尺度：Project、Stage、Case、Scaffold 与 Pipeline

解决“这段逻辑到底是组件、流水线、独立运行单元还是项目阶段”的尺度问题，为目录落位和组合方式建立判断依据。

#### 第 11 章　角色本体：Problem、Representation、Adapter、Controller、Plugin 与 Backend

从职责冲突中逐一引出运行中的角色，重点讨论它们不应该做什么。让读者以后看到一段逻辑时能够判断其语义归属。

#### 第 12 章　合同本体：类型、能力、上下文、资源与 I/O

解释对象之间为什么不能只靠 Python 可调用性连接。建立数据合同、能力合同、上下文合同、资源合同和输入输出合同。

#### 第 13 章　状态与反馈：UnknownState、Candidate、Feedback 和 Result

说明搜索状态、模型状态、候选、评估反馈和最终结果不是同一种对象，避免把临时值误当成可恢复事实。

#### 第 14 章　身份、时间与版本：同一个数值为什么不是同一个状态

讨论 metadata、fingerprint、generation、step、attempt、run identity、schema version 和 lineage cut。解释数值相同不代表语义相同，也解释继续溯源为何只增加有类型图的节点与深度，不应持续增加 Result 的协议维度。

#### 第 15 章　五类信息载体：Context、Snapshot、Artifact、Event 与 Manifest

从信息寿命、大小、权威性和读写方向推导五种载体的分工，说明为什么不能把所有东西都塞进 Context 或日志；进一步定义 Manifest 怎样登记 provenance policy、直接见证、上游引用、trust roots、外部假设与保留策略，形成一次有限证明切面。

#### 第 16 章　控制对象：资源、预算、截止时间、取消与错误

说明五种控制信息怎样限制运行，以及它们为什么不能退化成几个松散整数或布尔值；区分物理回收、及时关闭、逻辑归还、权限失效和外部收尾，建立 created、borrowed、shared、leased、external 与 committed evidence 的 ownership 规则；同时说明 commit fence 关闭写入资格，provenance boundary 关闭本次结果能够声称什么。

#### 第 17 章　生命周期代数：一次运行允许发生哪些事件

把初始化、提议、评估、更新、提交、结束和错误处理组织成事件顺序。setup 必须区分创建、借入与共享，teardown 必须按 ownership 关闭、归还、委托或报告残余风险；提交不仅选择权威状态，还要把公开 claim 与有限见证、上游引用、trust roots 和 unresolved assumptions 一起封口。生命周期代数协调底层原语，不重新实现垃圾回收、进程回收、驱动资源管理或数据库事务。

### 本卷验证性分析

选择一个现有计算系统，不改代码，只画出它的状态、资源、预算、生命周期和产物因果图；为图中的一个最终 claim 标出直接见证、可继续展开的上游引用、trust roots、外部假设和保留边界；再指出至少三个无法回答的恢复或组合问题，并使用本卷的不变量解释其架构根因。这份分析将作为后续运行底座设计的输入，而不是教学作业。

将慢评估从 Problem 内部裸调用迁移为正式边界，加入 timeout、错误分类、缓存 key 和资源需求。

#### 第 9 章　批量与并行评估

配置批量路径、线程安全声明和共享池。用会原地修改数组的错误评估器制造竞态，再修复输入隔离。

#### 第 10 章　多阶段策略与 Controller

建立探索、开发和精修阶段。阶段切换读取评估后的新 Context，而不是上一代旧视图。

#### 第 11 章　缓存、warm start 与公平比较

区分完全相同评估的缓存命中和有 lineage 的 warm start。改变 problem fingerprint 后验证旧缓存失效。

#### 第 12 章　checkpoint、resume 与长运行

在 update 前后不同位置注入崩溃，观察权威 snapshot 和恢复差异。

#### 第 13 章　优化结果怎样交付给下游

定义 best、Pareto、代表性解、约束证书、运行报告和大型 Artifact 的输出合同。

#### 第 14 章　综合项目：多目标工程设计或调度

从建模、脚手架、配置、资源、预算、并行、恢复到最终 Result 完整交付。综合项目不额外引入新概念，只验证前十三章是否闭合。

## 第九卷　《机器学习项目工程实施》

### 本卷定位

本卷回答“为什么工程系统不能停留在 estimator.fit()”。它从一个可以直接训练的任务开始，逐步加入数据版本、状态表示、反馈、资源、Artifact 和复合训练，以实现差异说明框架边界怎样随着工程复杂性出现。

### 章节目录

#### 第 1 章　固定数据事实：DataView、schema 与 split

逐步建立数据输入、训练/验证边界和时间截止点，并通过故障样例验证目标泄漏能够在正式边界被发现。

#### 第 2 章　建立第一个 LearningProblem

区分训练 loss、框架 objective、constraint 和报告 metric。用可人工计算的小批次验证 Feedback。

#### 第 3 章　表示模型状态：UnknownState、Codec 与 metadata

展示相同数值、不同 metadata 如何解码为不同模型，并建立稳定 fingerprint。

#### 第 4 章　选择 Head，让输出具有语义

从点预测扩展到概率、区间和结构输出，验证输出 shape 与评价合同。

#### 第 5 章　组装并运行第一个 Trainer Case

建立 canonical builder、Adapter、Plugin、backend 和 Result。读取有效 ResourceContext 与实际 backend，而不是只看配置。

#### 第 6 章　实现一个自定义训练 Adapter

覆盖梯度更新、黑盒更新或混合策略，处理权威模型状态、feedback 对齐和 checkpoint state。

#### 第 7 章　接入 sklearn、神经网络或外部模型 Provider

解释外部库对象怎样进入 Provider/backend surface，而不是污染核心协议。验证安全序列化和 Artifact 发布。

#### 第 8 章　并行候选评估为什么默认应谨慎

为 Problem、Representation 和 Plugin 声明线程安全，比较串行与并行结果。展示共享 estimator 或 session 的危险。

#### 第 9 章　CaseStageRunner 与多阶段训练

建立预训练、校准和评估三个阶段，传递 Artifact，定义最终输出 stage，并验证任一阶段失败时按照 ownership contract 执行 teardown，不关闭父级共享资源或删除已提交产物。

#### 第 10 章　完成条件、早停与预算

区分 step count、wall time、metric patience 和共享计算预算。确保结束条件通过协作式循环实际执行。

#### 第 11 章　保存并恢复完整模型状态

恢复 values、metadata、population、feedback、best state、Adapter state 和 backend 相关信息。

#### 第 12 章　模型 Artifact 与推理交付

发布模型、预处理器、schema、Head、指标和环境指纹；从 Artifact 重新构造推理链。

#### 第 13 章　模型族迁移

把同一运行协议分别应用于表格、时间序列、概率和符号模型，指出改变的是语义组件，不是私建新 Trainer。

#### 第 14 章　综合项目：可恢复的时间序列或表格学习系统

从 DataView 到模型 Artifact 完整交付，并包含数据版本变化、训练中断和恢复后的结果比较。

## 第十卷　《跨框架系统工程实施》

### 本卷定位

本卷以已经闭合的 Solver 和 Trainer 为前提，不再重复单体生命周期，而是逐步构建父子 Case、双向 Bridge、交替系统和多 Lane 项目，并记录每个跨边界决策的证据。

### 章节目录

#### 第 1 章　先选择组合关系，再写调用代码

比较上游数据生产、组件级 Provider、完整子 Case、Project 阶段、外层优化、外层学习和交替系统的适用条件。

#### 第 2 章　第一次父 Case 调用子 Case

构造 CaseRunRequest，派生 child grant、budget、identity 和 control，读取 CaseRunResult，并处理 named Artifact refs。

#### 第 3 章　外层优化、内层训练：最小超参数搜索

把 candidate 解码为 TrialSpec，创建独立 Trainer Case，把 TrainerResult 投影为 objective 与 violation。

#### 第 4 章　让试验比较真正公平

固定数据 split、seed、fidelity 和资源；配置缓存与 warm start；验证改变任一语义字段都会改变 trial fingerprint。

#### 第 5 章　外层学习、内层求解：最小决策反馈

把模型输出变成 SolveSpec，调用 Solver Case，用真实结果计算 regret，并将求解近似质量纳入 Feedback。

#### 第 6 章　结构化解码、标签生成和决策学习的三种落位

同一求解能力分别作为 Provider、上游 Case 和训练内子 Case 使用，比较生命周期、预算和 Artifact 差异。

#### 第 7 章　建立交替训练—优化循环

定义 iteration identity、输入状态对、两次子运行、提交 barrier、收敛残差和恢复点。故意在半轮崩溃，验证不会提交不完整状态。

#### 第 8 章　双层问题与近似内层

配置内层 fidelity、误差报告和外层接受策略。比较内层超时、不可行和近似成功在外层的不同语义。

#### 第 9 章　多 Solver、多 Trainer 和多 Lane

分别建立独立 benchmark、ensemble 和 cooperative lane，明确哪些信息只读共享、哪些状态禁止共享、结果怎样聚合。

#### 第 10 章　父子资源、预算、取消和 deadline

让子 Case 故意请求超过父授权，观察拒绝；取消父 Case，确认运行中的子任务在 checkpoint 观察同一 lineage。

#### 第 11 章　跨 Case Artifact、缓存与 lineage

传递模型、Pareto front、数据集和求解结果，不传裸对象。构造一次错误缓存命中并用完整 fingerprint 修复。

#### 第 12 章　外部数值求解器或仿真器

通过 Provider/Bridge 接入外部 backend，定义错误、成本、序列化和取消边界。

#### 第 13 章　符号正交嵌套综合项目

将 basis search、inner fitting、orthogonality/stability Feedback、conditioned expression 和图缓存组合起来，逐项核对闭包。

#### 第 14 章　跨框架项目验收

交付 Project 配置、两个以上独立 Case、父子 lineage、资源与预算记录、失败信封、Artifact 图、恢复记录和最终 Manifest。

## 第十一卷　《生产运行与故障验证》

### 本卷定位

本卷不把 Dashboard 或 Catalog 当成主角。它关注运行架构是否真的能够在长时间、并发、外部依赖和部分失败下守住边界。所有章节都采用可控故障注入和状态核对。

### 章节目录

#### 第 1 章　从内存运行迁移到持久状态后端

配置 Context、Snapshot 和 Artifact 后端，比较生命周期与数据大小，确认安全 serializer 不会静默丢失结构。

#### 第 2 章　Redis 环境下的隔离、TTL 与恢复

建立 namespace、run token、过期策略和并行运行隔离。停止 Redis、重启服务并验证恢复与错误报告。

#### 第 3 章　从单进程到共享 Pool

配置有效线程 grant，观察排队、额度、取消、递归同池保护和关闭。

#### 第 4 章　外部 Worker 与任务传输

运行 transport-safe request/result，处理重复投递、worker 失败、失联和晚到结果。

#### 第 5 章　批量评估部分失败

让第三个候选失败，检查已开始成本、成功数量和未使用 reservation 怎样结算，证明硬预算没有被退还穿透。

#### 第 6 章　并发状态污染

让两个分支共享 ndarray、Context 或 backend session，复现不确定结果，再通过复制、只读投影和独立 namespace 修复。

#### 第 7 章　timeout 后仍在运行的线程

区分 cancelled 与 still_running，使用协作式 checkpoint 和 fencing 拒绝晚到 Snapshot/Artifact 写入。

#### 第 8 章　错误恰好一次

分别从单点评估、批量评估、公开 evaluate、run loop 和子 Case 注入异常，验证 on_error、retry 和 teardown 的唯一 owner。

#### 第 9 章　checkpoint 崩溃窗口

在 Adapter update、Snapshot write、Context ref、Event 和 Manifest 之间逐点崩溃，确定恢复读取哪个提交版本。

#### 第 10 章　随机性与不可复现结果

改变 seed 派生、并发顺序、设备 backend 和数据版本，学会区分合法统计波动与运行协议漂移。

#### 第 11 章　从 Event 到运行证据

配置日志、metric、trace、report 和 manifest，确保每种载体只承担自己的责任。Dashboard 作为最后的读取层接入。

#### 第 12 章　性能分析：先找到成本中心

测量评估、序列化、存储、排队、模型训练和外部调用的成本，再选择批量、缓存、并行、异步或远程执行。

#### 第 13 章　Doctor、Catalog 与发布前检查

使用 Doctor 检查脚手架和协议，用 Catalog 验证可发现性；明确二者不能代替运行测试。

#### 第 14 章　事故演练与复盘

给出一份包含资源越权、缓存串用、部分失败和晚到写的综合事故。读者从症状出发，沿闭包和证据链定位根因，形成复盘记录。

## 五、各分卷在开发流程中的使用位置

### 架构设计与重构评审

- 第一卷提供共同判断语言；
- 第二至第六卷分别提供运行、优化、学习、组合和可靠性不变量；
- 评审结论应引用具体分卷命题，而不是只写“遵循框架设计”。

### 公共面实现

- 第七卷给出标准 Project/Case 基线；
- 第八至第十卷提供三类语义实施剖面；
- 第十二卷规定共享协议、组件扩展、兼容迁移和治理同步。

### 集成与故障验证

- 第六卷定义异常路径需要保持的性质；
- 第十一卷给出可执行的故障注入和状态核对；
- 参考手册 G 固定输入、环境条件和验收矩阵。

### 发布与长期维护

- Manifest、Result、测试记录和正式运行构成发布证据；
- Doctor、Catalog、示例和 Dashboard 分别承担规则检查、发现、公开面证明和事实呈现；
- 配置、API、源码索引和迁移说明进入独立参考手册，避免污染架构正文。

这种组织方式把“架构结论”“参考实现”“验证证据”和“查询材料”分成四种可维护产物，符合开发白皮书的用途，而不是把内容包装成课程进度。

## 七、工程实施卷的最低交付标准

工程实施卷每一章都必须满足以下要求。缺少其中任何一项，就只能算局部示例，不能作为开发白皮书中的参考实施。

### 7.1 有明确的入口状态

章节开头必须说明依赖哪些架构结论、当前目录有哪些文件、需要什么数据和资源。不能假定一个不可见的历史工作区。

### 7.2 有完整的最小路径

关键文件不能只贴差异片段。第一次出现时给出能够运行的完整最小版本；后续章节可以只展示增量，但必须能追溯到基线。

### 7.3 有命令和预期证据

不仅写“运行项目”，还要给出工作目录、命令、预期状态、关键输出字段和生成的 Artifact/Snapshot。界面截图只能辅助，不能替代可检查的结果。

### 7.4 有一次故意失败

每项重要能力至少配一个反例：shape 错误、资源越权、旧 snapshot、错误 metadata、预算越界、取消未传播或 Artifact schema 不兼容。验证记录必须表明框架确实保护了边界，而不只是正常路径可以运行。

### 7.5 有“为什么更好”的具体比较

优势不能写成“更灵活、更可扩展”。必须比较可观察事实，例如：

- 直接调用时无法知道资源是否越权，正式 grant 可以审计；
- 裸对象传递无法安全跨进程，DataRef 可以保持 lineage；
- 成功后统一计数会在部分失败时退还成本，reservation ledger 不会；
- 共用 Solver 实例会污染状态，子 Case identity 和 namespace 提供隔离；
- 控制台 loss 无法复现模型，TrainerResult 与 Artifact 可以交付。

### 7.6 明确适用范围与变体

每章结尾说明更换目标、数据、Adapter 或 backend 后哪些结论仍成立。变体必须复用本章已经建立的协议，不能依赖正文中从未说明的私有捷径。

## 八、接下来的写作顺序

在运行架构仍重构期间，不应立即填充大量命令和配置。推荐顺序如下：

1. 先确认各分卷的职责和引用边界；
2. 继续完善第一至第六卷中不依赖短期 API 的论证；
3. 等 canonical builder、Case invocation、ResourceContext、Budget、Result、Snapshot 和恢复接口稳定；
4. 优先编写第七卷，因为标准 Project 的完整剖面最容易暴露公开面的不一致；
5. 并行规划第八卷和第九卷，但分别由优化语义与 ML 语义驱动；
6. 在双向 Bridge 和循环协议稳定后编写第十卷；
7. 用第十一卷的故障实验反向验证工程实施没有只覆盖成功路径；
8. 最后编写第十二卷与参考手册，固定扩展和查询面。

正文生产不再按全局章号顺序进行，而按“概念稳定度 × 工程价值 × 证据成熟度”排序。某一实施章节如果依赖尚未稳定的协议，可以先完成问题叙事、目录树和验收条件，把具体 API 留为待验证部分，不能用猜测填空。

## 九、这次目录重构最终解决什么问题

V5 已经是一套架构论证；V6 在此基础上把它重组为一套可设计、可实现、可验证、可引用的开发白皮书体系。

第一至第六卷形成架构结论：

> 为什么框架这样设计，以及哪些边界不能被破坏。

第七至第十一卷提供工程实施与验证剖面：

> 从一个现实问题出发，完成建模、目录、配置、运行、观察、故障验证、恢复和交付。

第十二卷和参考手册闭合框架演进：

> 在不制造第二套协议的前提下扩展系统，并把实现、测试、示例、Doctor、Catalog、迁移和文档一起闭合。

这三组分卷合在一起，白皮书才不只是“描述一个很精妙的架构”，而是把设计依据、实现路径、运行证据和演进规则固定为可以长期维护的工程资产。最终文档不仅要定义 Solver、Adapter、Case 或 ResourceContext，还要准确说明它们为何存在、在什么边界使用、怎样装配、怎样证明生效，以及绕过它们会破坏哪一条不变量。
