# 第一卷·第六章　求值不是学习，调用也不是编排：外部计算处在什么位置

第五章把复杂计算中的三类责任分开了：有些运行拥有正在形成的答案，有些能力为答案提供领域事实，还有一套共享控制关系决定所有运行是否仍有资格继续。这个区分解释了为什么物理仿真器不必被改造成 Trainer，数据库也不因为参与训练就成为 ML 语义组件。

但“外部事实边界”仍然过于宽泛。一个对数组做单位换算的纯函数、一次本地有限元求解、一个远程天气服务、一个需要数小时并支持 checkpoint 的仿真任务，以及一个独立运行的商业数学规划器，都可以被父任务用于产生事实。若把它们统一包装成同一种回调，轻量能力会被过度工程化，重型任务又会丢失生命周期；若完全交给业务代码自行调用，资源、预算、取消、错误和 Artifact 则会重新变成隐式状态。

所以本章要解决的不是“外部系统能不能调用”，而是：

> **[I] 在不吞并外部系统语义的前提下，怎样根据执行粒度、独立状态和协议距离，把一项外部计算放到正确的运行边界？**

本章先从父任务真正需要的合同开始，再逐步引出确定性组件、Provider、Backend、Bridge 和完整子 Case。术语出现在判断之后，而不是先给每个外部产品贴标签。

---

## 6.1 父任务需要拥有边界事实，不需要拥有外部系统内部

设一个结构优化任务把候选几何发送给有限元引擎。有限元程序内部可能完成网格装配、非线性迭代、预条件求解、误差估计和文件输出。父 Solver 没有必要理解每一个内部对象；但它必须知道返回的最大应力究竟对应哪个候选、哪套材料参数、哪一版网格规则和哪一次 attempt。

父任务因此需要拥有的不是外部实现，而是六类边界事实：

1. **请求事实**：输入的领域含义、schema、版本、单位和引用；
2. **身份事实**：本次调用属于哪个 run、candidate、sample、iteration 与 attempt；
3. **执行事实**：是否开始、使用什么资源、是否命中缓存、是否仍在运行；
4. **响应事实**：返回值、近似误差、可行性、完整性和大型 Artifact；
5. **终止事实**：成功、不可行、未收敛、超时、取消或系统失败；
6. **成本事实**：已经真实发生的调用、核时、设备时间、外部计费与不可退款副作用。

外部系统保留自己的算法与领域语义。有限元引擎决定残差怎样计算，数据库决定事务怎样提交，云服务决定请求怎样执行。父框架则拥有“这次结果是否可以进入当前任务”的资格判断：请求是否仍有效，deadline 是否已过，旧 lease 是否失权，结果 schema 是否匹配，以及这次调用怎样计入预算。

这是一种双重尊重。框架不假装理解外部系统内部；外部系统也不能绕过父框架的运行控制，直接把结果写成当前权威状态。

## 6.2 第一种落位：Case 内部的确定性组件

最轻的一类能力没有独立运行事实。它在父 Case 生命周期中原子完成，失败可以立即归因，既不需要独立资源授权，也不产生可恢复的中间状态。例如：

- 对候选做单位换算；
- 将整数编码解码为排列；
- 对输入字段做确定性规范化；
- 根据静态规则计算派生特征；
- 把 Provider 响应投影成 objective 或 metric。

这些能力适合保留为 Pipeline 中的组件或普通领域函数。为它们创建完整 Case 会引入无意义的 run identity、Manifest 和 Artifact；把每一步都远程化，也会让运行边界比业务语义更重。

但“代码很短”不是唯一标准。一个本地函数如果执行付费 API、写数据库、持有 GPU session 或可能在父超时后继续运行，它就不再是纯确定性组件。相反，一个数值计算即使包含几百行，只要输入输出稳定、在父调用内同步完成、没有独立恢复需求，也可能仍然属于组件级能力。

判断关键是原子性：父 Case 是否可以把这次调用视为一个不可再分的生命周期步骤，并在返回或抛错时立即知道全部后果。如果不能，就需要更强的边界。

---

## 6.3 第二种落位：Provider 与 Backend 承载受控能力

当一项能力仍然服务于父 Case，却已经涉及外部资源、可替换实现、独立错误语义或昂贵副作用时，需要一个正式能力边界。

**Provider** 回答“谁能完成这项领域请求”。它暴露稳定输入输出和能力声明，隐藏具体库、服务或模型的内部接口。例如，同一仿真请求可以由本地库、远程服务或测试替身完成；同一预测请求可以由 sklearn、深度学习 backend 或云模型完成。父 Problem 消费的是能力合同，不是某个 SDK 的私有对象。

**Backend** 更接近执行条件，回答“这项能力在哪里、以什么 session、存储或设备执行”。数据库连接、对象存储、GPU session、线程池、远程队列和数值库运行环境都可能位于 backend surface。Provider 可以依赖 Backend，但不能借此私自扩大 ResourceContext。

二者都不拥有父任务的答案更新。Provider 返回仿真值，不选择种群；Backend 提供 GPU，不决定模型是否最佳；数据库保存 Snapshot，不解释候选是否可行。

一个合格的 Provider/Backend 边界至少需要声明：

- 能处理的请求类型与 capability；
- 线程安全、进程安全和 session 复用条件；
- 资源要求与有效 grant 的消费方式；
- timeout 和 cooperative cancellation 能力；
- 错误分类与 retryability；
- 结果 schema、近似质量和 transport-safe 条件；
- 大型输出怎样发布为 Artifact/DataRef；
- 健康检查和关闭语义。

如果这些信息仍藏在业务函数的异常和全局变量里，Provider 只换了名字，没有形成边界。

## 6.4 第三种落位：Bridge 负责跨语义翻译

Provider 解决“同一种请求由谁执行”，Bridge 解决“两个系统的公开合同并不相同，怎样保持双方语义进行翻译”。

例如，外层优化提出的是编码候选，内层 Trainer 需要的是 TrialSpec、DataRef、fidelity 与 seed policy；Trainer 返回 TrainerResult，外层 Adapter 只消费 objectives 与 violations。Bridge 负责候选解释、子资源派生、请求构造、结果校验和反馈投影，却不能直接读取 Trainer 私有 history 猜测最佳模型。

再如，模型输出成本向量，商业求解器需要矩阵、变量域、约束、容差和 solution policy；求解器返回状态码、primal solution、gap 与证书，LearningProblem 需要决策后悔、不可行率和近似质量。Bridge 把 SolveSpec 映射到外部协议，再把原生 Result 投影为学习 Feedback。

Bridge 的核心不是“多写一层包装”，而是保留两侧不同的真相：

~~~text
父侧语义声明
→ 显式映射
→ 子侧公开请求
→ 子侧原生结果
→ 显式投影
→ 父侧 Feedback 或 Result
~~~

它必须拒绝模糊映射。shape 不一致、字段缺失、schema version 不支持、结果属于旧 attempt 或近似质量不满足要求，都不能以默认值静默穿过。若 Bridge 开始创建私有 Project、分配全局资源、修改子组件内部状态或吞掉错误，它就越过了翻译责任。

---

## 6.5 第四种落位：完整子 Case 保留独立运行事实

某项外部计算即使服务于父任务，只要具有独立生命周期，就不应继续压缩成一次 Provider 回调。常见信号包括：

- 需要自己的 setup、finish、error 和 teardown；
- 运行时间足以需要 checkpoint 或 resume；
- 需要独立 ResourceContext 子授权与 BudgetHandle；
- 产生多个具名 Artifact 或完整 Result；
- 需要稳定 run identity、attempt、deadline 与 cancellation lineage；
- 可以脱离当前父任务独立 build、check 和 run；
- 失败以后由明确 retry owner 决定是否创建新 attempt。

此时，父 Case 应通过共享运行时发起完整 CaseRunRequest，子 Case 使用 canonical builder 装配，在派生授权中运行，再返回 CaseRunResult。父层不持有子 Solver/Trainer/仿真器对象，也不越过结果信封读取内部状态。

完整子 Case 不要求一定属于 nsgablack 或 mlblack。一个独立仿真 Case 可以通过外部 Provider 驱动领域引擎，由 blackbase substrate 获得身份、资源、取消、Artifact 与 Result；如果框架没有为仿真内部状态定义一等语义，它仍然是外部领域 Case，而不是被伪装成 Solver。

这也解释了“调用”和“编排”的区别。调用只表示一个函数或服务被执行；编排必须管理多个独立运行事实之间的顺序、授权、失败传播和结果交付。一个 Trainer 在 step 内部直接 new Solver 并调用 run，是对象调用，不一定形成子 Case 编排；只有父子身份、资源、预算、取消和 Result 同时闭合，组合才成立。

## 6.6 同一个外部引擎为什么可能有四种不同位置

以数学规划器为例，可以看到分类是相对的。

第一种场景中，规划器只解一个很小的投影子问题，调用同步、确定、无独立产物。它可以是 Adapter 内部的受控组件。

第二种场景中，规划器为每个候选计算可行性或最优 recourse，调用昂贵、实现可替换且有明确状态码。它应通过 Provider 暴露。

第三种场景中，父框架的 SolveSpec 与商业求解器 API 差异很大，需要处理变量映射、状态码、gap、证书和文件 Artifact。这里需要 Bridge。

第四种场景中，单次求解持续数小时，支持 checkpoint，拥有独立预算和最终报告，也可以单独运行。它应成为完整 Case，内部再通过 Bridge/Provider 使用商业引擎。

物理仿真器、远程模型和数据库同样如此。分类不能由 import path 决定，而要同时看独立状态、运行粒度、协议距离和交付责任。

可以把判断过程压缩成一条路径：

~~~text
是否只是父生命周期内的原子确定性步骤？
    是 → 组件或 Pipeline operator
    否
是否只需稳定能力合同与可替换执行实现？
    是 → Provider / Backend
    否
是否主要困难是两侧协议和语义映射？
    是 → Bridge
    否
是否拥有独立 lifecycle、授权、恢复、Artifact 和 Result？
    是 → 完整子 Case
~~~

这条路径不是互斥的产品分类。完整 Case 内部仍可使用 Bridge，Bridge 下方仍可选择 Provider 和 Backend；它描述的是由外向内逐渐增强的边界。

## 6.7 外部仿真与求值必须报告近似质量，而不只是返回数组

很多外部能力并不产生精确事实。数值求解可能在容差内停止，仿真可能使用粗网格，蒙特卡洛评价带有采样误差，远程模型可能经过量化，数据库查询可能读取一个一致性级别较弱的副本。

若父任务只接收一个数组，近似质量会被抹去。优化 Adapter 可能把粗糙仿真误差当成真实目标差异，Trainer 可能把未收敛求解结果当成精确标签，缓存也可能把低 fidelity 结果冒充高 fidelity 完成。

因此，外部响应至少要区分：

~~~text
value             领域结果
status            完成、近似、不可行、未收敛或失败
quality           残差、gap、置信区间、网格或 fidelity
cost              evaluations、时间、设备或外部计费
identity          request、attempt、版本和 lineage
artifacts         大型场、日志、证书或模型引用
~~~

父侧语义决定怎样消费这些事实。一个 2% gap 可能在早期搜索中可接受，在最终认证阶段不可接受；一次仿真超时可能代表候选过于复杂，也可能是集群故障。Provider 负责准确报告，Bridge 负责翻译，Problem 或父 Case 才能决定它进入 objective、constraint、metric 还是 error。

## 6.8 缓存、重试和取消必须服从外部副作用

外部调用的成本经常发生在函数返回以前。请求一旦被远程服务接受，可能已经产生账单；设备实验一旦启动，材料已经消耗；数据库事务一旦提交，副作用不能通过父进程异常撤销；Python thread 超时以后，底层仿真仍可能继续。

因此，边界不能用“最终是否成功返回”决定一切。

预算应在真实 dispatch/start 点消费，异常时只能释放尚未开始的 reservation。重试必须创建新 attempt，并由唯一 owner 决定；不能让 Provider、Bridge 和父 run loop 各自重试一次。取消必须说明是请求已发出、排队任务已取消、运行中任务观察到停止，还是父层只是停止等待。迟到结果必须经过 run token、namespace 或 fencing 检查，不能写入新运行。

缓存也必须覆盖完整语义。对仿真而言，几何向量相同但网格、材料库、solver version 或容差不同，结果不能复用；对数据库查询而言，查询文本相同但数据 snapshot 或一致性级别不同，也不是同一事实。缓存命中是一项有证据的等价判断，不是字符串或数组相同。

这些问题说明外部边界不是“次要插件”。它可能是整个系统预算、正确性和可复现性的最薄弱位置。把它正式化，是为了让父任务知道自己正在依赖什么，而不是为了把外部世界改写成框架内部。

## 6.9 什么时候真的需要新的第一等语义层

既然完整外部 Case 可以运行仿真、求解和远程服务，是否永远不需要新的语义框架？也不能这样绝对化。

当一类任务反复出现，并且它拥有优化与学习都无法表达的稳定答案状态、反馈来源、更新规则、结果类型和组件生态时，建立新的第一等语义层可能是合理的。例如，一个专门面向交互式实验控制或高保真时域仿真的框架，可能需要正式拥有实验状态、观测模型、控制策略、物理守恒、时间积分和领域 Result。

但新增语义层的理由必须来自独立闭包，而不是“这个 SDK 很常用”或“目录已经很大”。至少需要证明：

- 它的权威未知状态不能诚实地表达为现有优化或学习状态；
- 它的 Feedback 与更新语义具有稳定公共结构；
- 多个独立 Case 会复用这些领域合同；
- 将其留在 Provider/Bridge 会持续造成语义泄漏；
- 新层仍能消费 blackbase 的共享运行合同，而不复制 Project/L0。

在这些条件成立以前，外部 Provider、Bridge 或领域 Case 是更诚实的落位。它允许框架覆盖广泛计算，又避免共享核心被每个外部产品的私有概念污染。

## 6.10 外部边界明确以后，才有资格收束到优化与学习

至此，前四章的通用性与后续的领域重点之间已经建立了完整桥梁。

框架能够治理的不只 OR 与 ML。任何标准 Case 都可以获得身份、资源、预算、取消、Snapshot、Artifact 和 Result；任何外部能力都可以在适当边界上被调用。但 nsgablack 与 mlblack 之所以需要独立语义层，是因为它们不只执行一次请求，而是分别拥有两类长期答案怎样形成。

优化拥有候选、目标、约束、搜索反馈、环境选择和 Pareto 等答案语义；学习拥有 DataView、模型状态、Head、训练 Feedback、Provider 和模型 Artifact 等答案语义。外部仿真、数据库和第三方求解器可以为两边提供事实，也可以成为独立领域 Case，却不会因为被调用就自动取得父层更新权。

下一章将以这个边界为前提，重新进入优化与学习。它不再承担“从所有通用计算直接跳到 OR 与 ML”的任务，而只需回答一个已经被限定的问题：在各种可能的答案形成闭环中，优化与学习共享什么计算语法，各自又必须保留什么领域真相。

本章建立的是 **I：外部计算落位的不变量与设计判据**。Provider、Backend、Bridge 和 Case 的具体公共 API、当前源码事实、合同测试与正式运行证据，将分别在共享运行、语义组合和工程实施分卷中核对。
