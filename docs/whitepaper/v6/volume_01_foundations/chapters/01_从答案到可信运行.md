# 第一卷·第一章　从“得到答案”到“运行一个可信的计算过程”

一本介绍计算系统的白皮书，很容易从名词开始。先画一张层次图，再列出各种组件，接着解释每个组件能做什么。这样的顺序对于已经熟悉系统的人很方便，却没有回答初次阅读时最重要的问题：这些东西为什么必须存在？如果一段脚本已经能算出答案，为什么还要在它周围建立一整套运行结构？

所以，本章不介绍任何具体组件，也不要求读者预先接受某种设计。我们先回到程序最朴素的承诺：给它一个问题，它给我们一个答案。

在简单计算里，这个承诺通常足够。输入一个数，函数返回另一个数；把返回值抄下来，工作就结束了。可是在优化、训练、仿真和自动化实验中，我们常常遇到一种不易察觉的分裂：程序已经返回，计算意义上的“答案”也已经出现，但现实中的任务还没有真正完成。结果可能无法解释，过程可能无法继续，已经发生的成本可能没有被记录，后台工作甚至可能仍在改变外部状态。

本章讨论的正是这条分界线。我们不急着给它命名，而是顺着计算任务从简单到复杂的变化，观察一个普通返回值究竟在什么时候开始不够用。只有把这个过程看清楚，后面的架构才不是凭空增加的层次，而是对真实问题的逐项回应。

---

## 1.1 程序返回时，任务真的结束了吗

从最简单的情况开始：

```python
def square_distance(x):
    return (x - 3.0) ** 2

answer = square_distance(1.5)
```

只要函数定义固定，输入含义明确，计算立即完成，而且没有外部副作用，`answer` 几乎就是全部结果。失败以后重新调用一次，也不会造成值得单独处理的损失。此时，保留输入、函数和返回值就足以重现计算；再增加复杂的运行记录，反而可能是过度设计。

不过，这份简洁并不是返回值天然拥有的性质，而是由一组隐含条件换来的：函数没有内部历史，调用不会只完成一半，执行成本可以忽略，失败后能够无损重来，输入和规则不会在两次调用之间变化，也没有其他人需要在脱离当前进程以后理解结果。只要这些条件稳定，我们就可以放心地省略它们。

现在看一个稍微真实的结果：

```text
方案 = [0.31, 0.74, 0.18]
成本 = 12.6
风险 = 4.2
违反约束 = 0
```

程序似乎已经给出完整答案：一个方案、两个评价值和可行性结论。但当这份结果被发给另一个人时，对方首先遇到的不是算法问题，而是解释问题。三个数分别代表什么？它们使用什么单位和顺序？成本与风险依据哪一版数据计算？“违反约束为零”是原方案本来可行，还是程序先修改了方案？这是不是最终确认的结果，还是运行中某个时刻暂时最好的记录？

如果对方还要根据这个结果作出决策，问题会继续出现。程序一共尝试过多少方案？有没有评价失败的方案？失败的评价是否已经消耗时间或费用？结果是从头计算得到，还是从某个旧进度继续？如果明天输入数据更新，我们能否判断两个结果是否仍然可比？

这些追问没有否定 `12.6`。它可能计算得完全正确。真正缺失的是使这句话成立的上下文。日常语言里，我们说“这个方案的成本是 12.6”，完整含义其实是：

```text
对于某个明确问题，
在某一份输入和某一套规则下，
一次具体计算得到了这个方案，
并以指定方式把它评价为 12.6。
```

交谈双方熟悉背景时，前几行可以省略；结果离开原环境以后，它们就不能继续靠默契存在。于是，程序返回的值与可以交付的结论之间出现了第一道差距：值只告诉我们“得到了什么”，结论还必须告诉我们“它在什么条件下成立”。

到这里，问题仍然主要是解释。只要把输入、规则和输出含义记录清楚，似乎就够了。真正让事情变得困难的，是计算开始沿时间展开。一个持续变化的过程，会在不同时间产生多个都看似合理、却不能互相替代的“当前结果”。

## 1.2 时间怎样进入结果

考虑一个反复改进方案的程序：

```python
solutions = make_initial_solutions()

for round_index in range(100):
    new_solutions = generate_new_solutions(solutions)
    scores = evaluate(new_solutions)
    solutions = choose_for_next_round(
        old=solutions,
        new=new_solutions,
        scores=scores,
    )

return choose_best(solutions)
```

如果一百轮全部完成，最后一行看起来仍然可以代表整个任务。但假设程序在第 87 轮中断，我们就必须区分几个不同时间：第 86 轮已经结束，第 87 轮的新方案已经生成，其中一部分或全部已经得到评价，而下一轮要保留哪些方案可能还没有决定。

这几个时刻都可能存在一个名为 `solutions` 的变量，却不代表同一个事实。第 86 轮结束后的方案集合可以作为稳定进度继续使用；第 87 轮生成的新方案只是待评价材料；评价结束后的集合虽然有分数，却还没有经过筛选。如果程序把其中任意一个文件命名为“最新结果”，名称本身并不能说明它是否处在一个内部一致的位置。

因此，时间一旦进入计算，“保存了什么”就不能和“在什么时候保存”分开。要从中断处继续，程序不仅要留下数据，还要留下足够信息说明：上一项动作是否完整结束，下一项动作是否尚未开始，以及多个参与变化的部分是否属于同一时刻。

如果评价很便宜，判断错了还可以重算。可当一次评价需要数分钟、占用设备、调用仿真器或产生费用时，时间问题会进一步变成成本问题。

设想程序准备评价三个方案。前两个评价成功，第三个在计算过程中抛出异常：

```text
方案 A：已经开始，评价成功
方案 B：已经开始，评价成功
方案 C：已经开始，随后失败
```

从函数返回的角度看，整批工作失败了；从现实成本看，三次工作都已经发生。如果程序因为没有拿到完整结果，就把三次额度全部恢复，账面会显示本批没有消耗，下一次重试却会再次占用设备或产生费用。反复失败甚至可以绕过原本设置的成本上限。

这里不能只记录“成功了几个”。程序还必须区分哪些工作只是计划、哪些已经真正开始、哪些顺利完成，以及哪些虽然失败却已经产生成本。任务是否成功与成本是否发生，是两种不同事实。异常可以让结果缺失，却不能让已经发生的工作从历史中消失。

当计算进一步分成多个阶段，问题又多了一层。设想一条很常见的流程：

```mermaid
flowchart LR
  A["准备数据"] -->|"处理后的数据"| B["训练模型"]
  B -->|"训练结果"| C["搜索方案"]
  C -->|"选定方案"| D["生成报告"]
```

在同一个脚本里，四个阶段可以直接传递变量，看起来没有额外问题。但变量只说明“手里有一个对象”，不说明这个对象来自哪一版上游结果。数据重新处理以后，训练阶段是否仍在使用旧数据？模型重新训练以后，搜索阶段是否拿到了新模型？报告中的分数与最终保存的模型是否属于同一次训练？

一旦流程跨越进程、机器或日期，只靠内存传递建立的联系就会消失。下游不但需要一个值，还需要知道这个值由谁产生、基于什么产生、是否完整，以及以后怎样重新找到。同样，某个阶段失败时，整个流程也不能简单退化为一句“运行失败”；此前完成的数据处理和训练结果也许仍然有效，也许因为缺少一致关系而不能继续使用。系统必须能够区分这两种情况。

时间还会进入任务的结束方式。下面的程序在等待五秒后请求取消后台工作：

```python
task = start_in_background(expensive_work)

try:
    result = wait(task, timeout=5.0)
except TimeoutError:
    request_cancel(task)
    return {"status": "timed_out"}
```

主程序已经返回“超时”，后台工作却未必停止。正在运行的线程通常无法被外部安全地强制终止；远程请求也可能已经开始执行，只是确认消息没有及时送回。后台工作可能继续写文件、更新数据库或产生费用。于是，“主程序停止等待”和“现实中的工作已经结束”成为两个不同结论。

如果程序把前者描述成后者，旧任务就可能在用户以为一切结束以后继续改变结果。一个诚实的系统至少要区分：已经提出停止请求、已经确认停止、仍可能运行，以及外部副作用已经发生而无法撤回。这里的难点不在于多写一句日志，而在于程序不能声称自己拥有实际上不存在的控制能力。

至此，原本简单的“输入—计算—输出”已经被时间拉开。中间状态要求说明所处位置，昂贵工作要求说明真实成本，多阶段依赖要求说明结果来历，并发与远程工作要求说明任务是否真的结束。恢复也因此不再等于读回一个旧文件。要继续同一次过程，必须知道文件属于哪个问题、保存在哪个时刻、此前有哪些工作已经发生、随机过程和内部变化走到哪里，以及重新开始时的输入与规则是否仍然兼容。

这解释了为什么交互式实验常常让一个尚未闭合的程序显得已经完成。变量一直留在内存里，于是状态关系不必说明；作者记得单元格的运行顺序，于是人的记忆补上了过程；当前只有一个任务，于是资源冲突暂时没有出现；实验很短，于是从头重跑掩盖了恢复问题。交互式环境非常适合探索，却只能证明某条路径曾在某段内存历史中得到答案，不能自动证明答案已经可以脱离这段历史而独立存在。

随着这些问题逐一出现，我们可以看到一条连续变化，而不是若干无关功能：

```text
瞬时计算
→ 有历史的计算
→ 有真实成本的计算
→ 可能部分完成的计算
→ 依赖其他结果的计算
→ 中断后仍需继续的计算
→ 必须解释自身过程的计算
```

现在可以回头追问：这些现象究竟是在怀疑算法、怀疑代码，还是在怀疑别的东西？这个问题把我们带到下一层——一个结果为什么会在局部看起来完全正确，整体上却仍然不能放心使用。

## 1.3 从“局部正确”到“整体可信”

先看方案搜索。程序完整运行了五百轮，最终写出 `best.json`：

```python
solutions = make_initial_solutions(seed=7)

for round_index in range(500):
    proposed = generate_new_solutions(solutions)
    scores = evaluate(proposed)
    solutions = choose_for_next_round(solutions, proposed, scores)

save_json("best.json", choose_best(solutions))
```

文件中的方案可能确实是五百轮后最好的方案，程序实现也可能没有任何数组错误。但它仍然无法支持恢复，因为生成新方案所需的内部记忆、随机过程的位置、已经发生的评价成本和完整进度都没有保存。增加一个 `solutions.pkl` 也未必解决问题：如果方案集合在某一时刻写入，其他内部变化在另一时刻写入，恢复时仍会把不同时间的事实拼在一起。

再看模型训练。程序打印了很高的分数，也保存了模型文件：

```python
table = load_csv("train.csv")
features, target = prepare_data(table)
model = train(features, target)
score = validate(model, features, target)

save_pickle("model.pkl", model)
print({"score": score})
```

分数的计算公式可能正确，训练代码也可能忠实执行了方法。但如果 `train.csv` 的版本、特征顺序、缺失值处理、数据切分和输出解释没有留下来，另一个人就无法知道加载后的模型是否仍在回答同一个问题。即使参数数组相同，只要特征含义或类别编码变化，模型所代表的函数就可能已经不同。

这两个例子与前面的超时任务放在一起，揭示了三种不同的“正确”。

第一种是方法本身正确。它关心公式、排序、更新和评价规则是否成立。第二种是程序实现正确。它关心代码有没有忠实执行方法，有没有形状错位、数据错绑或异常误处理。第三种是运行过程正确。它关心真实时间、成本、失败和外部副作用出现以后，方法与代码原本表达的含义是否仍然保持。

方法正确并不保证程序正确，程序正确也不保证一次具体运行可信。一个系统可以稳定地运行错误方法；也可以正确实现方法，却使用了过期输入；还可以每个函数单独看都正确，却在批量失败后抹去已发生成本，或者在宣布超时后允许旧工作继续写入。

因此，可信不是在“正确”旁边再增加一个漂亮形容词，而是要求三层判断同时成立：

```text
方法有依据
∧ 程序忠实执行
∧ 运行没有悄悄改变语义
```

这三层判断解释了为什么单独增加日志不能解决问题。日志可以记录程序说了什么，却不能自动保证保存的数据属于同一时刻，不能让已经开始的工作恢复为“尚未开始”，也不能阻止后台任务晚到写入。日志是观察过程的材料，不是过程一致性的来源。

到这里，前面的各类问题终于可以被归纳，而不需要提前引入任何专门对象。一项复杂计算同时展开两条叙事。

第一条是问题叙事。它说明输入是什么，程序试图求什么，怎样评价好坏，约束是什么，结果中的每个字段如何解释。没有它，计算只是数字变化，我们甚至不知道结果是否回答了正确问题。

第二条是运行叙事。它说明这一次执行从哪里开始，经历了哪些变化，哪些工作真正发生，在哪里中断或完成，最后哪些信息可以继续使用。没有它，答案即使数值正确，也无法确认自己属于当前输入、当前时间和当前过程。

两条叙事必须在最终结果处汇合。问题叙事清楚、运行叙事缺失，会得到“理论上知道在算什么，实际上不知道这次怎么算完”的系统；运行记录完备、问题叙事含糊，则会得到“过程非常规范，却稳定地回答了一个没有定义清楚的问题”。

一个完整结论因此可以表达为：

```text
对于问题 P，
在输入 D 和规则 C 下，
一次可区分的执行 E 经历了过程 H，
消耗了实际成本 B，
在可确认的最终状态 V 上得到结果 Y。
```

这不是要求把所有信息放进一个巨大文件。恰恰相反，大型中间数据、长期交付结果和轻量过程记录具有不同寿命，适合分别保存。完整性来自它们能够重新建立关系，而不是来自无差别复制。

下面是一份朴素的运行摘要。它不依赖任何特定实现，只把前面已经推导出的关系写出来：

```python
run_summary = {
    "run_id": "run-20260816-001",
    "problem_version": "sha256:...",
    "input_version": "sha256:...",
    "progress": {
        "round": 42,
        "moment": "round_completed",
    },
    "work": {
        "limit": 1000,
        "planned_but_not_started": 0,
        "started": 860,
        "succeeded": 853,
        "failed_after_start": 7,
    },
    "resources": {
        "requested_threads": 8,
        "allowed_threads": 4,
        "actually_used": "cpu / 4 threads",
    },
    "saved_progress": "state/run-20260816-001/round-42",
    "final_output": "output/run-20260816-001/report",
    "status": "completed",
}
```

它比一个结果文件多回答了几件事：这是谁的一次运行，依据的是哪一版问题与输入，记录对应哪个时刻，多少工作已经真正开始，需求与实际资源是否一致，可继续的进度和最终输出分别在哪里。它没有保存全部方案和完整历史，因为摘要的责任不是容纳所有数据，而是让重要事实能够被重新关联。

当这样的关系能够被检查，结果才开始脱离作者的当前进程而独立存在。不过，“能够解释一次运行”仍不等于“保证一切正确”。为了避免把可信误解成万能承诺，还必须说明这套判断的边界。

## 1.4 可信过程不是完美过程

首先，完整运行记录不能替代问题建模。一个优化程序可以准确执行给定目标，却无法判断这些目标是否代表真实业务价值；一个训练程序可以如实报告指标，却无法替领域专家决定标签、损失或公平性标准。问题定义错了，最严谨的过程也只会稳定地回答错误问题。

其次，过程可信不能替代算法理论。程序可以记录每一步如何发生，但这不证明所选方法适合当前任务，也不自动证明它会收敛。运行层面能够保证的是：已经定义好的方法没有被过期状态、错误成本或失败处理悄悄改写；它不能替研究者完成方法选择和理论分析。

再次，系统不能制造不存在的控制能力。正在执行的线程未必能够被强制终止，已经发送到远端的请求未必能够撤回，写入外部系统的副作用未必可以回滚。可信过程不承诺消灭这些限制，而是准确表达它们：停止请求已经发出，停止尚未确认，旧工作的后续影响需要隔离，已经发生的成本不能抹除。诚实描述限制，比提供一个语义模糊的“取消成功”更重要。

同样，一张漂亮的页面、一份功能清单或一次静态检查，也不能单独证明本次运行可信。它们可以展示记录、发现结构问题、说明某项能力存在，却无法替真实执行证明：当前输入确实被使用，成本确实被遵守，保存的进度确实来自正确时刻，超时任务确实不再拥有修改结果的能力。展示必须服从事实，而不能反过来制造事实。

所以，可信过程不是“永不失败的过程”，而是**不会在成功或失败时伪造自己经历的过程**。一次失败可以是可信的：它明确指出失败发生在哪里，多少工作已经发生，哪些结果仍然有效，哪些后台活动尚未确认结束，以及下一次能够从什么位置继续。相反，一次只返回 `success=True`、却无法解释这些事实的运行，即使给出漂亮数字，也可能不值得使用。

这个边界非常重要。它让我们不必追求一个无所不能的系统，而可以专注于更现实的目标：让问题含义不被运行过程改变，让已经发生的事情能够被准确叙述，让成功与失败都留下足够依据。

既然目标已经明确，就可以反过来形成一套不依赖具体技术的检查方法。

## 1.5 怎样判断一个答案是否已经能够独立存在

面对一个已经跑完的脚本，第一步不是阅读它打印了多少日志，而是暂时拿走产生结果时的便利条件。

先关闭当前进程，看看还剩下什么。如果只剩一个数值、数组或模型文件，而输入版本、计算规则和过程位置全部消失，那么被保存的是对象，不是完整结论。另一个人必须依赖作者记忆才能解释结果，说明关键前提仍然在程序之外。

然后让失败发生在不同位置：开始工作之前、一批工作进行到一半、内部状态刚改变以后、最终文件正在写出时。观察程序是否会把已经发生成本说成没有发生，是否把新旧状态混在一起，是否留下看似完整却无法继续的文件。只验证从头到尾顺利结束，只能证明最理想的路径成立。

接着同时运行两个任务。检查它们是否争抢同一资源、覆盖相同文件、共享随机状态，或者在一个任务结束以后继续修改另一个任务可见的数据。单任务成功没有竞争，不能证明并发时仍保持原有含义。

再尝试中断和继续。重新开始以后，程序是在延续同一过程，还是只借用了旧结果开始一次新尝试？此前发生的成本是否仍在？内部状态、随机过程、输入和规则是否与中断前一致？两种做法都可能有价值，但如果系统无法区分它们，就无法对“恢复”作出可信陈述。

最后，把任务交给另一个人，或者把它放进更大的流程。对方能否仅凭留下的信息理解输入、输出和失败？上游变化以后，下游能否知道自己持有旧结果？内层工作是否仍遵守外层给出的成本与结束条件？如果程序只有在原作者、原进程和原执行顺序都存在时才成立，它还没有完成工程意义上的交付。

这些检查看似分散，其实都在追问同一件事：**结果能否脱离产生它的偶然环境而仍然成立。**

如果答案依赖当前内存、作者记忆、隐含顺序或无法核实的文字记录，那么任务仍停留在“曾经算出过一个答案”的阶段。如果问题含义、过程位置、真实成本、失败后果和交付关系都能被重新确认，它才开始成为一次可信的计算过程。

现在，我们终于可以在不借助任何框架术语的情况下，总结本章走过的路径。最开始，一个瞬时、无状态、低成本的函数调用只需要返回值。计算沿时间展开以后，返回值必须和过程位置绑定；工作产生真实成本以后，成功与消耗必须分别记录；任务分成多个阶段以后，结果需要保留来历；并发与外部执行出现以后，程序还必须诚实说明工作是否真正结束。正是这些变化，使“答案”逐渐扩展成“答案及其产生条件”。

由此得到两条出口结论。复杂任务必须说明**算了什么**：输入、目标、规则和输出含义构成它的问题叙事。它还必须说明**怎样运行**：时间、状态、成本、资源、失败、恢复和交付构成它的运行叙事。两条叙事在最终结果处对齐，计算才形成完整结论。

本章故意停在这里。它不为这些责任指定对象，也不把当前代码结构当成论证前提；否则我们又会用尚未解释的设计去证明设计本身。按全书的证据口径，本章建立的是一条基础不变量。具体实现、源码事实、测试证据和真实运行证据，应当等相关概念正式出现以后再逐层给出。

下一章仍然不会立刻列出组件。我们先要回答另一个承上启下的问题：为什么有些程序只有几百行，却比拥有上百个模块的系统更难可靠运行？“复杂”显然不只是代码数量。它可能来自含义不清、状态错位、任务嵌套、资源竞争、部分失败，也可能来自记录与事实互相矛盾。第二章将把这些来源逐一分开，并进一步说明它们为什么会相互放大。只有完成这一步，后面寻找共同约束和稳定结构才有充分理由。
