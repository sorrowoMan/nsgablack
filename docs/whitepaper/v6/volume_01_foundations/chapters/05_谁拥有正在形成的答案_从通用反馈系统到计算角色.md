# 第一卷·第五章　谁拥有正在形成的答案：从通用反馈系统到计算角色

前四章刻意没有把讨论限制在某个算法领域。只要一项计算需要维持长期状态、消费有限资源、承受部分失败、接受反馈并留下可追溯结果，语义闭包、运行闭包、状态闭包、组合闭包和证据闭包就会成为真实问题。数据库事务需要回答哪些写入已经提交，增量编译需要回答哪个产物对应哪一版源文件，Web 服务的背压控制需要回答哪些请求仍有资格继续，设备控制需要回答旧指令是否已经失效。它们都能被前四章的十条不变量审查。

这份普适性带来了一个必须先解决的困难。如果所有长期运行、反馈驱动的系统都共享若干结构，为什么后续白皮书还要专门建立优化和学习语义？反过来，如果一个物理仿真器、数据库或外部数值求解器也会迭代、失败、保存状态和消耗预算，它是否也应该被压进优化或学习框架？

答案不能从产品名称、数学方法或代码形态中寻找。一个程序使用梯度，不一定就是机器学习；一个程序调用数学规划器，不一定自身就是优化 Case；一个服务内部有循环，也不意味着父任务拥有那个循环。真正稳定的判断轴是：

> **[I] 在当前讨论边界内，谁拥有那个尚未确定、最终需要被提交的状态？谁有权根据反馈改变它？谁只负责返回领域事实？谁只负责治理运行资格？**

这一问把前四章的通用计算重新分成了不同的责任位置。它不会立刻得出三个仓库，也不会提前发明一组框架类名；它先确定一条计算因果链中有哪些不同种类的所有权。只有完成这一步，下一章才有条件解释外部仿真、数据库、远程模型和第三方求解器怎样接入；第七章也才有条件说明为什么优化与学习是当前框架重点拥有的两种答案形成语义，而不是框架所能调用的全部计算。

## 5.1 有反馈，不等于在形成同一种答案

“反馈驱动”是一个很宽的描述。系统先做出动作，观察结果，再据此改变后续行为，都可以被称为反馈驱动。但动作、观察和改变分别属于谁，会产生完全不同的架构。

考虑增量编译。源文件变化后，构建系统判断哪些目标失效，重新执行必要步骤，并把新产物提交为当前版本。这里正在形成的答案是“与给定源码版本一致的构建产物集合”。编译器内部的优化过程可能非常复杂，但对构建系统而言，它通常只是一个接受输入并产生目标文件的执行边界。构建系统拥有依赖图、失效关系和产物版本，编译器拥有语言翻译语义；二者不能因为都维护状态就被视为同一循环。

再考虑数据库事务。事务执行过程中会读取、写入、冲突、回滚和重试。数据库拥有提交顺序与持久事实，业务服务拥有订单、账户或库存语义。服务调用数据库，不等于服务拥有 WAL、锁表或复制状态；数据库返回成功，也不自动证明业务任务已经形成完整 Result。

Web 服务的背压控制又不同。它根据队列深度、延迟和下游容量调整接收速率。这里正在变化的是运行许可和调度决策，而不是待搜索的工程方案，也不是待训练的模型。它拥有的是治理状态：哪些工作可以开始、应当等待或必须取消。

物理仿真器可能接收几何、材料和边界条件，经过数千步数值积分后返回温度场与应力场。它内部显然有长期状态与收敛条件，但在一个结构优化任务中，父层真正拥有的是候选结构和搜索状态；仿真器只为候选产生领域事实。若仿真本身就是最终研究对象，项目要求交付完整时间演化、checkpoint 与误差证据，它又可以成为独立运行单元。

这些例子说明，循环形态不能定义语义归属。真正需要区分的是三种问题：

1. 哪个状态是本次任务最终要形成和提交的答案？
2. 哪些计算只是为这个答案提供观测、评价、变换或外部事实？
3. 哪些状态只决定运行能否继续，而不定义领域答案本身？

如果不先回答这三个问题，任何“通用循环”都会把领域状态、外部系统状态和控制状态揉在一起。系统表面上统一了，实际上没有人能说清某次更新改变的是答案、证据，还是执行资格。

## 5.2 第一类责任：形成答案的语义闭环

所谓“形成答案”，不是指某个函数最后返回了一个值，而是指当前运行拥有一个起初未知、随后在反馈中逐步确定、最终必须以领域含义提交的权威状态。把它记作：

~~~text
S_t       当前权威状态
P(S_t)    由当前状态形成的可执行提议或可评价对象
E(P)      外部世界、数据或领域规则返回的反馈
U(S_t,E)  根据反馈得到下一状态
C(S_t)    判断是否允许提交或继续
~~~

在这条链中，状态 S 不是任意缓存。它是任务结果形成史的主语。系统必须能够回答它由哪个前态和哪份反馈产生、当前 revision 是什么、崩溃后怎样恢复，以及最终 Result 为什么引用它。

优化搜索属于这种责任。待形成状态可能是一组候选、搜索记忆、Pareto 前沿或当前最优决定；提议被解释成排产、结构、路径或参数；评价返回目标与约束；更新决定下一轮保留和探索什么。最终交付的是行动、方案或一组折中，而不是仿真器的内部时间步。

机器学习也属于这种责任。待形成状态可能是模型参数、结构、规则、统计量与优化器记忆；数据和任务语义产生 Feedback；更新形成新的模型状态；最终交付的是可复用模型、表示或预测能力。即使训练内部调用优化器，学习 Case 的权威结果仍是模型语义，而不是优化器内部某一步的向量。

答案形成语义至少包含五项所有权：

- **状态解释权**：内部状态代表什么领域对象；
- **反馈解释权**：哪些观测能够推动状态更新；
- **更新权**：谁可以把前态变成后态；
- **提交权**：哪个时点的状态可以成为结果；
- **结果解释权**：最终产物回答了原问题中的什么。

这五项权力不能被共享底座或外部 Provider 接管。共享层可以保存状态、限制资源、传播取消，却不知道某个排产是否可行，也不知道某个概率 Head 是否满足校准语义。外部仿真器可以返回应力，却无权决定搜索 Adapter 怎样选择种群。一个远程训练服务可以返回模型，却必须通过正式结果合同说明哪个模型才是调用任务的权威产物。

因此，一等语义不是“代码很多”或“算法复杂”的同义词。它意味着框架选择理解并拥有一类答案怎样形成。

## 5.3 第二类责任：产生领域事实的计算边界

并不是所有复杂计算都需要在父框架中获得一套状态更新语义。很多能力的责任是在一个稳定请求下产生事实：

~~~text
领域请求
→ 外部计算或外部系统
→ 领域响应、误差、成本和证据
~~~

物理仿真器根据候选结构返回位移和应力；有限元程序根据网格和边界条件返回数值场；数学规划器根据模型声明返回可行解、gap 或不可行证书；数据库根据查询返回记录；对象存储根据引用返回字节；远程模型根据输入返回预测；实验设备根据控制声明返回测量。

这些系统内部可以有极其复杂的状态机。它们可能迭代求解、进行缓存、维护事务、使用分布式资源，甚至支持 checkpoint。父框架无须假装这些复杂性不存在，但也不应因此复制其内部语义。父任务真正需要拥有的是边界合同：

- 请求表达什么，schema 与版本是什么；
- 响应代表哪个请求和 attempt；
- 计算何时算真正开始，消耗什么预算；
- 可以怎样取消，超时后是否仍可能继续；
- 失败属于输入不可行、近似未收敛还是基础设施错误；
- 哪些大型产物通过 Artifact 引用返回；
- 同一请求在什么条件下可以缓存或重试；
- 外部结果以什么证据进入父任务的 Feedback 或 Result。

这里最容易犯的错误，是把“没有父层更新权”误解为“只是一个无关紧要的函数”。外部求值可能比父层搜索昂贵得多，也可能决定最终结论是否可信。它仍然需要身份、资源、预算、取消和证据；只是它的内部状态没有被父框架冒充为自己的语义状态。

同一个外部系统在不同关系中可以处于不同位置。数学规划器为一个 Trainer 样本计算结构化解时，是事实产生边界；以完整求解结果作为项目交付物时，可以成为独立 Solver Case；被用于某个优化 Adapter 的局部子问题时，则由 Adapter 或专用 Bridge 消费其结果。产品名称没有变化，父子关系中的责任发生了变化。

这说明“外部”并不等于“进程之外”。一个本地 Python 库也可能是外部语义边界，因为框架不拥有其内部状态与错误语义；一个远程 Case 也可以是框架内部的标准运行单元，因为它遵守共同请求、授权、生命周期和结果合同。边界由所有权决定，不由网络地址决定。

## 5.4 第三类责任：治理运行资格的控制闭环

还有一类状态既不是领域答案，也不是外部系统产生的事实，而是决定计算是否仍有资格继续。资源、预算、deadline、取消、lease、fence、重试和阶段状态都属于这一类。

例如，评估预算从 100 降到 0，不表示当前候选变差，只表示系统不再允许启动新的评估；父任务取消后，子任务的领域问题可能仍然有解，但它已经失去继续提交的资格；旧 Worker 最终算出一个正确结果，也可能因为 lease 过期而必须被拒绝；资源调度器把线程从 8 收窄到 2，不会改变目标函数，却会改变允许的执行结构。

治理闭环可以写成：

~~~text
运行事实
→ 控制决策
→ 授权、收窄、停止、取消或隔离
→ 新的运行事实
~~~

它与答案形成闭环都存在状态和反馈，但它们的权威对象不同。答案形成闭环回答“结果正在变成什么”，治理闭环回答“这次运行还允许做什么”。若把二者混在一起，算法就会私自解释资源，调度器也可能通过改写业务状态来实现停止。

共享底座之所以需要独立存在，正是因为治理关系会跨越优化、学习和外部任务。父 Project 必须能够给不同 Case 发放同一资源池中的 grant，共享预算 Authority 必须看见嵌套消耗，取消必须沿 lineage 传播，Artifact authority 必须拒绝旧参与者晚到写入。这些责任若由每个 Solver、Trainer 或 Provider 分别实现，组合时就会出现多个互不承认的事实源。

但治理统一不能升级为领域统治。Project 可以拒绝超出授权的仿真，却不能篡改仿真结果；BudgetController 可以停止新一代，却不能决定哪个 Pareto 解更优；SnapshotStore 可以保存模型状态，却不能解释模型输出。共享运行秩序与领域答案语义因此必须同时存在、互不越权。

## 5.5 三类责任不是三层固定软件，而是一次关系中的三个位置

把答案形成、事实产生和运行治理区分开以后，还需要避免另一种僵化理解：它们不是三个永远固定的产品类别，而是某次组合关系中的责任位置。

假设一个项目研究机翼结构。外层优化提出几何候选，物理仿真返回升阻比和应力，Project 限制总核时并传播取消。相对于这次运行：

~~~text
优化 Solver      形成候选与最终设计
仿真系统         产生空气动力与结构事实
Project/L0       治理资源、预算和运行资格
~~~

如果研究任务改为验证一种新的流体数值方法，仿真器的离散状态、误差控制和收敛过程本身成为主要交付物，它就可能作为完整 Case 拥有自己的 Result、Snapshot 和证据。它仍然不必被称为优化或学习，但已经不再只是父任务中的原子 Provider。

再看机器学习服务。在外层优化搜索超参数时，Trainer Case 形成模型答案，外层 Solver 形成试验选择答案，共享 Project 治理嵌套资源。一个任务中可以同时存在多个答案形成闭环，只要每个闭环有独立状态、生命周期和 Result，并通过公开父子合同组合。

数据库同样如此。作为 Context/Snapshot/Artifact 的持久化后端时，它是执行基础设施；作为业务 Problem 的查询来源时，它是事实边界；如果项目本身研究数据库查询优化，查询计划又可能成为优化语义中的候选。不能通过“这是数据库”一次性决定其框架归属。

因此，分类必须带主语：

> **对于哪个父任务、在哪个边界、以什么结果为交付，某个计算承担什么责任？**

缺少这三个限定，诸如“仿真属于优化”“求解器属于外部”“模型属于 ML”都可能只在某个例子中成立，不能成为架构规则。

## 5.6 五个判断把模糊需求变成架构边界

面对一个新能力，可以依次提出五个问题。

第一，**主要交付物是什么**？如果最终要交付被选择的方案、模型或独立仿真运行，说明某个状态需要成为正式答案；如果只交付给另一个状态更新过程使用的测量，它更可能是事实边界。

第二，**谁根据反馈改变权威状态**？若组件只接受请求并返回响应，它没有父层更新权；若它跨多轮维护状态、决定下一步提议并最终提交结果，它拥有答案形成闭环。

第三，**失败由谁解释**？仿真未收敛可能是候选不可行，也可能是 backend 故障。外部边界负责准确报告，父 Problem 或 Bridge 决定它怎样进入目标、约束或错误路径。若组件自己把所有异常压成一个巨大 loss，它越过了语义边界。

第四，**它是否需要独立运行事实**？若需要独立 identity、资源子授权、预算、取消、checkpoint、Artifact 和 Result，它应成为完整 Case；若可以在父生命周期中原子完成，则可以保留为组件或 Provider。

第五，**谁拥有全局执行资格**？无论组件多么专业，它都不能私自扩大父 grant、复制预算、创建不可见 Project 或在取消后继续提交。治理权始终来自共享运行底座。

五问得到的不是一个类名，而是一组架构条件。下一章会把这些条件进一步收束为四种常见落位：Case 内的确定性组件、Provider/Backend、协议 Bridge 和完整子 Case。

## 5.7 从通用计算回到统一框架，真正的桥梁是什么

现在可以准确回答本章开头的问题。前四章之所以足够通用，是因为闭包和不变量约束所有长期复杂计算；后文之所以重点讨论优化与学习，是因为当前框架选择对这两类“答案形成过程”提供一等语义，而不是因为其他计算不重要。

物理仿真、数值求解、数据库、对象存储、向量索引、远程模型和实验设备仍然属于框架覆盖范围。覆盖它们的方式，是承认其现实语义，通过正式请求、资源、预算、取消、错误与结果边界调用；不是把它们伪装成 Trainer 或 Adapter。

这一结论同时阻止两个极端。

第一个极端是把白皮书写成只适用于 OR 与 ML 的封闭系统，于是所有外部计算只能躲在 Problem 函数里，失去身份、预算和证据。第二个极端是为每一种外部产品新建一个一等语义层，最终共享底座被无数领域对象污染，框架再也没有稳定公共面。

更稳固的结构是：

~~~text
一等答案语义
    拥有未知状态、反馈解释、更新与提交

外部事实边界
    拥有请求到响应的领域真实性

共享运行治理
    拥有资源、预算、身份、取消与证据秩序
~~~

这三种责任可以组合，却不能互相冒充。第六章将沿着中间一项继续：当外部计算有时只是一条纯变换，有时是昂贵 Provider，有时需要协议 Bridge，有时又应升级为完整子 Case，边界究竟怎样决定。完成那一步后，第七章再从所有可能的答案形成语义中，解释为什么优化与学习构成当前统一框架的两种一等闭环。

本章建立的是 **I：架构不变量的角色化推论**。它不声称当前所有 Provider、Bridge 或 Case 已经满足这些边界；具体源码、测试和运行证据将在相关分卷逐项核对。
