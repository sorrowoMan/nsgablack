# 从状态演化到可重组求解系统 理解 NSGABlack 的框架思想

NSGABlack 的核心思想，可以表述为：**把一个完整求解系统拆成具有明确职责与契约的部分，再通过这些部分的组合，表达不同的问题、搜索方法和运行系统。** 在这个思想下，算法的名字只是理解系统的一个入口。更值得追问的是：它处理什么状态，依赖什么结构，怎样构造候选，怎样判断结果，又怎样把一次计算的结果变成下一次计算的依据。

这也解释了这个项目为什么会同时出现 Solver、Adapter、Problem、Representation、Unit、Plugin，以及 Project、Case、ResourceContext。这些概念分别承接求解中的不同责任。它们之间的关系建立起来以后，路径搜索、连续优化、多目标决策和模型训练就能够在保留各自语义的同时，共用相当一部分执行与工程基础。

本文以 2026 年 10 月 8 日工作区代码为基础，从求解的共同结构讲起，逐步说明 Unit 的位置、算法重组的条件，以及 nsgablack、mlblack、blackbase 如何组成一个框架栈。

理解这套框架，可以先暂时放下 NSGA-II、A*、VNS、Adam 这些名字，观察求解过程本身。一个程序获得输入，形成内部状态，根据规则执行操作，读取结果，然后改变状态。在一次路径搜索里，状态可能包含待扩展节点、已访问集合和路径代价；在一次进化搜索里，状态可能包含种群、目标值和随机数生成器；在一次训练里，状态可能包含模型参数、优化器槽位和当前数据进度。

因此，用状态演化来观察算法是一个有力的起点。可以用一个简化表达式记录这种观察：`S(t+1) = T(S(t), I(t), F(t), R(t))`。这里，S 是执行所需的状态，I 是当次输入，F 是评价反馈，R 是随机选择等外部影响，T 是状态转移规则。这个表达式用于说明共同结构，并不是仓库中的某个 API。它提醒我们：要解释一个算法，不能只看最后的公式，还需要解释它持有什么信息、依赖什么输入，以及什么变化被算作一次有效推进。

状态演化与图灵机所体现的计算视角相通，但二者承担的解释任务不同。计算理论给出描述计算过程的基础；一个工程框架还要进一步决定哪些状态可以独立组织、哪些机制能够替换、替换时需要满足什么条件。NSGABlack 值得研究的地方，正是在这一步：把抽象的计算过程落实成可以装配、检查、运行和恢复的组件关系。

状态发生变化以后，还需要一个标准，才能讨论变化是否有助于“求解”。这里的目标不必都表现为一个待最小化的数字。找到满足条件的对象、证明不存在可行解、找到一组折中方案、把误差控制在指定范围内，都可以形成有意义的求解要求。目标也可能由外部任务给定，而不是写在某个算法函数的第一行。对框架而言，关键是让评价与完成条件有明确的表达位置。

由此便得到第一个重要分离：**问题说明什么结果有意义，方法说明怎样利用已有信息继续寻找结果。** 同一个问题可以使用多种方法；同一种方法也可以用于多个问题。某个方法在一个问题上效果不好，需要结合表示、操作结构、算子和预算分析，不能只凭算法名称归因。这一分离给后续的组合提供了基础。

在实际建模时，“问题”还包括决策变量、可行域、输入数据和评价方式。例如生产排程需要说明如何表示一张排程表、什么约束必须满足、成本和延误怎样计算；模型训练需要说明参数代表什么模型、输入数据怎样解释、损失对应什么任务。把 Problem 视为目标的承载点，是一种清晰的职责选择；数学问题的其他部分则需要在表示和约束处理组件中得到实现。

当前代码保留了这个区别。[BlackBoxProblem](C:/Users/hp/Desktop/nsgablack/core/base.py) 提供目标评价，也提供约束违背评价接口。问题管线承担初始化、编码、变异、修复和解码等工作。也就是说，约束的含义、约束是否被满足，以及怎样把候选修成可行解，是彼此相关但不同的事情。一个约束可以参与可行解构造，也可以在评价时返回违背量；有些约束适合修复，有些约束需要拒绝候选或调用昂贵的外部验证。框架的分离允许为它们选择不同实现方式。

这在复杂问题里尤其有用。排程系统中的“机器不能同时执行两个任务”可以由构造算子尽量保证，也可以由 repair 修正，并由最终约束评价复核。算法仍然需要知道候选的评价结果，而不必承担整套排程规则。反过来，排程规则也不必依附于某一种接受准则。这样，更换搜索方法时，领域建模可以保留相当一部分。

不过，只分开 Problem 和求解方法，还不能完成算法的拆解。一个算法通常还隐含着一套特殊的操作结构。A* 操作带路径信息的节点；多目标进化方法操作种群及其评价；差分进化需要把 trial 与原来的 target 对应起来；梯度优化可能需要一阶、二阶动量；信赖域方法需要中心、方向和局部几何信息。只给这些算法一个普通向量，往往无法表达它们真正依赖的关系。

**Unit 的作用，就是把算法所依赖的操作结构显式化。算法管线构建 Unit，Adapter 操作 Unit。** 这句话既说明了职责，也给出了定制的入口：结构怎样建立，可以独立于搜索决策实现；搜索怎样推进，则由明确消费该结构的 Adapter 决定。

Unit 可以很简单，也可以很丰富。一个简单候选可以被封装成 CandidateUnit；一条当前轨迹可以包含当前点和最优点；PopulationUnit 可以同时保存候选矩阵、目标、约束违背和候选 token；更专门的结构还可以加入参考方向、邻接关系或探针对。Unit 的大小取决于算法需要保持哪些关系，而不取决于某个统一容器必须有多少字段。

这里需要区分“完整算法状态”和“算法操作结构”。随机数生成器、温度更新计数、停止策略、阶段调度等信息，未必都应放进 Unit。当前实现仍允许 Adapter 保有自己的策略状态。Unit 提取的是需要被明确构造和操作的结构，Solver 则继续管理整个运行的生命周期与权威结果。线程池、数据库连接、Provider session 或全局资源租约也各有所有者，不能因为它们参与计算就统统塞入 Unit。

以 A* 为例，这个划分非常直观。一个节点除了候选状态，还需要已发生的路径代价 g、启发信息 h、排序依据 f，以及父节点关系。当前 [AStarAdapter](C:/Users/hp/Desktop/nsgablack/adapters/astar/adapter.py) 计算相关代价，通过构建请求交给 SearchNodeBuilder 建立节点，再将节点放入待扩展结构。节点的构造和编码可以定制，扩展、排序、重开与反馈处理仍由 Adapter 执行。

从优先级的角度，可以把 `f = g + h` 理解为同时使用已经付出的代价和对后续代价的估计。这有助于说明 A* 与其他最佳优先搜索之间的关系。不过，完整的 A* 行为还涉及后继关系、代价累积、重复状态处理和结束条件。把这些条件放回系统中，才能准确说明一个具体实现正在运行什么方法。

因此，“A* 是一个 Case”和“框架存在 AStarAdapter”可以同时成立。前者指向一个完整可执行系统：某个路径问题、特定状态表示、后继生成规则、启发函数、节点构建器与搜索策略共同组成一个 Case。后者指向其中可复用的算法策略部分。一个完整案例可以采用 A*，也可以从中提取出稳定的策略机制，以 Adapter 的形式复用到其他案例。

这种理解避免了仅凭名字决定组件粒度。抽象层次不同，同一个算法名可能指向一本教材中的方法、一个可复用策略实现，或者一套已经针对具体问题装配好的系统。框架需要明确每个组件实际承担什么，而不是要求所有算法名称都只能落在一个层级。

A* 也说明了为什么结构检查不能停留在字段是否存在。如果问题管线在提案后把子节点修成另一个状态，原来的父边代价就可能失效。当前实现为此提供明确的 repair 策略：默认拒绝这种变化；领域允许重新解释父子边时，可以选择重新计算。仅仅补上 g、h、parent 这些字段，并不能自动保证路径关联正确。结构、反馈与搜索决策需要一起维护相应的不变量。

VNS 展示了另一个角度。它的可复用方法包含邻域切换、改善后的接受与重置、停滞后的扩大或重启。至于“邻域”在当前问题中意味着交换两个任务、调整连续变量，还是改变某种组合结构，需要由问题表示及其算子落实。邻域还没有被具体化时，我们得到的是一个方法框架；把这些操作实例化以后，才得到可执行的求解系统。

当前 [VNSAdapter](C:/Users/hp/Desktop/nsgablack/adapters/vns/adapter.py) 使用候选 Unit 保存当前与待反馈候选，同时通过独立的 NeighborhoodUnitBuilder 构建邻域尺度序列。Adapter 把当前邻域编号和尺度传给候选操作，依据评价决定接受或切换。这里已经实现的是明确的候选结构与尺度结构分离；具体领域的邻域仍需要对应的管线算子。把这个边界写清楚，才能知道定制一个新问题时究竟应改哪里。

VNS 的流程相对简洁，并不削弱它作为方法的价值。它提供的是关于“怎样组织局部搜索”的规则。复杂程度和抽象层次是两回事：一个简洁规则可以用于很多领域，而一个很长的实现也可能只是某个具体场景的装配细节。框架提取可复用机制时，应依据职责与依赖，而不是依据代码行数。

同样的思路可以延伸到种群算法。[复合 Unit 定义](C:/Users/hp/Desktop/nsgablack/units/collections.py) 中，基础种群结构保存候选及其反馈；参考种群增加参考方向；差分种群增加 target 索引和基线分数；分解结构保存权重、邻接、理想点和待反馈子问题记录。这些信息分别对应不同方法依赖的关系。结构提取后，选择、交叉、接受、标量化和替换规则仍由相应 Adapter 实现。

对于有限差分，探针的坐标、正负方向和实际位移也值得成为明确结构。假设一个负向探针在边界处被修复，真正发生的位移就可能小于名义步长。此时，梯度估计需要依据实际变化处理，而不能只拿原始步长代入。当前 PollUnit 就为方向、探针身份和位移提供了表达位置。这个例子说明，Unit 的意义往往体现为保住某种关系，而不是多包一层对象。

对于参数优化，算法管线可以构建参数布局及动量槽位，Adapter 决定怎样裁剪梯度、更新动量和推进参数。对于局部区域方法，算法管线可以根据输入数据建立一组基，Adapter 决定何时重建、在哪些方向取样，以及怎样调整半径。这些构建逻辑可以很复杂，甚至需要 QR、SVD 等计算；只要它承担的是结构建立的职责，就有独立组织的理由。

在代码上，这条边界由 [UnitSchema、构建请求和 UnitBinding](C:/Users/hp/Desktop/nsgablack/units/contracts.py) 共同表达。Schema 描述结构身份及必要字段，构建请求描述这次需要建立什么，Binding 把构建逻辑与持久化编码方式联系起来。候选型结构使用能够投影成候选的请求；种群、参数槽和局部几何等复合结构使用单独的结构请求，不需要伪装成一个巨大向量。

**拆分以后，灵活性来自明确的替换条件。** Adapter 需要什么结构、会请求哪些构建操作、是否需要额外的模型工厂，都必须能够检查。当前实现因此不仅检查 schema，还检查 `unit_build_operations` 与 `unit_builder_methods`。例如，一个构建器即使声称提供参考种群，如果不能执行参考方向构建，NSGA3 的装配仍会失败；MAS 所需的模型工厂也必须确实存在。

兼容可以超出完全相同的 schema，但需要显式声明。ReferencePopulationBuilder 提供比基础种群更多的结构，同时声明兼容基础 PopulationUnit，因此可以供 NSGA2、SPEA2 和 NSGA3 使用。它们可以共享无状态构建器，各自拥有独立运行 Unit。反过来，一个只有基础种群能力的构建器不能据此满足 NSGA3 的参考方向要求。这样的兼容具有方向性，也受版本和投影方式约束。

这进一步说明：严格对齐与灵活重组并不冲突。严格的是消费方真正依赖的契约；可替换的是满足契约的实现。若所有东西都可以接在一起而不检查，错误就会推迟到搜索过程中。若只认具体类名，又会让本来可复用的结构被锁死。显式兼容为二者建立了一条可以审计的边界。

契约还需要与语义验证配合。字段同名，未必代表含义相同；两个矩阵尺寸一致，也未必代表相同的坐标系或反馈顺序。兼容声明意味着构建器作者承诺可替换的语义，运行时可以检查字段、投影和部分结构关系，领域测试则负责验证具体含义。这个区分给框架留下了开放扩展的空间，同时让“已经检查什么”有清楚范围。

状态恢复使用另一条更严格的规则。两个结构能够被同一个 Adapter 消费，并不意味着它们的历史状态可以互相解码。当前 checkpoint 保存实际结构 schema 与 codec binding，恢复时要求匹配。恢复通过专门的 codec 读取已经保存的结构；重新运行构建管线可能重新采样、重新拟合或产生不同结构，不能被默认为原状态的恢复。

至此，问题、操作结构和方法已经有了清晰位置，但一个可运行的系统还需要协调它们。**Solver 的职责，是让求解按照一致的运行语义发生。** 它管理生命周期、评估入口、预算、状态提交和插件通知。Adapter 提供搜索策略，Solver 负责把策略放入一个可以运行、停止、恢复和交付结果的过程。

在 [ComposableSolver](C:/Users/hp/Desktop/nsgablack/core/composable_solver.py) 的实际路径中，Adapter 首先提出候选；控制面建立候选身份，检查可用预算；配置了问题管线时，候选经过公共 repair 路径；随后统一评价，再把反馈交给 Adapter 更新。与此同时，Solver 维护评估事件、接纳处置和权威状态。一个最小闭环可以读作：`提出候选 → 表示与可行性处理 → 评价 → 反馈更新 → 提交有效状态`。

这个闭环能够服务不同算法，原因在于它表达的是共同的交互过程，而没有要求所有算法内部执行相同操作。A* 可以提出后继节点，进化方法可以提出一批 offspring，参数优化可以处理梯度与状态转移。共同协议负责交接信息，具体策略仍然决定如何利用这些信息。

其中有一个容易被低估的设计：候选具有语义身份。两个数值完全相同的向量，可能属于不同模型规格、不同来源，或不同的算法位置。仅凭数组相等，不能可靠地判断哪份反馈属于哪个候选。框架使用 CandidateBatch 同时保留语义状态、数值矩阵和 candidate token，使数值算法能够高效操作矩阵，同时让评价、结果绑定与恢复继续识别语义对象。

Unit ID 与 candidate token 也分别承担不同责任。Unit ID 标识 Adapter 内的结构对象，candidate token 用于控制面中的候选关联。它们可以互相关联，但不能未经定义就当成同一套身份。尤其在父子路径、多标签搜索、候选复制和多个种群槽位中，这种区别能够防止“数值还对，来源已经错位”的问题。

组合多个 Adapter 时，状态关系同样需要保留。两个子策略可能持有不同种群，并依赖不同布局或不同含义的辅助结构。将它们随意拼成一个 population，会掩盖谁拥有哪些候选、谁能够解释哪些反馈。当前框架通过单一、委托和分区等种群状态模式表达不同所有权；复合策略可以逐子实例传递 Unit binding，并保留独立结构。同一 Solver 内的候选仍需满足共同的问题维度与评价契约；只有真正执行了有定义的融合，才应把结果解释为统一种群。

这意味着，算法组合需要说明的不只是执行顺序，还包括信息如何交换。一个策略把输出作为另一个策略的起点，与两个策略并行维护各自种群，具有不同语义。一个精英保留机制向内层插入候选，也可能破坏内层的父边、探针对或 target 对应关系。当前实现对带有这种关联的提案设置替换限制，正是为了让组合保持方法本身的含义。

工程层面的状态提交，则回答另一个问题：一次操作到底有没有成为正式进展。提出了候选、发生了评估，并不保证已经完成一个逻辑步骤。预算可能耗尽，候选可能被拒绝，Provider 可能失败。框架通过 StepOutcome 区分这些结果，只让真正 committed 的步骤推进逻辑计数。物理尝试和逻辑提交分别记录，恢复以后预算和进度才有一致含义。

这也是步骤事务、Snapshot 和 checkpoint 存在的理由。Context 保存轻量运行字段和引用，大对象进入 Snapshot 或 Artifact。评估事件可以记录“这次确实计算过什么”，权威状态则记录“系统已经正式接纳什么”。两者分开，失败的尝试就不会覆盖上一份有效种群；恢复也能够依据已有证据处理未决状态，而不是盲目重放可能具有副作用的评价。

当算法依赖外部状态 Provider 时，这个要求更具体。一次参数更新可能产生新的模型状态引用和优化器槽位；被拒绝时，应能恢复前驱引用并清理本次新增资源；提交后，再回收不再需要的旧状态。清理失败需要留下可重试的记录。Unit 提供结构表达，Provider 与 Adapter 的显式事务协议则维护这些外部状态的生命周期，不能依靠复制整个 Python 对象图代替。

Plugin 和 Bias 承担另外两组工作。Plugin 可以加入日志、checkpoint、运行报告、监测和评估后端等能力，并通过公共生命周期参与运行。Bias 表达先验、偏好与软引导。它们让一个搜索方法适应具体环境，却各有边界：把某条规则作为软偏好，与把它作为必须满足的硬约束，产生的含义不同；把搜索接受准则藏进日志插件，也会使方法本身难以识别。

四个主要扩展面因此仍然成立：Solver 负责控制，Adapter 负责策略，Representation 负责候选表示与流转，Plugin 负责运行能力。Problem 提供评价语义，Bias 提供软引导，Unit 与算法管线把结构构建的边界补得更明确。这些组件能够共同工作，是因为它们之间存在数据、生命周期和所有权契约；正交性并不意味着彼此完全没有联系。

把视野扩大到机器学习，这套分解就显得更加有用。模型结构说明怎样从输入产生输出，模型状态说明当前参数和其他必要信息，训练问题说明数据、损失和评价，求解方法说明怎样依据反馈更新状态。这些责任分别表达以后，模型组件就能够与不同求解方法建立关系。

在这个意义上，可以把一次训练视为对模型语义状态的求解。不过，机器学习系统还需要处理数据切分、输出含义、统计评价和泛化问题。优化目标下降能够说明求解取得某种进展，却不能单独说明模型对新数据有效。因此，框架统一的是求解过程中的共同接口，机器学习的领域语义仍需要专门组件承担。

这正是 mlblack 的位置。它提供 DataView、Spec、模型表示、Codec、Head、LearningProblem、Evaluation Provider 和模型 Artifact 等组件。Codec 建立模型状态与算法可处理视图之间的联系，Head 解释输出，LearningProblem 消费数据并产生反馈，Provider 执行具体后端上的计算。算法管线再建立相应 Unit，Adapter 据此推进搜索或参数更新。

当前 [LearningSolver](C:/Users/hp/Desktop/mlblack/integrations/nsgablack_control.py) 直接建立在 ComposableSolver 上，`fit()` 调用共享运行入口，再交付 ML 语义下的 TrainerResult。这是代码中已经存在的控制面统一，而不仅是两套接口长得相似。闭式拟合与第三方 estimator 的拟合操作，则由相应 Problem 或 Provider 承接，外层仍然使用同一运行与结果协议。

因此，Unit 的提取主要影响模型状态进入搜索方法的结构接口。它不要求每个模型族重新定义自己的优化生命周期，也不要求优化 Adapter 理解所有神经网络或第三方后端。大型模型的活状态可以由正式 Provider 引用管理，Unit 只持有所需的可编码结构或约定引用。计算执行、模型语义和搜索规则由各自的组件负责。

统一训练和优化的好处，还体现在嵌套系统中。外层可以搜索模型配置、结构或资源预算，内层运行训练，再把验证误差、复杂度或计算成本返回外层。内层也可以继续调用一个独立优化 Case。此时，内层训练对外层而言是一种评价过程，但它自身仍然需要完整的运行边界、状态恢复和产物交付。

这种嵌套不能只靠几个互相调用的函数维持。父任务需要向子任务传递资源授权、取消信号、剩余预算和输入产物；子任务需要返回结构化结果，并说明产物是否已经正式发布。否则，计算层级越深，越容易出现资源超用、预算重复计数、失败后仍读取半成品等问题。

blackbase 承担的就是这组共享责任。[Project runner](C:/Users/hp/Desktop/blackbase/src/blackbase/project/project_runner.py) 以及相关 Case、Artifact 和资源协议，为不同语义层提供共同运行基础。nsgablack 负责优化搜索，mlblack 负责机器学习语义，Project 级 L0 发放 ResourceContext。Case 可以声明需求并消费授权，不能各自建立一个互不知情的全局资源分配器。

这里的 Project、Case 和 Scaffold 可以按三个尺度理解。Project 描述多个可运行单元之间的依赖与资源安排。Case 是能够独立运行、也能够作为内层被调用的单元。Scaffold 则是这个单元内部的正式组织方式：问题、管线、策略、插件、评价与运行配置通过规范入口装配起来。`build_solver.py` 是这一装配入口；Trainer 的命名习惯可以通过薄别名保留，底层边界保持一致。

复杂系统由此拥有两种组合尺度。在 Case 内部，组合的是问题表示、Unit 构建器、搜索策略和运行能力；在 Project 内部，组合的是独立的 Solver、Trainer 或其他标准 Case。前一种组合关心算法结构和策略交互，后一种组合关心任务依赖、资源、产物和执行关系。把两者分开，才能让一个局部搜索方法保持清楚，同时让整个系统拥有复杂拓扑。

仓库中的[跨框架拓扑示例](C:/Users/hp/Desktop/nsgablack/examples/cases/super_topology_orchestration/project_config.py) 已经展示了这种组合：基线 Solver 与 Trainer 可以作为 DAG 中的就绪节点运行，外层搜索依赖它们发布的 Artifact；[外层 Problem](C:/Users/hp/Desktop/nsgablack/examples/cases/super_topology_orchestration/cases/outer_search/problem/nested_training_problem.py) 再通过正式 Case 请求调用内层训练。这个示例说明，静态任务依赖与搜索过程中产生的动态调用可以处在同一套运行协议中。

若把这种能力用于“预测加排程”，可以设想一个具体系统：先由训练 Case 建立需求预测模型并发布 Artifact；再由优化 Case 在产能、材料和交期约束下搜索排程；评价阶段使用模型或仿真器估计成本与延误；外层还可以比较不同预测方案对最终决策的影响。这个场景是架构组合方式的说明，具体业务模型和效果需要单独实现与验证。

在这样的系统里，Unit 的价值很清楚。排程领域的候选表示和可行性处理可以保留，算法所需的索引、邻域或种群结构可以定制，搜索方法也可以在满足契约的前提下替换。预测模型的语义由 mlblack 承担，计算资源由共享底座授权，跨 Case 的结果通过正式产物传递。每次改动都能回答它究竟改变了系统的哪一部分。

从这个角度看，NSGABlack 对多种逻辑的统一已经有具体含义：问题与方法通过反馈协议交互，结构与策略通过 Unit 契约交互，训练与搜索通过同一控制面运行，不同任务通过 Case 协议组合，状态与结果通过共同的证据和持久化机制交付。各领域仍保留自己的数学含义，但不必为每种算法重建整套运行基础。

这种统一也有表达边界。一个能够描述状态演化的框架，不会因此自动获得对所有问题都高效的算法；一个能够组合策略的系统，也不会让任意组合都保持原方法的性质。具体算法依赖的前提、特定结构的语义，以及目标与数据是否建模正确，都需要在相应层面成立。明确这些条件，会让统一接口更有用，因为使用者知道哪些部分可以复用，哪些部分必须重新论证。

如果讨论长期研究价值，我更倾向于把这个框架定位为：**面向求解系统的可组合架构，以及结构与搜索策略分离的实验平台。** 这个定位连接了优化方法、机器学习系统与软件体系结构。它既允许研究新方法，也允许研究同一种方法在不同结构、表示和运行条件下怎样表现。

一个直接的研究问题是结构与方法的相互作用。固定 Adapter、问题管线、评价预算和随机种子，替换 Unit 构建方式，可以研究结构定制带来的影响。固定结构契约与构建器，替换兼容 Adapter，可以比较方法的行为。再对少量关键组合进行交叉实验，才有机会区分结构效应、方法效应以及二者的交互。

这也使“结构不好不等于方法不好”从一个合理判断，变成可以落实的实验安排。评价指标除了最终目标值，还可以包含可行率、构建耗时、评价次数、达到给定质量所需的时间、恢复成本和失败类型。某个结构提升搜索质量却显著增加构建开销，与一个质量略低但成本更小的结构，可能分别适合不同使用场景。

另一个研究问题是组合是否保持语义。候选被裁剪、复制、修复或重新排序后，反馈还能否准确对应？某个子策略失败时，其他策略的已提交状态是否保持？模型 Provider 更新后，前驱状态还能否恢复？最终产物发布前失败，外层是否会误读它？这些问题关系到实验结果是否可信，也关系到复杂系统能否长期运行。

可复用性本身也能够被观察。接入一个新问题时，需要重写多少搜索代码？替换模型或表示时，是否需要改动控制平面？一个新结构能否服务多个兼容方法？一次错误配置能否在装配时被指出？这些指标比单纯统计组件数量更能说明抽象是否有效。长期积累不同领域的正式 Case，可以检验哪些边界稳定，哪些边界仍然过于依赖某一类算法。

当前 Unit 改造已经给这些研究提供了实际基础。候选、节点、种群、邻域、探针、参数和局部区域等结构有独立构建入口；Adapter 声明消费要求；组合树可以审计子绑定；自定义字段可以通过 codec 进入恢复路径。[兼容性测试](C:/Users/hp/Desktop/nsgablack/tests/test_unit_binding_compatibility.py) 还覆盖了共享构建器、显式兼容的方向、版本限制、缺失操作、额外槽位，以及自定义结构的回滚。

2026 年 10 月 8 日这一工作区的最近一次 nsgablack 全量回归结果为 1169 项通过、6 项跳过、6 项警告，严格 Doctor、两个正式 Unit Case 的装配检查及 Catalog 双口径检查通过。详细记录保存在[算法 Unit 中文说明](C:/Users/hp/Desktop/nsgablack/docs/guides/ALGORITHM_UNITS_CN.md)。这说明已有实现通过了对应功能与契约检查；算法效果、跨领域收益和性能开销仍需要针对相应问题进行实验。这个结果也不应被当成三个仓库所有可选后端都已经完成独立全量验收。

对使用者而言，最有帮助的建模顺序是先明确目标、变量、约束和评价，再说明候选怎样表达；随后列出方法需要的操作结构，决定哪些结构由算法管线构建，哪些决策由 Adapter 执行；最后装配运行能力，并判断是否需要拆成多个 Case。这样，框架中的概念会逐一对应具体需求，而不必在项目开始时就堆满所有扩展点。

后续演进也可以沿着同一原则进行：每增加一种结构，说明它服务什么操作；每增加一种方法，说明它依赖什么契约；每增加一种组合，说明状态与反馈怎样关联；每增加一个跨 Case 调用，说明资源与产物怎样传递。让这些关系在代码、装配检查和实验中同时成立，框架就能够持续容纳更复杂的求解系统，而使用者仍然能够理解每一部分为何存在。
