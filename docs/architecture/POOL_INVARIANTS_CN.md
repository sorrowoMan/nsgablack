# Pool 语义压缩试写：9 条不变量与不能唯一推出的策略

核对日期：2026-11-02。状态：讨论稿；不改变当前运行契约或执行权限。

## 结论先写清楚

核心安全语义可以压成下面 9 条，但 **AGENTS.md 中的全部具体限制不能仅从数据结构唯一推导出来**。其中既有不变量的直接后果，也有算法语义的专门化，还有实现选择的默认策略和当前未开放的能力。

这不是通过把每条特例换个名字塞进“不变量”来完成压缩。下面的不变量不列回调名、算法名、参数默认值或具体 API 白名单。遇到必须额外引入这些前提才能成立的规则，就标出前提，不能假称已经推出来。

因此，待验证的主张应是：**用户理解少量语义，就能预测什么一定不能做；至于多个合法方案中框架选了哪个，文档须简明告知。** 它不应承诺用户可以从一个容器类型猜出所有方法名和默认参数。

## 一、先分清正在压缩哪几层

当前公开名 `Pool` 是调用期选择/草稿的接口；`SolutionPool` 是运行内版本与集合的存储权威。二者不能被当成两个独立的全局池管理器。

最小语义地图是：

- 候选版本：一个具体解在某个版本下的内容。
- 成员视图：对精确版本的有序引用，可以包含重复出现的位置。
- 解释：这些引用在何种问题、偏好或任务下被评分、比较。
- 操作作用域：谁在何时可以读什么、向哪里提交哪些操作。
- 提交：操作何时成为公共事实，以及失败后如何对账。

前两项主要是数据模型；后三项属于框架已经选择的运行协议。若把“核”仅定义为一个存放数组的容器，事务、权限和恢复当然不可能全从它推出。这些协议必须作为少量前提明说。

## 二、9 条候选不变量

### I1：身份确定对象，版本确定内容

一份引用必须无歧义地指向所属范围中的一个具体版本；已存在版本的内容不能被原位改写。读取不创造新对象；产生新对象和修订已有对象是不同动作。

**预测：** 数值相同不能替代身份；只记 token 或名字不能追到任意“最新内容”；repair 改内容也不能覆写旧版本。

不变量要求的是可验证的精确指向，不规定必须使用哪种 key、哈希算法或物理存储布局，也不保证一个未被保留的旧引用永久可读。

### I2：每种事实有一个明确的决策归属

候选内容、集合成员、算法结构、评分解释和执行进度是不同事实。一个对象只能通过明确的操作影响另一种事实，不能因共享引用或配置绑定而自动获得另一方的决定权。

**预测：** 池成员不等于算法成员；借用一个解不等于借用别人的 Unit；改变数据来源不能自动创建任务、运行算法、选择成员或分配全局资源。

一个权威可以接收多个操作计划；“同一事实一个权威”不等于“永远只能有一个调用者”。

### I3：视图的成员与含义必须显式，不能靠名字猜

一个成员视图说明它引用哪些版本、顺序/重复位置有什么含义，以及它是普通集合、算法结果还是目标投影。成员关系、派生来源、最终选择和已接纳历史不是同一种关系。

**预测：** 一个来源父视图不必包含后代视图的全部成员；accepted 不等于最终 members；重复引用的两个位置不一定是同一个槽位；池没有天然的“最优”排序。

这里的“有序引用”不是新建永久 occurrence ID：位置属于具体冻结视图，不能把修订前的位置直接套到修订后。

### I4：一次解释必须绑定确定的读取范围与时点

一个操作使用的来源、目标前提、读取授权和坐标必须可识别；不能在执行中偷偷切换身份、修订、来源范围或任务解释。

**预测：** 名字相同而 view_id/revision 不同，不能默认为同一输入；部分接纳后不能靠压缩索引猜原行；恢复不能重抽输入或默默追读最新版本；选择已发布视图不等于等待未来视图出现。

这要求稳定语义，不强制“每一次查询必须重新访问磁盘/SQL”。经过验证的不可变值可以在满足同一身份/范围前提时复用。当前调用期对象的失效时机是落实该要求的一种具体方案。

### I5：反馈和判断只能作用于它们真正描述的对象与语义

“这个值已评估”“这个解可行”“这个候选更好”等判断，必须绑定候选版本和相应的问题/比较含义。变换后的解释不能反过来冒充原始事实；维数相同也不证明分数可比。

**预测：** 修复后旧评分不能直接绑定新内容；不同方向的标量分数不能自动拼成一列排序；选择偏好不能伪装成原始约束。缓存复用要证明兼容，不能靠同值或同 token 猜测。

这并不推出“永远必须重新求值”：有明确兼容条件和合格证据时可以设计复用。当前默认重新经过评估/偏好链是保守执行政策。

### I6：查询不隐含效果；效果必须有明确授权与归属

一个被声明为查询/选择的操作只返回读取结果。创建对象、改变成员、产生提案、启动求解和发布结果等效果，必须由有权主体明确声明，并交给它所属的提交过程。

**预测：** 纯选择回调不能偷偷发布成员编辑；写权限不能顺便扩大读权限；能读一个集合不意味着能替换其算法结果视图；返回有改写意图的计划不等于计划已经执行。

它不规定效果必须用 `inject`、返回值、装饰器还是其他语法表达，也不规定只有哪两个回调可以拥有这种授权。对任意 Python 外部副作用，这仍是组件契约，不是沙箱证明。

### I7：公共事实按声明的提交条件一致发布，恢复只对账

一组相关变更必须有明确的提交条件与一致的可见性边界。失败不能留下半套公共事实；已经真实发生且不能撤销的外部事件，不能伪装成没发生。恢复依据已保存事实，不隐式重做决策。

**预测：** Unit、成员计划、池 manifest 和 Authority 不能各自宣布成功；未提交草稿不应混入公共查询；失败时内部状态可回滚，实际求值和预算消耗保留；恢复不能偷偷重跑 Problem 或接纳规则。

“什么情况下允许提交”需要另有执行协议。当前 change 编辑依附携带它的接纳提案、初始化有独立入口，都是对提交条件的具体规定；原子性本身推不出这些条件。也不能把“公开”偷换成“已评估且可行”。

### I8：组合后的操作必须只有一个明确含义

多个计划作用于同一事实时，必须由已声明的顺序、合并代数或仲裁规则解释；不能靠实现偶然的遍历顺序决定结果，也不能静默丢掉一个写者。

**预测：** 不等价的替换不能无说明地合并；相同计划可以按明确规则幂等去重；含义有歧义时必须拒绝，或进入预先声明的解析流程。

这不推出“所有 append/replace 组合都必须拒绝”，也不推出必须使用某一种异常码。当前未提供显式有序组合时采用拒绝，是满足本条的一项保守策略。

### I9：存活由使用声明决定，不能由某个局部关系单方面决定

移除一种成员关系只解除该关系；候选是否可回收取决于仍有效的成员、任务、历史窗口和显式保留声明。派生来源与存活权不是同一件事。

**预测：** 一个 Unit 淘汰 x，不能删除另一个 Unit 仍使用的版本；删除父视图不自动删除后代；物理回收要等相关提交完成。只有手握一个旧 Ref 字符串，不等于获得无限期保留权。

保留多久、是否启用 GC、窗口大小和清理频率是资源政策，不是本条能推出的常量。

## 三、先检验用户指出的五个例子

### 1. “具名 inject 只开放 survivor 和 pool_maintenance”

I6、I7 能推出：需要有权限、目标前提、计划收集器和提交归属的写入口。

**推不出具体这两个回调名。** 当前实现的 `_require_writer` 明确检查这两种 mode，属于已经接通的入口清单。未来第三个入口若提供同样的授权和提交条件，原则上可以开放。

归类：不变量要求 + 当前支持边界。不能把白名单本身称为核心定律。

### 2. “chosen 规则内禁止 inject”

给定 chosen 的公开定义是纯 Pool→Pool 查询，I6 可以直接推出不能收集或发布成员写计划。否则外层对规则进行组合、重试或重复调用时，调用次数会变成业务写入次数。

归类：语义定义的直接后果。将来可以另设计“选择并提交”的效果操作，但那不是同一个纯查询契约。

### 3. “append/replace 同目标冲突拒绝”

给旧集合 [a]，append [c] 与 replace [b]：前者先执行得到 [b]，后者先执行得到 [b,c]。I8 推出不能在未说明顺序时随便选一个。

**推不出永远拒绝。** 如果公开计划明确表达顺序，并验证授权、目标前提和原子提交，两种结果都可以是合法的用户意图。当前只支持某些脱离计划、未提供这类顺序表达，所以拒绝。

归类：必要的无歧义要求 + 当前冲突政策。

### 4. “MOEA/D members 不是统一方向评分”

额外算法前提是：不同槽位对应不同方向/比较参数。再用 I3、I5，即可推出这些槽位的标量值不能自动当作统一排名。

归类：算法契约在通用不变量下的实例化。Pool 不必认识 MOEA/D，但调用者须知道自己比较的是什么。

### 5. “绑定不自动给裸 Adapter 加池任务”

I2 推出数据来源绑定与任务创建不是同一效果。I6 要求初始化、精修或竞争等行为由明确的任务/调用声明触发。

归类：职责分离的直接后果。将来装配糖可以显式同时生成绑定与任务，但必须说明它做了两件事，不能靠属性赋值悄悄运行算法。

## 四、其余规则的推导账本

以下按语义义务分组核对，不按 AGENTS.md 的分号或源码行计数。标记含义：

- **D**：在上述模型内能推出必要语义。
- **A**：还需要所属算法/执行协议的前提。
- **P**：不变量允许多个合法方案；当前具体行为仍是政策/支持范围。

1. **D / I1**：同值不同身份、同 token 不同版本不能自动合并；读取保留身份，新对象与对象修订不同。
2. **D / I1、I4**：不能跨 pool/scope 直接解释一个地址；存储位置、摘要、版本和权威身份必须相容。具体 Snapshot 格式不是由此唯一推出。
3. **D / I2、I3**：Pool、Unit 和 Authority 不维护同一事实的多份独立可写真相；Unit 可保留自己负责的工作数组。
4. **D / I3、I5**：accepted 历史、当前成员、最终精修结果是不同关系；保留根也不能代替成员顺序。
5. **D / I1、I4**：部分接纳必须回到原提案坐标；同值匹配、仅按 token 追未来版本都不充分。
6. **D / I5**：ProposalRepair 处理内容变化，BatchDisposition 处理保留哪些原行；二者不能互代。Unit 不变量的重算/拒绝还需算法定义。
7. **D / I3、I5**：普通集合存成员不代表拥有某一时刻的选择评分；跨 root 合并要声明统一解释，不能自动拼不同投影分数。
8. **A / I5**：Feasible 接纳按 raw violation 判断，来自“可行”的 Problem 定义；不能推出所有接纳策略都必须拒绝不可行解。
9. **D / I4、I7**：目标同名重建或修订漂移不能静默当旧目标继续写；需要重新建立前提或明确失败。
10. **D / I6**：创建空草稿/选择视图不能自动产生公共集合、创建 Unit 或启动 Adapter。
11. **P / I3、I8**：append 对新增引用去重、replace 保留重数、merge/intersection 的顺序规则，属于这些操作的公开定义，不能从“池是集合”猜出。
12. **P / I4、I6**：调用结束即让临时 Pool 失效，是当前授权生命周期方案。冻结值对象可以另行设计为长生命周期，须显式携带合法范围。
13. **P / I6、I8**：同 scope 同名草稿共享一份计划、自动收集编辑等是语法方案；其他显式计划表达也可以满足不变量。
14. **A / I3**：survivor 不允许重复原位置，需要该选择位置“保留成员”的契约；一般抽样可以有放回，普通子池也可保留重复引用。
15. **D / I2、I4**：working_pool 绑定不暗中改变 Unit 成员，不隐含 task；继承最近区域是当前选定的来源解析政策。
16. **P / I6、I7**：携带编辑的至少一条提案被接纳才应用该编辑，是当前 change 的提交协议；并非所有可能的维护事务都必须依附提案。
17. **D / I7**：编辑、成员选择与输出不能分别成功；准备 manifest 后继续修改其内容会破坏已准备的发布事实。
18. **D / I7**：失败不抹掉已发生的求值/预算；恢复从证据对账，不再随机选择输入、重做接纳或重跑算法。
19. **A / I2、I4、I7**：任务游标、RNG、原始输入和子算法状态须共同恢复；具体 distribution/count/default/error/wait 规则是编排政策。
20. **D / I2、I6**：有 Unit 不自动说明支持 initialize/refine/compete；调度和资源授权不能由 Pool 读取偷偷发生。
21. **D / I4**：all/random 不隐含阶段屏障；是否等待属于任务/编排。选择计划的解析时机仍须由执行协议指定。
22. **D / I2、I3**：created_by 指创建视图的所有者，不能用算法类型或候选生产者替代具体实例身份。
23. **D / I3、I4、I5**：投影视图要保留源解释及其修订；不能把方向标量写回母池原目标，也不能无声明地重复应用继承投影。
24. **A / I5**：只投影目标而没有对应梯度变换时不能宣称同一梯度任务；路径代价也不能当作目标投影。这是领域数学前提，不是池特例。
25. **D / I3、I9**：parent/ancestors 是来源，不是集合包含或级联删除权；删除父级不撤销后代独立的保留关系。
26. **D / I1、I4**：父子关系必须基于稳定身份，名字前缀不能证明关系；轻量元数据也不能证明任意外部历史没有伪造。
27. **D / I9**：一个算法局部淘汰不等于全局可回收；池容量、Unit 容量、任务取解配额不能混成一个 population_size。
28. **P / I9**：默认是否 GC、窗口长度和回收频率是资源政策；提交后再执行不可逆删除来自 I7、I9。
29. **A / I2、I7**：成员扩展字段由其所有者给出维护规则；member_fields/on_members_changed 是当前落实方式，不是只能这样写的定律。
30. **D / I4、I5**：本次调用的 individual 或 StrategyTask 不能从旧全局值猜；每条反馈必须回到原提案和解释。
31. **P / I4、I7**：当前一个子批不混池输入和新提案，源于游标对账方式；若逐行明确来源和结算，可以设计安全混批，核心不禁止。
32. **P / I2、I7**：独立无送评维护尚未开放，是提交/进度协议的支持边界；原子成员修改不在数学上依赖一次新求值。
33. **D / I4、I6**：跨 Case/运行不能拿本地引用直接扩大读取权；正式传输、授权及接收方身份映射要显式。不能据此声称现有 Pool 已实现跨 Case 共享。
34. **D / I1、I5、I7**：调用内已脱离的值可以用于本次计算，但不自动成为跨调用的持久读取收据；候选阶段合批不应改变各行身份和来源。

## 五、真正没有唯一压掉的 8 类选择

这些不是再补 8 条“不变量”，而是应当移出核心介绍、放进配置或支持矩阵的内容。

1. **哪些回调拥有写入口。** 当前是 survivor/maintenance；根本要求是授权、计划收集与提交归属。此处最值得用共同机制统一，避免每增加一个入口都加白名单。
2. **冲突如何解析。** 当前拒绝某些 append/replace 组合；根本要求是含义唯一。若增加顺序组合，需明确执行模型，而非去掉检查。
3. **集合操作与语法默认。** 去重、重数、稳定顺序、同名草稿共享等，要用少量一致的方法定义说明，不能让用户猜。
4. **算法成员的合法性。** 某种 Unit 的成员/槽位能否重复、方向是否独立，来自算法，而非 Pool。应归入相应 Unit/Adapter 契约。
5. **取解与调度默认。** 最近区域、默认配额、分发方式、不足时 error/wait、请求解析时机等，属于编排配置。
6. **重评与证据复用政策。** 根本要求是有资格的版本/语义关联；当前保守重评不是唯一合法实现。
7. **临时对象与语法的生命周期。** 当前调用内 handle、关闭后失效、自动收集计划等是 API 设计方案；它们不应被混称为存储模型的本质。
8. **提交入口的支持范围。** 无送评维护、混合来源批次等目前有限制。应说明缺的是何种结算/提交能力，不能暗示这些行为违反 Pool 的根本逻辑。

其中 1、2、8 是最值得继续消化的实现复杂度；3、5、7 主要是 API 一致性和文档分层；4 必须保留为算法知识；6 是有成本取舍的运行政策。不能为了让“不变量能推出一切”而把它们全删掉。

## 六、给新手的盲测题，而不是让作者自评

只提供第二节，不先提供当前 API 白名单，请读者回答：

1. 两个算法能否共用同一解，而保留不同排名？——能，内容共享不等于决定权共享，I1–I3。
2. 一个算法删掉成员，能否顺便删除另一个算法还用的版本？——不能，I9。
3. 刚创建的子池，能否让其他调用在本步提交前看到一半？——不能，I7。
4. 冻结目标后来同名重建，旧计划能否静默作用到新池？——不能，I1、I4。
5. 精英选择能否直接拼两个方向的标量分数？——需先声明统一比较含义，I5。
6. 纯选择规则能否顺手给精英池写成员？——不能隐含效果，I6；可显式交回写计划。
7. 显式声明 replace 后 append 的顺序，理论上能否安全执行？——可以满足不变量，但当前 API 仍可能不支持，I8。
8. 不重新求值，只整理已有精英成员，理论上是否必然非法？——不必然；需明确授权与提交条件，I6、I7。当前未开放不能回答成理论禁止。

如果读者能答对前六题，却答不出 survivor/maintenance 的白名单，这不表示不变量失败：白名单本来就不是可推导事实。若他们经常在“已提交就必然可行”“投影视图自带统一评分”“删除父级会删除后代”等问题上出错，说明核心说明仍未传递成功。
