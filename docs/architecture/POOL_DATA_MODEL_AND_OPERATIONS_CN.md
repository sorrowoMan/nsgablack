## 1. 这次要统一什么

**用户面对的 Pool 表示一批具有明确身份、顺序和比较含义的解。**

选择规则直接接收 Pool，返回允许留下来的 Pool。
取全部、抽样、过滤、排序、合并后的结果，继续使用同一个 Pool 接口。
用户不必为了组合这些操作，反复在数组、Selection、子池名称与引用列表之间转换。

```python
# 概念示意，尚未实现。
def choose(pool: Pool) -> Pool:
    return pareto_select(pool, count=100)


offered = parents.concat(offspring)
survivors = choose(offered)
```

这里选择的是已有版本。规则返回后，由实际所属 Adapter 把结果应用到自己的结构。
返回 Pool 不意味着自动创建具名子池、重新存储候选、调用 evaluate 或修改所有引用者。

统一的范围是解集合接口。指标仍返回数值，分组返回多个 Pool，成员更新返回计划；
不要求所有函数无论用途都返回一个 Pool。

## 2. Pool 与当前 SolutionPool 的关系

当前 `core/state/solution_pool.py::SolutionPool` 负责运行内的候选记录、Snapshot 索引、
具名集合、输入游标、事务、checkpoint 和保留声明。
当前 `ChangePool/ChangeSelection` 提供调用内访问和临时引用选择。

建议的公开 Pool 是这些已有能力上统一的解集合视图，不再创建另一套候选仓库。

- 所有 Pool 复用当前运行的 SolutionPool 与 SnapshotStore。
- 候选值、原始反馈和候选版本仍由已有记录保存。
- Pool 主要保存精确引用及其解释信息。
- 一个变量赋值、一次 sample 或一次 choose 不新增持久候选记录。
- 具名集合的成员发布继续进入已有 Pool manifest 和 Authority Snapshot。

同一个 Python 接口可以表示母池读取结果、具名子池快照或临时筛选结果。
是否具名、是否有更新目标、是否允许写入，必须由内部绑定与作用域明确记录。

## 3. 最小数据结构

以下是概念字段，不要求照此增加七种公开类型：

```text
Pool
  storage_scope       同一运行、存储作用域及其访问能力
  refs                有序的精确 SolutionRef 序列
  captured_at         捕获成员时的逻辑时点
  binding             可选：直接绑定的具名池身份与 revision
  comparison          当前允许使用的冻结比较含义
  selection_positions 可选：对当前选择请求的原始位置映射
  access_scope        本次调用的来源限制、合法时段与更新权限
```

这些字段大多已有底层对应物，应该复用而不是建立第二份权威。

### 3.1 refs：有序序列，不是天然去重集合

一个 Pool 可以是：

```text
[ref_a, ref_b, ref_a]
```

位置 0 和 2 可以属于不同槽位，即使它们引用同一个候选版本。
因此必须同时区分：候选内容版本、候选在本次 Pool 中的位置。

相同数值不能判断身份相同；同 token 也不能替代完整版本引用。
取值时继续按给定顺序对齐，不能在中间阶段自动去重。

### 3.2 binding：具名快照与临时结果

直接读取一个具名池时，binding 保存冻结的 name/view_id/revision 等已有描述符。
其他代码随后更新同名池，不改变已经取得的 Pool。
重新从存储入口取用，才得到新的已提交成员。

sample/filter/take/choose 产生的匿名结果不继承“可以替换原具名池”的目标绑定。
它可以保留来源说明，但来源说明不能冒充该结果自己的持久身份。
`all()` 返回等价完整视图时可以保留原绑定。

更新使用明确目标和预期 revision；不根据一个旧名称悄悄改写后来重建的新池。

### 3.3 comparison：解相同，不意味着分数含义相同

Pool 不在候选公共字段上保存一份供所有算法改写的 rank、crowding 或方向分数。
这些值属于明确的比较输入、当前请求或所属 Unit。

比较描述至少要能区分：

- 原 Problem 的目标顺序、约束含义与可比较的评估语义。
- 当前读取的是 raw 反馈还是某个明确的 selection/task 反馈。
- 是否带投影，以及冻结的方法、权重、参考点。

第一版不要求新增通用语义注册中心，但不能仅靠目标列数相同就断言可以比较。
无法证明来源可比时，应拒绝混排，或要求调用者明确指定共同比较输入。

**当前实现还存在一个必须保护的区别：**
ObjectiveProjection.apply 使用 feedback.objectives，其中可能已有 Bias；
池历史 read_raw_feedback 只返回 raw。
因此“在 raw 上再套方向权重”不自动等于“原任务含 Bias 的比较结果”。

若要提供原任务比较反馈，必须沿已有事件/收据读取或绑定已经记录的对齐结果；
不能重新运行有状态 Bias，也不能缺少数据时静默退回 raw。
第一版可以先提供 raw 与明确标注的 raw 投影，任务完整比较在证据充分时开放。

### 3.4 selection_positions：把选择结果准确交回算法

选择请求给出 N 个位置时，内部可以绑定局部坐标 0…N-1。
规则通过 take/filter/sort 等操作返回 Pool，仍须保留对应的原始位置映射。
即使两个输入位置的 SolutionRef 完全相同，也不能因此猜它们的槽位状态相同。

这份映射只服务本次调用，不为每次选解创建新的持久候选身份。
这样用户返回 Pool，内部仍可转换为现有 Adapter 所需的准确局部索引。

例如 parents.concat(offspring) 先形成完整 offered，框架在进入留存规则前为该次请求统一编号。
不能拼接两个都从 0 编号的局部映射，然后假定它们仍唯一。
规则内部的 take/filter/sort 继承这个请求的坐标；merge 去重时保留首次出现位置的映射。

### 3.5 生命周期、空池与大值

临时 Pool 受所属外层选择/变化/维护请求的作用域保护，不自动成为永久保留根。
框架先验证规则返回的 Pool、提取位置映射或接收成员计划，再关闭作用域；不能让一次合法返回立刻失效。
作用域关闭后，用户保留的临时 Pool 不再允许继续寻址。读取期间的存活由既有受控步骤/读作用域保证，
不能把普通 Python 引用当成跨提交的 GC 保留声明。
跨调用需要保存时，使用具名成员提交或现有任务输入/checkpoint。
候选数组和反馈按实际读取加载；只读视图不允许原位改写候选记录。

空 Pool 仍保留运行作用域、比较框架和已知 schema。
空选择不需要生成候选来补齐。读取空数值矩阵时可以使用已知维度；
维度未知则明确报告缺少 schema，不能凭空猜维度或触发 Unit 构建。

## 4. all 的唯一含义

```python
# 建议 API。
pool.all() -> Pool
```

**返回当前 Pool 视图中的全部成员。**

```python
small = main.filter(predicate)
same_small = small.all()
```

same_small 仍是过滤后的成员，不能跳回母池或扩大任务权限。
对不可变冻结视图，all 可以直接返回自身或轻量等价视图，不复制候选大值。

它不负责刷新具名池、不展开全部子池、不清空选择条件。
已有 `subpools.all(adapter)` 继续表示“选择该实例创建的子池视图”的装配计划；
那是在选池，不是取一个池里的全部解。

## 5. 基础操作：返回 Pool 的只读操作

以下签名是统一接口的建议，不是当前可直接运行的 API。

### 5.1 指定位置、抽样与过滤

```python
pool.take(indices)                              -> Pool
pool.sample(count, *, rng, replace=False)        -> Pool
pool.filter(predicate)                          -> Pool
pool.sort(key, *, reverse=False)                -> Pool
pool.groups(size)                               -> tuple[Pool, ...]
```

- take 使用当前视图的局部位置，明确重排或重复时保留映射。
- sample 默认无放回抽取位置；count 大于可用位置时报错，不自动补新解。
- replace=True 明确表示允许重复抽取，用于需要重复父代等场景。
- filter 的批量 predicate 接收只读 Pool，返回对齐的一维 bool mask；不自动猜成逐元素函数。
- sort 的 key 接收只读 Pool，返回对齐的有限数值键，完整并列保持当前顺序。
- groups 按当前顺序切分并保留尾组；只返回临时 Pool，不创建具名子池或 Unit。

这些操作不调用 Problem，不产生新候选 token，不改变源池成员。

### 5.2 合并与集合关系

```python
pool.concat(other, *, comparison=None)          -> Pool
pool.merge(other, *, comparison=None)           -> Pool
pool.intersection(other)                        -> Pool
pool.difference(other)                          -> Pool
```

concat 拼接位置，完整保留两侧顺序与重数：

```text
[a, b] concat [a, c] = [a, b, a, c]
```

merge 保持当前 ChangeSelection.merge 的含义：精确引用的有序并集，保留首次出现：

```text
[a, b] merge [a, c] = [a, b, c]
```

两者不能同名后再按算法类型改变默认行为。
保留槽位或方向任务坐标时使用 concat；整理候选档案时可以明确使用 merge。

intersection/difference 按精确引用判断是否出现，保留左侧顺序与符合条件的重数；
不是把右侧每个重复项逐个配对扣除。
这两种身份运算不混用右侧分数，结果保留左侧比较框架；双方仍须具有合法的共同访问作用域。
跨运行、跨存储或不同授权作用域的合并，不能凭同名或同值放行。

### 5.3 不同方向怎样合并

第一版每个 Pool 只携带一个有效比较框架，不新增多段 Pool 结构。
默认 concat/merge 要求比较框架一致；不能把两个方向各自的一列标量拿来全局排序。

确实要回到共同原始目标时，可以设计为显式指定：

```python
# 建议 API；要求两侧原始目标/约束语义可比较。
combined = direction_a.concat(direction_b, comparison="raw")
```

这明确放弃原方向分数，结果只使用共同 raw 比较框架。
默认相同框架不要求 Adapter 实例相同；但维度相同也不足以证明框架相同。
按各个方向分别处理时，继续使用多个 Pool 或已有 subpools/PoolTask 选择计划。
不把100个不同方向压成一列含义混杂的“统一分数”。

## 6. 选择：Pool 输入、Pool 输出

### 6.1 规则与调用

```python
# 建议的用户规则形状。
def choose(pool: Pool) -> Pool:
    return pareto_select(pool, count=100)
```

需要统一传递数量、随机性或参考池时，可由一个 select 门面交给实际规则：

```python
# 建议 API；by 是明确的普通函数/现有可恢复组件。
result = pool.select(
    100, by=pareto_selection, rng=rng,
)

result = pool.select(
    20, by=diversity_selection, reference=elite, rng=rng,
)
```

直接调用 choose 和门面 select 表达同一类操作，不再建立另一套选择执行循环。
普通规则可按现有绑定机制记录身份；有状态规则使用已有显式 codec，随机性来自所属 Adapter。

### 6.2 留存规则不能偷偷生成或引入解

作为生存/留存选择时，返回值必须：

- 来自本次输入 Pool 的位置子集或重排。
- 保持精确候选版本、同一作用域和比较框架。
- 默认选择唯一的原始输入位置，不重复使用同一个位置；输入中原本不同槽位可以指向相同引用。
- 空结果仍保留合法作用域和框架，不自动生成随机候选。

要加入另一个池，先明确 concat/merge，再进行选择。
要产生新解，走候选变化与正式提案流程。
不能通过手工构造一个 Pool 绕过来源、修复、评估或接纳。

父代抽样可以允许重复，其 purpose 与生存选择不同。
Adapter 的既有 purpose、结构约束和数量限制继续保留，不把所有选择压成一个没有语义的 choose。

### 6.3 Pareto 是具体留存规则

- 第一前沿规则：只保留第一非支配层，数量不保证达到指定容量。
- 环境选择规则：按约束支配层依次取用，最后一层按明确的拥挤度等准则裁剪。
- 精英规则：由调用方明确选择目标和、单目标、Pareto 或其他标准。

这些都可以使用 Pool → Pool 的接口。
普通多列 sort 是词典序，不等于 Pareto；不能为统一外观偷偷替换数学规则。
拥挤度的边界无穷值由 Pareto 选择规则处理，不塞进要求有限键的普通 sort。

## 7. 创建与成员更新：明确目标和提交点

### 7.1 具名池的管理入口

存储管理仍由现有 solver.solution_pool 及控制面承担。
未来门面可以提供如下返回 Pool 的读法；名称是建议，当前尚不存在：

```python
store.main_pool(*, stage="accepted", region="main") -> Pool
store.get_pool(name)                               -> Pool
store.create_pool(name, *, members)                 -> Pool
store.drop_pool(name)                               -> None
```

store 仅代表当前 SolutionPool 的访问门面，不是新的服务、数据库或注册中心。
main_pool 与 get_pool 分开，避免母池区域和恰好叫 main 的普通子池混名。

get/main 返回当前允许读取的已提交冻结视图。
create/drop 是有副作用的受控管理操作，放在初始化或明确的控制面位置。
第一版公开 create 可先限于步骤外初始化；运行内动态创建继续复用既有正式内部路径与输出计划。
不允许普通只读函数根据调用位置自动把同一个 create 猜成“立即创建”或“返回计划”。

当前可用的是 create_subpool/get相关成员接口；它们与上述建议门面的返回类型不同，迁移时必须明示。

### 7.2 更新已有目标

```python
# 建议的具名 Pool 方法，均返回现有 PoolEdit 计划。
target.replace_members(result_pool)                  -> PoolEdit
target.update_members(*, add=pool_a, remove=pool_b)   -> PoolEdit
target.remove_members(result_pool)                   -> PoolEdit
```

这些方法针对明确具名、可更新的普通集合。
匿名选择结果没有自动更新父池的目标绑定，不能对它调用 replace 就修改来源。
已有算法 population/方向视图仍由所属 Adapter 发布，不变成任意规则的可写集合。
母池的候选记录索引也不是可以普通 replace 清空的种群容器。

计划通过冻结目标身份/revision 校验，随原搜索步骤发布。
同目标冲突、append/replace 冲突继续明确拒绝。
删除成员只解除该集合持有，不删除其他池、Unit 或历史仍引用的候选。

同一步中的普通池维护不额外计代或求值。
无提案、零接纳或整个步骤未提交时，不单独制造一次维护提交；独立维护事务仍暂缓。

## 8. 读数、比较和新候选生成

### 8.1 数据与只读分析

```python
pool.refs                         # 有序精确引用
len(pool)                         # 成员位置数，不是去重候选数
pool.values                       # 按需加载的只读数值矩阵
pool.candidates                   # 保留语义 metadata 的候选
pool.raw_feedback()               # 原始目标和约束，不重跑求值
```

HV、IGD、距离、多样性等函数可以接收 Pool，返回标量或逐成员对齐的只读结果。
只有用评分实际挑出成员时，选择函数才返回 Pool。
参考对象必须明确传入另一个 Pool 或 UnitView；同一个解的“新颖程度”不是全局固定字段。

不需要给每个指标都添加一个 Pool 方法；需要的是输入、引用位置和比较含义一致。

### 8.2 新候选不是选择旧引用

变异和交叉产生新的提案值与来源；当前 ChangeResult、未来批量返回与 CandidateBatch 已有各自职责。
普通函数不能把新数组伪装成已经存在的 SolutionRef。
框架登记提案、repair、正式评估、硬接纳并提交后，才形成其他算法可读取的新版本。

这次统一先覆盖已有候选的集合视图和留存选择，不承诺所有变化函数已经可以返回公开候选 Pool。
后续如增加提案集合门面，也必须复用同一存储与身份流程，明确未评估/未提交状态，不另建一套池。

### 8.3 环境选择中的后代 Pool 从哪里来

parents.concat(offspring) 中的 offspring，不是普通函数自行包装的未评估数组。
建议由控制面在所属 Adapter 本批 update/维护请求中，将已硬接纳、尚未公开的精确引用与反馈，
授权为本次受限只读 Pool。父代和后代在同一外层请求作用域中交给留存规则。

这复用接口手册中的 accepted 授权设计：权限贯穿读取、选择返回、成员计划和提交校验。
通用 get/main 仍只枚举已公开数据，不因该授权放开任意 pending。
未送评、未通过硬接纳的提案不属于这个 offspring Pool，实际求值与接纳也不因此重复执行。
若按原算法 selection 反馈比较，应显式交付该算法既有对齐反馈与比较含义，不能自动换成 raw。

## 9. 与 Unit、Adapter 的连接

- Pool 决定“这一批具体版本有哪些”，不保存供所有算法共同写的排名。
- Unit 保存算法成员、槽位、路径、温度、区域及其派生状态。
- 选择规则决定输入中留下哪些位置。
- Adapter 决定何时调用规则、如何应用结果，以及需要哪些额外结构校验。

GA 的环境选择可把父代与后代 Pool 交给规则，再按位置映射更新 PopulationUnit。
成员扩展字段继续经过既有 PopulationChange/on_members_changed，不由通用 Pool 猜维护方式。
MOEA/D 槽位与方向规则、SA 的接受规则、图搜索的路径和有限差分的配对几何都不能因返回 Pool 而省略。

Pool 选择结果不自动构建 Unit；未启用算法仍按需创建结构。
不要求每个 Adapter 使用固定四阶段循环，也不保证同一选择规则适用于全部算法。

## 10. 从当前 API 到统一接口

- ChangeSelection 的 refs/values/raw_feedback/take 等，是统一 Pool 视图可复用的现有基础。
- random/where/order_by 可对应用户层 sample/filter/sort；这仍是命名建议，不能在未迁移时混写成现有方法。
- 当前 merge 是精确引用去重；保留该语义，新增 concat 明确承担保留重数的拼接。
- 当前 all 不存在；建议仅提供本视图全部成员的等价 Pool。
- 当前 SelectionRequest 返回索引；未来用户返回 Pool 后，内部通过局部位置映射交回已有索引协议。
- 当前子池管理、PoolEdit、PoolTask、事务、Snapshot、保留和结果交付继续复用。
- Pareto、精英、偏好参考来源与成员维护按接口手册的真实接入状态逐一接通。

第一版不新增自动实时查询、跨运行 Pool 合并、分段比较框架、通用流程语言、求值缓存或永久操作图。
临时 Pool 的来源说明也不自动变成保留所有祖先候选的永久根。

## 11. 用一个具体流程检查结构是否完整

```python
# 完全是目标语法示意，当前不能直接运行。
main = store.main_pool(stage="accepted")
elite = store.get_pool("elite")

offered = main.concat(elite)
survivors = choose(offered)          # Pool -> Pool，具体规则决定留下谁
plan = elite.replace_members(survivors)
```

这段代码只表达引用集合与更新计划，不隐含新的求值或全局删除。
真实算法把成员计划放到既有提交前位置；新后代仍由正式变化与评估链提供。

后续实现至少要证明：

1. all 不扩大范围，过滤后的 all 仍只有过滤结果。
2. 所有只读操作保留精确身份；同值不同身份不合并。
3. concat 保重数，merge 精确去重；重复槽位选择仍映射正确。
4. 已取得的具名快照不自动追新；同名重建和 revision 漂移拒绝更新。
5. 不同方向不能默认混排；显式 raw 合并仍校验目标/约束含义。
6. raw 投影不冒充原任务含 Bias 的选择反馈。
7. choose 不能偷偷引入新候选、外部来源或扩大授权。
8. 空结果、部分接纳、失败回滚、checkpoint、保留回收与既有机制一致。
9. 普通 Pool 视图不创建 Unit，也不复制候选仓库。

## 12. 选择规则内部的比较语义：不新增 compare 原语

从这个设计看，我们正在把优化过程中的对象、关系与操作显式表达。
Pool 统一解集合的交接，Unit 明确算法状态，规则明确比较和留存的含义。
这有利于复用与编排，但 Pool 数据结构本身不包含整个算法。

当前明确不把 compare 或统一比较结果协议列入 Pool 基础操作。
下面只解释选择规则内部需要正确理解哪些含义；用户可以把计算直接写在 choose 中。
只有实际出现多处复用需求时，再抽取普通辅助函数，不要求每个算法实现一套比较接口。

### 12.1 区分语义，不增加四个强制步骤

1. **求值**：Problem 返回这个候选的原始目标和约束。
2. **评分或比较**：在明确的方向、约束优先级、偏好或参考集合下解释结果。
3. **留存或算法接受**：根据比较、数量、Unit 状态和随机性，实际决定使用谁。
4. **应用结果**：由所属 Adapter 更新结构，控制面按原事务提交。

它们可以由普通函数与现有组件表达，不要求再新增四套基类或调度器。
控制面的预算/硬接纳仍独立存在，不等于 SA 的算法接受或种群的生存选择。

### 12.2 比较不一定产生一个总分

设两个可行候选都在最小化费用和时间：

```text
a = [1, 10]
b = [10, 1]
```

Pareto 比较下二者不可比；不可比不同于相同，也不同于必须随机挑一个赢家。
若明确采用 0.8×费用+0.2×时间，a 得 2.8、b 得 8.2，a 较优；
换成 0.2×费用+0.8×时间，优劣反转，但原始目标没有变化。

两解比较至少应能区分更优、更差、按该规则等价、不可比。
“等价”只属于本规则的结果，不表示两个候选身份或内容相同。
若第一版不新增公开比较结果类，也不能在内部把不可比强行压成相等或某个默认总分。

Pareto 第一层的候选可以互不可比，容量不足时再用明确的拥挤度等留存规则裁剪。
模拟退火即使判断新点更差，也可能依据温度和随机性接受。
因此比较函数不能自动承担所有算法的接受决定。

### 12.3 比较对象有不同范围

- **解与解**：支配关系、目标优劣、槽位当前解与 trial 的比较；可以从单元素 Pool 取明确对象。
- **解与一个 Pool**：最近成员距离、相对档案的新颖性、与参考成员的相似度；返回逐候选分数。
- **Pool 整体**：多样性、覆盖或 HV 等统计；通常返回一个值或只读统计结果。
- **结构与结构变化**：涉及温度、路径、邻域、区域等算法状态时仍显式使用 Unit，不强行抹平成 Pool 数组。

解相对 Pool 的分数依赖参考成员、距离及归一化规则；
参考集合变化后分数可以改变，不能把它写成候选永久共享的 novelty/rank 属性。
需要排除候选自身时明确依据引用/身份规则，不按数值相等误删不同候选。

### 12.4 内部结果应保留对应关系

```text
评分：        Pool + 明确参考/规则 → 对齐本次成员位置的分数
两解比较：    明确候选与规则       → 优劣/等价/不可比关系
集合度量：    Pool + 指标参数      → 标量或只读统计
留存选择：    Pool + 规则/必要状态 → Pool
```

评分和比较的结果应知道自己对应哪些候选版本、位置和比较框架。
临时结果可以与本次输入绑定，不需要注册一个全局评分仓库。
要持久化或用于后续任务时，才沿已有视图/事件/收据保存其明确输入与配置。

choose 仍负责“本次留下谁”；rank、crowding、方向分数或距离只是它可以使用的输入。
同样的 Pool → Pool 形状，可以承载不同规则，不能据此假定它们具有相同数学性质。

## 13. 先找正式交接断点，再决定是否需要新原语

这里“不能表达”指无法通过现有普通函数、Pool 操作和正式调用位置完成交付，
必须改 Adapter 源码、绕过身份/评估/事务，或制造无关动作。
它不表示 Python 无法计算该数学公式。

一条需求先尝试组合已有能力；不能仅因为缺少一个同名方法就增加原语。
进一步核对后，下面两项更准确地说是已有 change/selection 的装配接缝，
不是缺少两套新的算法原语。自定义 Adapter.propose/update 已有相应表达能力。

### 13.1 已补齐：一次变化交付多个独立后代

反例：两个父解一次交叉，使用同一个交叉位置产生两个孩子，各自变异后交给正式评估。
N 个父代的读取、配对与数组计算已经能够表达；
原普通 change 只返回一个 candidate，缺少 M 个独立提案的正式交接。
现由 ChangeBatchResult 逐项交付，NSGA-II/III、SPEA2 真实消费；标量位置仍保持单候选约束。

因此要补的是批量提案返回：逐后代身份、来源、数量预算、原始坐标、repair 与部分接纳对齐。
不是新增每种交叉/变异的框架基类，也不是用多个 outputs 冒充多个孩子。
GA 的实际消费位置需要一起接通。

最小返回含义是有序的后代序列，每项携带自己的候选、来源与输出目的地。
同一次交叉可以共享随机位置，但两个孩子仍各自获得提案身份。
例如原始坐标为 0、1、2，只接纳 0、2 时，后续输入与输出按这两个原坐标对齐，
不能把压缩后的第二行误认为原始孩子 1。
共同计算不默认要求共同接纳；有配对几何依赖的算法仍由其原所有者校验。

批次共享的成员替换不应随意挂到第一个孩子上，否则它会由这个孩子的接纳偶然触发。
真正依赖整批反馈的计划交给反馈后的决策位置；逐后代目的地仍逐项交付。
输出数量也须服从实际消费者的声明，不能把多出的孩子静默丢弃。

这里有一个 Pool 统一接口不能抹去的边界：
选择、切片和合并使用已有候选版本；change 生成的是新提案。
新提案须先经过控制面的身份绑定与求值流程，不能伪装成已经提交的 Pool 成员。
无需为此再造一个可变候选仓库，也不要求公开每个内部中间对象。

### 13.2 已补齐：新反馈之后的成员决策交接

反例：本轮新后代求值和硬接纳后，普通函数从旧成员与这些后代中选出精英，
把结果与本步算法状态一起发布。

此前自定义 Adapter.update 能完成，但普通 change 的成员计划在评估前计算，
不能自然使用本轮刚形成的已接纳引用与反馈。
要补的是已有步骤中的正式装配位置和受限输入交付，不是新的事务或评估循环。
choose 返回的 Pool/成员计划仍由原所有者应用。
现 GA 的普通 selector 直接接入原生生存位置；五种实际叶 Adapter 另提供每批一次的 pool_maintenance，
使用本消费者已接纳精确引用生成计划，并与旧输出在同一提交点校验和发布。

**先复用已经存在的选择位置。** NSGA-II 的 update 已合并旧成员和新反馈，
调用生存选择一次，再更新 PopulationUnit、对齐引用与发布种群视图。
当前 SelectionRequest 交付矩阵、反馈、purpose、count 与参数；
应优先补精确引用和调用内 Pool/位置映射，并把返回 Pool 转为现有局部索引。
不能保留一次默认选择，再在后面追加一次同义的用户 choose。
现有 survivor/replacement 等用途与各自数量约束仍保留，不统一成任意长度的无语义筛选。

**算法留存与历史档案仍是两份不同的决定。**
GA 为保持有限容量淘汰的孩子，可能仍值得进入历史 Pareto 档案。
因此档案规则不能被自动解释为“复制本轮 survivors”；
它应显式选择已接纳提案、最终成员或其他已授权来源。
两种决定可以复用相同只读输入、规则绑定与 PoolEdit 校验，而不共享同一份选择事实。

**批次档案维护不能挂到任意一次 selector 调用。**
VNS 首次建立基准时不会调用自定义候选 selector；
MOEA/D 的 replacement selector 则会随每个候选、每个竞争槽位多次调用。
把一次档案更新藏在这些回调里，会漏执行或重复执行，也会让冻结的目标 revision 冲突。
需要批次维护时，由真实 update 路径明确调用一次，继续处于原步骤事务中。
是否提供独立 setter 是装配表面的选择，不构成新增维护调度器的理由。

本次静态依据见 [NSGA-II update](../../adapters/nsga2/adapter.py)、
[SelectionRequest](../../adapters/selection.py)、[选择绑定](../../adapters/operations.py)、
[VNS](../../adapters/vns/adapter.py) 与 [MOEA/D](../../adapters/moead/adapter.py)。

### 13.3 当前可组合的需求，不单独提升为原语

- 成对挑父代、交叉池取样、按条件分支：已有取解/位置选择加普通 Python 可以表达。
- Pareto、多样性、禁忌附近判断：计算可写入具体选择或偏好规则；需要复用时提供普通工具。
- 多池成员移动或交换：在同一步对不同目标组合增删/替换计划，不必新增 move/swap 事务。
- 等待足够输入、按阶段启用、重复触发：已有 PoolTask 的不足策略、phases/request_key 与 Router 策略负责。
- 普通子池创建：已有受控 create_subpool 和接纳后 PoolOutput(create=True)，不再新增创建引擎。
- 重复槽位选择：现有 take/局部索引已能保留坐标；统一 Pool 外观时保持这一能力。

一个实际反例是“GA 已求值，从这些解中选 20 个，交给 VNS 精修”。
现有 `PoolTaskSpec(select_callback, count="all", ...)` 已允许回调读取已有反馈，
返回精确引用并冻结为任务输入；筛选本身不求值，不要求先建立一个新的公开精英池。
VNS 起点的正式送评仍由原任务执行，两者不能混称为筛选新增求值。
[已有测试源码](../../tests/test_subpool_tasks.py) 包含 top_twenty 输入选择与任务 checkpoint 续跑。
这里核对的是源码和测试覆盖意图，本轮没有重跑这些测试。

### 13.4 只整理已有解：先明确是否真的需要独立发布

下面两个需求不能混为一谈：

1. 下游拿到筛选后的旧引用：现有任务输入回调与队列已经可以表达。
2. 替换一个既有公开集合，并要求这次替换独立形成与 Authority 同步的持久发布：
   当前普通装配入口未开放这样的独立步骤，属于更强的提交要求。

不能为了把第二种需求列成缺口，给第一种常见交接额外强加独立发布条件。
也不能笼统声称“无提案就不可能创建可读集合”：步骤外初始化可以创建普通子池，
正常 rejected/idle 尝试还可按现有 reject_attempt 规则保留只含已公开引用的新任务输入集合。
这些队列可读与完整 checkpoint 保存，不等于既有 Authority destination manifest 已经更新。
它们也不使替换既有公开集合自动变成独立的持久提交。

若今后确有算法要求第二种语义，再设计正式调用位置与所有权；
复用已有池发布和 Authority 事务，不增加 move/swap 各自的事务体系。
本轮仍不扩展独立维护提交，也不通过制造无意义提案或求值来模拟它。

### 13.5 后续设计的判据

每项候选原语必须附一个最小场景，并指出：

1. 现有哪一步已经可以表达。
2. 正式输入/输出或生命周期在哪里断开。
3. 为什么已有操作与普通函数组合仍不能完成。
4. 补齐后复用了哪些现有身份、状态、事务和恢复机制。

先用批量后代与反馈后留存两个反例验证统一 Pool，再根据真实断点扩展。
统一命名、参数别名和更短写法属于易用性改进，应与新增表达能力分开记录。

最小闭环应只要求这条链可装配：

```text
读取两个来源池 → 一次 change 交回多个独立后代
→ 原控制面完成修复、求值与部分接纳
→ 原有选择位置决定算法成员
→ 如有档案需求，明确用本批反馈形成成员计划
→ 原步骤一起提交
```

若这条链只需扩展 change 的返回基数、selection 的精确输入与真实消费位置，
就没有理由提前增加 compare、join、通用流程图或新的池运行器。

本轮实现、测试与真实运行已同步接口手册和 Project README；其余未落地签名仍保留设计标识。
没有运行性能 benchmark，也不由这些行为验证推断算法数学性质。

## 14. 可表达之后：以完整使用任务检查是否好用

本节是 2026-10-20 的后续使用模型讨论，**没有实施本节的新绑定形状，也未运行新测试**。
第 13 节补齐了交付能力，但“能用普通 Python 拼出来”不能作为常见任务已经好用的判据。
应检查用户从声明来源、选择输入、执行算法到取用结果，是否一直使用同一套可预测的含义。
不增加 compare 原语，也不为每一种筛选方式建立新组件。

### 14.1 已有功能在完整流程中的真实摩擦

本次静态核对发现：

- `PoolTaskSpec.select/output` 的字符串会加任务命名空间；ChangePool.subpool、PoolOutput、
  MixedPoolParentSelector 使用精确公开名。同一个字符串在不同入口可能指向不同对象。
- PoolTask 回调接收 control/context、返回引用；普通 choose 接收并返回 Pool；
  parent selector 返回引用；subpools.all 返回延迟的视图选择计划。
  底层角色不同是合理的，但普通装配仍要求用户自行在这些形态之间转换。
- PoolTask.count 对普通来源按 worker 配额计算，对视图来源按每视图起点数计算；
  subpools.random 取视图，Pool.sample 取解。仅把参数名改短，不能消除数量层级的歧义。
- output="refined" 收集硬接纳试探解；最终被算法选中的结果另有视图。
  只看 refined 名称无法判断拿到的是轨迹中的试探点，还是每次精修的最终选择。
- 同一 VNS 实例的不同 request 会保留各自结果视图；只按 created_by 的 all 会选中历史轮次。
  来源查询能做到枚举，不等于它足以表达本次输入依赖。
- selector 的 offered Pool 带本次选择反馈；maintenance 的 accepted Pool 当前只有引用与 raw，
  选择反馈另在 request.objectives/violations。同为公开 Pool，用户换调用位置后仍需换读取方式。
- GA→VNS 示例按成员数乘 local_steps 推阶段长度；MOEA/D 嵌套示例还读取
  pool_tasks["coarse:0"]["status"]。用户正在手工维护与实际任务进度重复的一份判断。

对应源码见 [PoolTask](../../adapters/pool_tasks.py)、[池调用视图](../../adapters/change_pool.py)、
[父代选择](../../adapters/parent_selection.py)、[批次维护](../../adapters/pool_maintenance.py)，
以及 [GA→VNS 装配](../../examples/cases/assembled_ga_vns/cases/hybrid_search/adapter/composition.py)
和 [MOEA/D 嵌套装配](../../examples/cases/assembled_moead_nested/cases/direction_refinement/adapter/composition.py)。

这些是使用成本，并不等于上述每个实现都是错误，也不能据此声称所有算法必须使用同一流程。

### 14.2 普通装配从“查某实例创建过什么”改为“引用所需输出”

普通用户应能直接表达：

```text
GA 的当前成员
  → 按明确规则取 20 个起点
  → 每个起点执行一次 VNS 任务
  → 取这些任务最终选中的解
  → 交回 GA 自己竞争
```

这里不要求用户先查 created_by，再拼内部池名，再判断哪些视图属于本轮。
更合适的用户层连接对象是“一个明确的输出引用”：

- 由哪个已装配算法或任务提供。
- 取哪种输出：当前成员、方向视图、硬接纳试探、最终选择等。
- 绑定哪次任务，或者在明确触发时捕获哪个已提交版本。

这是对现有池与任务数据的引用，不是另建候选仓库、资源授权或发布事务。
装配时可以引用尚未产生的合法输出；实际输入在原请求开始时解析、冻结，恢复后不重选。
来源身份与权限仍由原装配和任务边界校验，引用一个输出不授予整个父池或兄弟任务访问权。

created_by、kind、parent 与逻辑时间继续用于发现、检查和高级筛选。
常规连接不应要求用户反复手填这些底层字段。
具体引用语法尚未确定，不先增加一套查询 DSL 或大量必填参数。

### 14.3 单个 Pool、多视图与数量：含义固定，配额不随入口漂移

单个 Pool 表示一批解；一组带不同投影的视图仍分别保留各自解释。
用户应能直接区分“在 GA 当前种群挑 20 个解”与“在 MOEA/D 挑 20 个方向，各取一个起点”。
不能因为两者都写 20，就让程序从引用对象的内部类型重新解释数量。

目标要求：

- 选择范围清楚后，all 只取该范围，不反向放大到所有历史输出。
- 选中工作量与 worker 数量分开；20 个起点增加到 4 个 worker，仍是分发这 20 个起点。
- 确需每个 worker 独立取得 20 个起点时显式表达该分配政策。
- 每个方向取几个起点，与选几个方向是两个数量；默认值可省略，但必须能被解释和检查。
- 同一候选在两个方向出现仍是两个有各自比较含义的任务，不能按引用全局去重。
- 取解默认保留源池成员；任务游标推进、成员淘汰和候选物理回收继续是不同动作。

这不要求 sample 与 top 在不足时强制同样行为。
sample 的“准确抽取 N 个”和 top 的“最多保留 N 个”可以不同，但数量与不足政策应从意图上清楚。
缺少来源、来源未就绪、已就绪但为空、数量不足，应报告不同状态，不能都退回随机初始化。

### 14.4 一次任务的结果要能直接交给下一次任务

以两轮粗细精修为例：

```text
MOEA/D 的方向输出
  → 本轮 coarse 任务的最终选择输出
  → 本轮 fine 任务的最终选择输出
  → MOEA/D 当前规则下的返回竞争
```

下一轮 coarse 再次运行时，fine 应引用这次调用的输出，而不是重新扫描 coarse 全部历史。
不能靠结果名字前缀或“最新 100 条”猜批次；方向异步完成，完成时间不等于批次身份。
历史结果可以保留，保留历史不应悄悄增加当前任务数量。

当前成员输出是持续更新的视图；有限精修任务的最终输出则有明确完成条件。
输入“已有提交帧可读取”与“上游整批任务已完成”须分别声明，不能统一成模糊的 ready。
调度仍复用 Router 的阶段、完成状态与原任务进度，不另造运行循环。
用户表达依赖时，不必再手算成员数×local_steps 或解析 role:worker 内部状态键。

默认取哪种结果应服从明确的输入模式。
普通“接续精修”应容易拿到最终选择；要拿全部硬接纳试探也应可明确指定。
不能只把两种产物都叫 output，让用户读源码才能判断。

### 14.5 同一解集合接口，应在不同调用位置保持一致体验

变化、父代选择、生存选择、档案维护可以有各自的算法请求，
但来源引用、候选访问、精确身份与反馈读取应尽量使用同一套公开操作。

已交付的选择反馈应随相应只读成员视图对齐，而不是有时读 Pool.objectives、有时读 request 数组。
未评估池须明确其反馈缺失状态；不能填零、借用旧反馈或为了读取隐式重新 evaluate。
raw 与任务比较反馈的区别仍保留，不能为统一外观重跑 Bias 或猜测投影。
跨不同方向合并不自动变成一份可混排的分数。

一个来源或目标引用应贯穿装配、函数读取与访问声明。
内部字符串、owner 路径、view_id/revision、token 和 Snapshot 仍负责正确性，
普通使用不要求用户手工构造它们。需要诊断、恢复或自定义组件时才展开这些细节。

### 14.6 用户应能在运行前后解释一次装配

复用已有 Doctor、运行图和任务状态，展示当前能确定的事实：

```text
来源：MOEA/D 本轮方向输出
选中范围：20 个方向，每方向 1 个起点
工作：20 项精修任务，由 4 个 worker 分发
比较：各自冻结的方向投影
推进条件：本批粗精修全部完成
交付：每项任务最终选择的精确候选
去向：下一层精修；最后由 MOEA/D 自己竞争
```

静态检查只显示可证明的声明和预计工作量；尚未产生的视图数量不能伪装成已知。
请求开始后应可看到实际解析的来源、批次、成员数量、分配和等待原因。
错误应指出用户的连接位置与修复方法，例如缺少哪个已声明输出、哪种投影不受支持，
不能只抛内部池路径或 requires 某 key。

### 14.7 本轮使用模型的验收标准

后续实现前，先检查完整用法是否满足：

1. GA→20 起点→VNS→GA，无内部池名和 role:worker 键，无按成员数手算调度时长。
2. 将 VNS 换为另一种已声明支持的精修算法，来源、输出和交接写法不变；不支持时在正式边界明确拒绝。
3. MOEA/D 的逐方向精修保留投影，粗细两轮与重复触发不会混入历史产物。
4. 添加观察者、保留更多历史或给同一 Adapter 增加无关输出，不改变已绑定下游的输入范围。
5. worker 数量只影响分发，除非显式选择重复或独立分配，不改变选中的工作集。
6. 暂停/恢复继续同一批精确输入与进度，不重新抽样、不重复初始化。
7. 来源未就绪、空输入、任务部分失败、预算不足和已完成均可区分，不自动扩大池范围补齐。

这些验收检查的是用户模型与跨入口一致性，不替代原有算法、身份、事务和恢复测试。
下一步优先收拢来源与结果的连接方式，再决定需要哪些便捷写法；不先堆 all 的筛选参数。

## 15. 运行内 Pool、跨 Case 交接与 L0：边界先固定

本节保护未来兼容性，**不在本轮实施跨 Case Pool 桥接、共享可写池或新的资源运行层**。
当前已具备标准 Case 结果与 Artifact 交付，不能据此声称任意 Pool 已能透明跨 Case 读写。

### 15.1 默认写权威属于一次 Solver 运行

当前 SolutionPool 属于一次 Solver 运行，而不是永久属于某个 Case 目录或整个 Project。
Case 配置可以反复执行，每次运行的输入、逻辑时间、任务进度和提交仍须隔离。
SolutionRef 包含 pool_id；当前 _record 会拒绝其他池的引用。
同一 SnapshotStore、同一数据库或同一台机器，不自动赋予两个 Case 共同修改索引的权力。

这不限制数据只能留在 Case 内：

- 本运行使用自身 Pool 与具名视图，成员变更由其步骤事务管理。
- 跨 Case 交换明确发布的结果、候选集合或投影视图数据，由共享 Project/Case 产物通道交付。
- 物理存储可以由共享 backend 提供；语义上的写所有者与提交范围仍要明确。

未来若确需 Project 级共享可写候选区域，必须先声明独立所有者、并发写入与提交/保留协议。
不能通过让多个 Solver 持有同一个 Python Pool 实例，隐含获得这项语义。

### 15.2 用户使用同一种来源引用，内部显式处理跨边界交接

目标使用路径可以保持自然：

```text
Case A 本轮已发布结果
  → Project 声明的产物依赖与授权读取
  → Case B 可用的只读来源视图
  → B 选择、搜索，再按 B 的规则应用结果
```

标准 SolverResult 已能携带 UnknownState、PopulationSnapshot、token、求值身份与来源，
较大结果通过 DataRef/Artifact 交付；正式输入还须经过对应权威发布收据验证。
当前没有把任意选定 Pool 集合自动导出/导入的完整用户接口。
因此上图是未来 Pool 交接应接入的现有底座，不是已经完成的自动跨 Case 功能。
接收 Case 仍须声明并实现正式输入处理；bare SolverBase 目前没有一个把任意 input_artifacts 自动装池的统一 setter。

跨边界至少保留以下含义：

- 交付的是哪次 Case 运行、哪次任务、哪份已提交输出及其版本。
- 候选语义、编码/schema、来源身份、原始反馈与必要证据；不可只交一个可碰撞的裸名字。
- 投影的权重、参考点等是明确的解释数据，不能只留下不知含义的标量分数。
- 原 Case 的可写 Unit、排名、锁、executor、Provider session 不随候选一起迁移。
- 接收方取得自己可解析、可保留的存储引用；不能把 A 的 SolutionRef 原样交给 B 的 pool.read。

导入与读取本身不等于产生新解。需要区分存储地址重绑定与候选身份：
原候选 token/来源应按正式交付契约保留或显式映射；B 搜索产生新提案时才按已有规则派生身份。
不能为了换存储地址就伪造一次搜索变化，也不能把数值相等当作跨 Case 身份相同。

接收到旧求值不表示 B 可以直接使用它作自己的评估结果。
原始证据可以保存；是否复用须校验问题版本、约束、编码与评估上下文的明确兼容性。
不同问题须显式映射或重新评估，不按 shape 相同、同名目标或同算法类型猜测。
跨 Case 的导入与后续求值是两个动作，不为运输本身虚增 B 的求值次数。
现有 warm start 默认把外部候选作为新运行种子重新评估，并不信任旧 objectives/score。
整运行 checkpoint 能恢复原 pool/run 身份，属于恢复；不能据此断言已支持跨 Case 的池集合合并。

### 15.3 跨 Case 不隐含跨 Case 原子提交

A 已发布的结果可以成为 B 的输入。B 失败时回滚自己的成员、Unit 与发布，不撤销 A 已完成的运行。
将 B 的结果交回 A，应作为 A 的一次后续输入与竞争，而不是远程改写 A 正在运行的 Unit。
若 A 已结束，接收结果需要显式的新受控调用、恢复流程或另一个接收 Case，不能回写已结束的那次运行。
若某种流程确实要求跨 Case 原子性或持续共享更新，须另外声明该协议，不能从 Pool 操作自动推导。

来源产物的保留与可达性由共享 Artifact/存储协议保障，不能依赖 A 的活进程或临时池 GC 根。
使用只读已发布数据不强制复制大数组；能否共享底层值取决于 transport/backend 能力，
不能提前承诺跨进程、跨机器或远程存储总是零复制。
重复交付与恢复还须按同一产物版本识别导入，防止把一次传输重试变成重复成员或一次额外搜索。
这不禁止用户显式从同一来源启动两次不同搜索；传输幂等与算法重复运行是不同意图。

### 15.4 L0 发放授权，Pool 表达数据与算法工作集

选择 100 个方向表示 100 项逻辑工作，不代表允许创建 100 个进程或分配 100 份 GPU。
worker、线程、设备、嵌套 fanout、deadline 与共享求值预算继续服从 Project 提供的 ResourceContext。
Pool、Unit、子池选择计划和 Adapter 都不能借此建立第二个全局 lease 所有者。

局部的读取/筛选/合并不应暗中启动新的 Case、进程或求值；
真正的跨 Case 执行使用现有 Project/stage/inner Case 正式入口。
外部 Snapshot/Artifact 的读取、传输和后续计算也必须经过相应受支持的存储与运行接口。
池负责声明使用哪些版本和保留关系，资源底座负责实际执行授权；两者不能互相替代。
这是一项兼容性要求，不代表当前所有 Pool 存储成本都已纳入统一的内存或 I/O 计费。

实现依据见 [SolutionPool](../../core/state/solution_pool.py)、[Case 结果](../../core/solver_result.py)、
[ResourceContext 消费入口](../../core/blank_solver.py) 与 [共享 Project 门面](../../project/project_runner.py)。

## 16. Pool 的核心操作闭环：选择、操作、应用分别明确

本节是使用模型要求，不提前定义一个包办所有行为的 apply API。

### 16.1 选择：回答本次使用谁

从一个合法来源或明确的一批视图，得到冻结的 Pool/视图集合。
选择、切片、过滤、排序、抽样和成员引用组合默认不修改源池、不淘汰候选、不创建 Unit，
也不自动重新求值。单个 Pool 与多个不同投影视图的层级不能被 all 或 count 隐藏。

同一普通选解规则应尽量用于任务起点、父代来源、生存选择与档案筛选；
实际拥有者仍校验各自用途、数量、原始坐标、Unit 依赖与范围。
共用选解函数不意味着四种算法决定拥有完全相同的约束。

### 16.2 操作：说明计算产生了什么

- 引用集合操作产生已有候选版本的新视图，保留身份。
- 候选变化产生新提案，由控制面绑定身份，再走正式修复、求值和硬接纳。
- 指标或评分计算产生对齐数值或统计，不自动改池成员，也不把临时分数写成候选永久属性。
- Unit 结构操作维护算法自己的关系与派生状态，不向所有引用同一候选的算法广播可写状态。

“都围绕 Pool 使用”可以统一输入外观，但不能让用户猜返回的是旧引用、新候选、统计还是更新计划。

### 16.3 应用：明确目标、意图与何时生效

一个选择结果可以用于不同目标，必须按实际意图交付：

- 更新普通精英/禁忌/档案集合：形成该具名目标的成员计划，由其所属事务应用。
- 更新算法种群、当前点或方向槽位：交给所属 Adapter 的选择/竞争入口，再维护 Unit。
- 给下一次精修提供起点：形成任务输入，不自动替换来源算法成员。
- 交给另一个 Case：发布/引用只读产物，接收方再决定自己的输入与应用，不远程写 Unit。

choose 返回 Pool 本身不表明应修改哪个目标，也不授权按来源名字回写全部上游。
同一个精英池剔除 x，不影响其他 Unit 对 x 的合法引用；物理回收继续服从真实保留关系。
同一次运行的相关计划复用原步骤事务，返回数据、暂存更新与已经发布必须可区分。
跨 Case 只有已声明的依赖与各自提交，不附带一个隐含分布式事务。

### 16.4 用这条完整流程验收接口

```text
取明确来源 → 用普通规则选解 → 计算新提案
→ 正式修复/求值/硬接纳 → 形成精确结果
→ 明确应用到普通池、算法 Unit、下游任务或 Case 输出
```

普通使用应看得出来源、规则、产物与目标。
框架内部负责引用解析、访问能力、版本、对齐、预算与提交校验；
用户需要明确的是算法意图和不同问题之间的必要语义映射。
后续优先完善这个运行内闭环，跨 Case 只先保护上述交付与 L0 边界，不抢先实现共享可写全局池。

### 16.5 原语首先遵守有序位置语义，不把 Pool 默认为数学集合

讨论基础方法前，先固定对象：一个读取中的 Pool 是有序候选版本引用视图，可保留重复引用。
它与具名池的可写成员目标有关联，但筛选得到的临时视图不自动获得回写权。
名字、候选版本、当前输入位置是不同含义，用户不应自行拼接这些内部字段。

从语义基础看，take 是位置投影，concat 是保留重数的拼接。
filter、sort、sample、top、groups 可以在这些基础上实现，但仍是有价值的用户方法，
不因为可推导就要求每个用户重复写索引代码。这里区分实现最小性与使用便利性，不强行二选一。
choose(Pool)->Pool 是普通规则的交付契约，Pareto/距离/禁忌判断是其规则，不分别变成池内置搜索引擎。

**选中位置的补集不等于候选引用差集。** 例如 x 是同一个精确引用：

```text
输入 P = [x, y, x]
选中 P 的位置 0 = [x]
按引用 difference 得到 [y]
按本次位置得到的未选部分应为 [y, x]
```

当前 difference 按引用去除全部出现，含义正确，但不能把它当作通用的“剩余成员”。
当前尚无公开的按选择位置补集/成对拆分入口，这是应讨论的实际交付缺口。
已有选解函数返回 Pool，框架应能在需要时一次性交付选中与未选中的两部分，
不让用户按浮点值或引用重新匹配，也不再调用一次随机规则猜另半边。

更深一层，Q=P.take([0,1,0]) 后，Q 的位置 0 与 2 都来自 P 的位置 0。
若选择 Q 的位置 2，未选部分应保留 Q 的位置 0。
因此不能只对最早母池位置做 set 差集；坐标必须对应本次被选择的输入视图。
实现可在显式选择边界建立局部位置，不建立永久的操作祖先图。
具体 split/remaining 等方法名尚未确定，不能在当前丢失直接来源坐标时声称补一个名字就已解决。

完整拆分应使每个输入位置恰好落入一边。
有放回父代抽样则允许重复选择同一位置，属于另一种用途，不要求它同时构成这样的互斥划分。
生存选择不能重复同一输入位置，但两个不同位置引用同一个候选时仍应按用途保留。

### 16.6 用少量稳定语义组织方法，保留常用便利操作

第一组是读取与选取：定位合法来源，读取候选/已存在反馈，按位置、条件或规则返回视图。
all 只指当前范围，反馈读取不自动求值；空视图仍应可继续组合。

第二组是组合与拆分：concat 保留顺序和重数，显式 merge/去重按精确引用，
intersection/difference 表达引用成员关系，按选中位置拆分表达本次选择的两部分。
分组只组织视图，不自动生成持久子池或 Unit；多个不同方向不会默认合成一个比较框架。

第三组是明确生成新提案：普通函数读取 Pool 后可产生零个、一个或多个新候选。
计算顺序由算法编排，交付复用已有批量提案与后续评估；不要求每种交叉、变异新增一种 Pool 方法。

第四组是成员关系计划：创建具名区域、追加、替换、移除、解除具名区域。
完整有序成员替换可作为底层统一操作；增删裁剪是有明确重复策略的便利方法。
创建/移除区域与生成/删除候选不同，更新普通池与更新算法 Unit 也不同。
这些计划由明确所有者在受支持的初始化/步骤/发布边界应用，函数返回不等于已经生效。
纯成员操作不应为了获得触发器而额外制造候选或求值；当前独立维护提交仍未开放，不能冒称已支持。

基础操作的验收应覆盖：同值不同身份、同引用不同位置、重复抽样后再选择、空结果、
顺序与重数保持、反馈位置对齐、作用域关闭、目标 revision 漂移与失败回滚。
先把这些语义定清，再确定公开名字和便利组合；不按所有算法名逐一堆出池方法。

### 16.7 当前已实现：在一次选择内算两部分，再投回调用者

本节接口已实现并从 `nsgablack.adapters` 导出，复用已有选择和作用域：

```python
from nsgablack.adapters import partition

selected, remaining = partition(pool, by=choose, rng=rng)
# choose 仍然是 Pool -> Pool，不要求所有规则改成返回二元组。
```

这个封装只在需要两部分时使用。非空输入调用 choose 一次，不能用第二次随机选择推算剩余。
空输入可以直接交回两个空视图，不生成候选或构建 Unit。
`rng` 可省，规则可采用 `choose(pool)` 或 `choose(pool, *, rng)`。
非空输入遇到需要 rng 的规则而没有显式提供时，在执行前报错；只接收 pool 的规则不消耗传入 rng。
空输入仍检查 Pool、同步 callable、签名与已传 rng 的类型，但不要求提供不会使用的 rng。
内部 TypeError 或其他异常原样传播，不用第二次调用探测签名。

内部可按以下方式处理，而不保存永久操作图：

1. 将当前输入 Q 的本次位置临时编号为 0…len(Q)-1。
2. 让 choose 在这份只读临时输入上选择，返回同一请求的派生 Pool。
3. 获取选中局部位置，检查唯一性、范围和输入归属。
4. 在同一局部输入内计算未选位置。
5. 分别用 Q.take(选中位置)、Q.take(未选位置) 返回，立即映回调用者已有的来源坐标。

这样 Q=P.take([0,1,0]) 中选中 local2，仍可保留 remaining 的 local0/local1。
临时编号不是新的候选身份；它只服务一次选择，不复制候选大值。
临时选择反馈也按 Q 当前顺序和重数交付，没有显式反馈时保持缺失，不猜 raw 或重跑 Bias。

返回时恢复原映射有必要：若 Q 的 local0/local2 都来自外层同一个输入位置，
它们在 Q 内是不同出现，但不能借一次临时编号伪装成外层两个独立的生存槽位。
外层消费者继续按自己的 purpose 校验：生存选择可拒绝重复原输入位置，父代抽样可显式允许。
真正的新选择请求可以把 Q 的全部出现作为正式输入；这与规则内部自行复制位置不同。

规则不得返回旧 Q、另一次 read 的同引用 Pool 或其他来源，再要求框架猜本次局部坐标。
sort、filter、groups 和内层拆分都须保留本次输入归属；每一层完成后立即投回调用者即可。
访问有效期仍属于外层调用，不能在合法返回两部分后立即关掉它们的读取能力。

一个合法完整拆分应满足：

- 每个本次输入位置恰好属于一边，两个位置集合无交集。
- len(selected)+len(remaining)==len(input)。
- selected 保留规则返回顺序，remaining 保留输入相对顺序。
- 两边可以出现同一候选引用，因为它们可能来自输入中的不同位置。
- selected.concat(remaining) 不保证恢复原排列；规则可能已重排 selected。
- 显式重复同一局部位置的有放回抽样不构成这种拆分，不能静默去重后声称成功。

“未选中”只描述本次位置关系，不自动表示硬拒绝、算法淘汰或从来源池删除。
某次 GA 保留 20 个精英，其余 80 个可继续充当变异父代；它们不因被称为 remaining 就失效。
80 个新后代若仅 60 个硬接纳，补旧成员、继续生成或允许规模改变由算法明确决定，
Pool 不隐式初始化补齐，也不让被拒绝提案成为已接纳成员。

最终应用仍检查目标的冻结身份/revision。选择期间目标更新或同名重建，
旧拆分不能自动套用到新成员上；回滚、保留与提交继续使用原所有者机制。

实现见 `adapters/pool_partition.py`；位置/反馈/作用域验证见 `tests/test_pool_partition.py`，
真实步骤回滚与正式 checkpoint 恢复见 `tests/test_pool_partition_integration.py`。
完整标准 Project 的 100 个输入拆成 20 个精英与 80 个其余成员，见
[Pool Project](../../examples/cases/pool_workflow_pilot/README.md)。此处是接口与运行验证，不是算法效果或优越性的证明。

## 17. 选择之后：变化、入池与 Unit 更新能否自然接上

核对日期：2026-10-20。本节起于**源码与测试文件的静态审查**，随后按第 18 节的实现更新了相关状态。
第 18 节交付机制已经定向验证，其他未实现项目仍为静态结论，不能推定下面全部场景均已执行。

本轮判断：基础的取解、筛选、组合、分组与拆分已经足够表达主要操作。
必要完善集中在已有阶段之间的数据交付、成员计划与实际消费者接入，不能用更多查询动词掩盖这些断点。

### 17.1 先对齐当前实际执行次序

```text
已公开来源 Pool → 选择父代/参考解 → 普通 change 计算新候选
    → 正式提案身份 → 预算 → repair / Unit 对账 → 求值与硬接纳
    → 暂存 accepted 精确版本及反馈收据
    → Adapter 决定本算法留下谁 → Unit 一起维护成员、反馈和扩展字段
    → 本批维护计划 + 逐提案入池指令
    → 同一 Pool manifest / Authority 提交 → 下游可读
```

这里有三种不同的“选中”：选择生成所用的父代、选择通过硬准入的提案、选择算法最终保留的成员。
它们可以使用同一 Pool 数据接口，但不能互相代替。

例如父代 100 个、新提案 80 个都通过硬接纳，GA 最终仍只保留 100 个成员。
80 个新解都可以进入 trials；其中未成为 GA 成员的候选也可以进入参考档案。
“从所有接纳试探解维护精英”与“只从 GA 最终生存成员维护精英”是两个有效且不同的需求。

当前顺序见 [控制面](../../core/composable_solver.py:1143)、
[GA 更新](../../adapters/nsga2/adapter.py:285)与[输出发布](../../adapters/change_outputs.py:63)。
不能让 PoolOutput 直接覆盖算法 Unit，也不能要求 change 先写 Unit 再让控制面补评估。

### 17.2 变化本身不需要拆成一批新的 Pool 方法

对于纯数值、没有额外语义 metadata 的问题，以下已经是当前可用写法：

```python
from nsgablack.adapters import ChangeResult, PoolOutput


def change(request, *, rng):
    # 要求 reference 已存在；任务中也要声明 change_sources。
    selected = request.pool.subpool("reference").sample(2, rng=rng)
    a, b = selected.values
    child = (a + b) / 2
    child = child + rng.normal(0, 0.1, child.shape)
    return ChangeResult(
        child,
        source_refs=selected.refs,
        outputs=(PoolOutput("trials", create=True),),
    )
```

先交叉再扰动、先扰动再交叉、从不同池各取一个、一次产生多个后代，都可以由普通函数表达。
批量消费者再用 ChangeBatchResult 保存逐孩子声明。没有必要分别增加 pool.crossover、pool.mutate、
pool.cross_then_mutate 或一个通用计算图执行器。

这里返回的是尚未评估的新提案，不是带着父解分数的新成员。
读取旧解不换身份；即使新提案数值碰巧没变，也不能据此跳过身份、求值或接纳协议。

### 17.3 场景覆盖：生成与身份

**1. 单池选择后变化：已有。**
take/filter/sample/top/partition 的结果继续是 Pool，可以读取对齐 values/refs/candidates 后计算。
ChangeResult 声明来源，普通变化桥负责后续提案身份。

**2. 多池交叉、先后次序不同：已有。**
同一调用作用域内组合来源，普通代码决定顺序。任务中的额外来源仍需显式授权，不能用 concat 扩大权限。
不需要按每一种顺序命名一个新 API。

**3. 一次计算零个、一个或多个孩子：GA 已有。**
ChangeBatchResult 保留逐孩子来源与目的集合，request.max_outputs 限制剩余许可，空批次不自动重试补齐。
VNS/MOEA-D 的标量调用仍只接一个孩子；改变算法候选批次语义不是 Pool 容器的职责。

**4. 预算不足与非前缀部分接纳：已有。**
预算与接纳通过原提案坐标组合处置，只有最终接纳版本执行入池声明。
不能因为计划产生 80 个孩子而把未评估或被拒绝的 20 个偷偷补成成员。

**5. 两个父代拥有不同语义 metadata：已有表达方式，使用约定需要明确。**
批量桥为各孩子使用同一调用 anchor；只返回数字时继承该 anchor 的语义。
source_refs 记录因果，并不自动切换语义基底或合并多父 metadata。
已知选中项为 UnknownState 时，可显式返回 `selected.candidates[i].with_values(child_values)`，
再声明对应 source_refs；不需要另造一个 base 类。
应补不同 metadata 的双孩子示例和相应验证，不能把“来源声明正确”当成“语义继承必然正确”。

**6. 同一个引用出现两次，分别对应不同 Unit 槽位：选择可表达，后续父代位置交付有条件性缺口。**
partition 与 survivor 已保留本次位置；但 NSGA 父代路径向 ChangeRequest 主要交付 refs/矩阵，
未统一交付选中的原 Unit 槽位。若同一引用占两个槽位且 age 等扩展字段不同，refs 不能反推槽位。
MOEA/D 已有自己的 parent_indices 参数，说明这里需要统一请求内来源位置，而非更多候选身份。
普通数值变化可继续使用当前接口；需要槽位字段的变化不能猜位置。

主要证据：[普通变化桥](../../adapters/change.py:227)、[批量桥](../../adapters/change_batch.py:47)、
[GA 父代路径](../../adapters/nsga2/adapter.py:190)、[数字与语义输出](../../core/blank_solver.py:3033)。

### 17.4 场景覆盖：集合写入与生命周期

**7. 同一个接纳孩子进入多个集合：已有。**
outputs 可以声明多个普通集合，复用同一精确版本，不给每个目的地复制新候选或分数。
create=True 允许在有接纳输出时创建集合；声明本身不提前创建。

**8. 已有集合的追加、替换、移除和裁剪：已有。**
普通维护返回 PoolEdit，冻结目标 view_id/revision，与其他入池声明一起检查并提交。
相同计划可以合并，不同 replace 或 append+replace 同目标不能靠执行顺序猜结果。

**9. 从 A 取旧解，放入 B，同时解除 A 的成员关系：可表达。**
在同一维护调用内计算最终 A/B refs，各生成一次 replace 计划即可，不需要新 move 动词。
移动成员关系不删除母池候选；其他 Unit/集合持有的引用保持有效。
若 B 尚不存在，使用 replace_members(..., create=True)，冻结缺失前提，和 A 的更新一起提交。

**10. 首次把选出的旧解保存为一个新集合，或建立空集合：已接通。**
第 18 节的命名副结果支持用本次 offered 中的旧成员或接纳版本创建普通集合，允许空结果。
普通 change/maintenance 的 replace_members(..., create=True) 也使用相同的缺失前提；默认仍要求目标存在。
目标名在受限任务中须声明，创建不扩大读取权限，也不允许写算法结果视图。
PoolOutput(create=True) 继续只追加本次接纳提案；零接纳时不建立独立空池。

**11. 阶段结束解除临时集合：底层有能力，普通计划尚不完整。**
SolutionPool.drop_subpool 可解除集合保留，但 change/maintenance 的受控计划没有对应生命周期操作。
若补齐，应与创建、替换共用同一目标身份检查；只允许操作自己可管理的普通集合。
不能因删除一个区域而级联删除后代视图、其他消费者或候选值。

**12. 无新提案、预算为零或零接纳时，只整理旧成员：当前没有独立提交路径。**
控制面提前返回，不进入 update/maintenance。不能制造一个假孩子、重复评估一次，来触发纯成员计划。
这是已有事务的可达提交边界问题；需要另行明确是否推进搜索代、池逻辑时间与进度，不能加个方法名就算解决。

**13. 最后一步的新反馈立即参与精英维护：已有，按归档含义选择输入。**
维护可以合并旧 elite 和 request.accepted；此时 trials 输出尚未统一暂存，不能先读 trials 猜本批结果。
main 继续只枚举调用截止时已公开记录。不要为了让示例更短而开放任意 pending。
若只归档实际最终种群成员，使用同次交付的 request.members，不以 accepted 代替。

主要证据：[成员计划](../../adapters/change_pool.py:234)、[本批维护](../../adapters/pool_maintenance.py:67)、
[目标校验与统一发布](../../adapters/change_outputs.py:13)、
[空/零接纳控制流](../../core/composable_solver.py:811)、[底层解除集合](../../core/state/solution_pool.py:674)。

### 17.5 场景覆盖：反馈与 Unit 更新

**14. GA 生存选择一次更新 X/F/V/token 与自定义行字段：已有。**
Adapter 决定 keep；PopulationUnit 用同一位置映射维护基础数据与 member_fields。
on_members_changed 只维护字段，不再选择或求值。不得让 Adapter 或 Pool 猜未知字段的含义。

**15. 普通集合变化后，让所有引用它的 Unit 自动变动：不应默认支持。**
两个 Unit 可以持有同一候选而使用不同排名、槽位和关系。
改变参考池不代表改动所有 Unit；实际接收方仍经 initialize/compete/refine 或自身选择流程应用。
已有候选版本不可被一处原位变化而影响所有持有者。

**16. 同一个 Pool→Pool 规则同时用于 survivor 与维护 accepted：反馈交付已接通。**
GA offered、维护 accepted 与最终 members 分别携带其实际已有选择 F/V，普通规则可以消费相应视图。
不重跑 Bias、不改 raw、不增加评分 API；不同 root 合并仍不自动拼接投影分数。

**17. 只从本轮最终生存成员挑精英：GA 已能在一次选择内直接交付。**
第 18 节允许先计算 members，再从它选择 elite，返回 `members, {"elite": elite}`，不重跑生存选择。

新结果视图未提交时仍不可公开读取；不靠“成员没变、旧视图仍公开”的偶然分支获取本次选择。

候选提名、考察顺序、槽位替换和最终生存仍保留不同 purpose，不能被统一成一种默认留存含义。

### 17.6 场景覆盖：多算法、嵌套与结构约束

**19. GA 后接 VNS 精修，再回种群竞争：正式池任务已有。**
选取已提交的精确成员版本作为起点，由 VNS 建立自己的 Unit 和基准；
返回找到的候选本身，再由接收方评估/比较，不把找到的 y 的分数记在原 x 上。
多轮精修需要中间反馈时继续使用算法步骤或正式内层任务，不能把一次纯 change 伪装成内部已评估搜索。

**20. MOEA/D 方向投影与递归子视图：已有；返回原槽位不是当前默认保证。**
PoolTask 冻结权重、参考点、来源 descriptor，下一层继续使用同一投影解释。
外部返回候选目前按 MOEA/D 当前分解在全局槽位竞争并受 nr 限制；若要求仅回原来源方向，
必须另行声明返回策略，不能因来源池带 slot 就静默改变替换范围。
不同方向裸 concat 不能自动合成一种选择分数，更不能把标量写回母池 raw。

**21. 并行算法共享一个 elite：候选汇集可做，共同 topN 需要唯一决策所有者。**
两个叶分别用自己的 accepted 计算同一个 elite 的不同 replace，当前会正确拒绝冲突。
可先写各自结果集合，再由一个所有者统一收敛；不能用 last-wins 丢掉另一分支。
若要承诺同一步自动共同 topN，缺的是汇合后的统一维护位置，不是另一种 Pool 容器。

**22. 信赖域、图搜索与 Provider 活状态：限制需要保留。**
TR 要求区域与几何一致；A* 的 g/parent 需要路径证据，不能随意用池中任意点替换节点；
目标标量投影也不能替代梯度变换。Provider 的活状态引用不能当作普通可传输候选任意复制。
这些应由实际 Unit/Adapter/Provider 校验，不能被 pool.apply(any_unit) 绕过。

**23. 懒激活、解不足、暂停与恢复：已有机制，不应自动补解或构建所有 Unit。**
Unit 实际使用时创建，恢复已有结构走 codec；不足采用任务声明的 error/wait/available。
命名来源不存在与暂时没有足够成员是不同情况。各算法的最低结构数量也不能被 available 抹掉。

**24. 多 Case 或多进程传递选择：使用发布引用与正式交付，不携带调用内 Pool 活对象。**
Pool 访问范围在回调结束后失效；跨步保存精确 refs/正式任务状态，跨 Case 使用 Artifact/Snapshot 交付。
跨步仍需要值可读时声明保留根，下一调用重新验证来源范围和版本，不能让关闭的 Pool 继续提供访问能力。
checkpoint 恢复整个池不等于任意跨 Case 合并，当前也不能把 foreign pool_id 的 refs 当作本地引用。
跨 Case 导入与反馈兼容仍须单独契约，不能靠给 Pool 增加 merge 名称声称已支持。

**25. Pareto、精英与相对参考集合的多样性：复用数学规则和明确输入，不增加通用 compare。**
非支配排序已有数学实现，可以把返回位置投回输入 Pool；top 的词典序并不等于 Pareto。
多样性需要明确参考集合及反馈含义，依赖 Unit 特征时继续通过只读 Unit 输入消费。
从私有 ParetoArchive 发布可供搜索使用的精确引用档案仍有连接工作，不能仅按 token/数值补造 refs。
优先复用已有算法与成员计划；专用便捷函数属于规则适配，不应建立第二个可写档案权威。

**26. 禁忌池、去重与回收：集合保存记忆，是否禁止由算法规则决定。**
TabuSearchBias 现有的是接纳提案的私有软评分记忆，不等于已开放的共享禁忌池或硬拒绝策略。
用普通集合保存历史时，需要明确何时记入、保留窗口以及状态等价键；新 token 的同状态解不会被引用 difference 自动识别。
软惩罚与硬过滤/准入应分别走实际偏好或选择/接纳位置，不因有一个 tabu 集合而自动改变算法。
移出历史集合也不立即物理删候选；现有保留根与提交后回收继续保护其他 Unit 和任务。

主要证据：[池任务与冻结投影](../../adapters/pool_tasks.py:338)、
[MOEA/D 外部输入](../../adapters/moead/adapter.py:238)、
[同目标冲突](../../adapters/change_outputs.py:74)、[按需 Unit](../../adapters/unit_backed.py:145)。
各算法约束的完整盘点见 [Pool 接入准备度](SOLUTION_POOL_ADAPTER_READINESS_CN.md)。
Pareto、多样性与禁忌的现有能力及缺口见 [接口手册第 14–16 节](POOL_API_REFERENCE_CN.md#14-现有能力是否真的接入了-pool)。

### 17.7 最小完善顺序：补交付与应用，不扩张查询词汇

第一步中，维护已有选择 F/V 附到 accepted 已完成；members 也交付自身反馈。
其他选择 purpose 的普通 Pool 接入仍须补 exact offered 或明确拒绝，不应混成一种最终留存。

第二步的 GA 路径已按第 18 节落地：一次选择交付有序主成员与命名副结果。
单轨迹算法仍应区分 current 与任务 best，
MOEA/D 保留方向作用域。名称和结构需要以实际消费者为准，不能从 retention roots 猜一个“万能最终池”。
它只交付本消费者可拥有的旧成员与本批 accepted，不开放兄弟 pending，也不重放选择。

第三步的选择副结果已能在同一事务内表达“目标不存在时创建并填已有 refs”。
通用 replace_members 的显式创建也已完成，受控解除普通集合仍待补齐。创建冻结不存在这一前提，更新/解除须检查精确 view_id/revision；
同名重建不能重定向旧计划。应扩展现有计划模型，不另造第二个池管理器。

需要 Unit 槽位数据时，再统一父代的位置来源交付；这种位置只属于本次请求与实际 Unit，
不成为永久候选身份，也不建立无限操作祖先图。普通数值变化不必承担这一复杂度。

纯成员维护的独立提交需要单独确认进度与发布规则，再接入现有事务。
共享精英的跨分支归并也需要明确一个所有者；两者都不应通过假求值或新全局运行循环补洞。

目前不建议增加通用 compare、交叉顺序专用方法、万能 beunit/apply、隐式 evaluate、自动补满、
跨方向默认分数合并、自动 metadata 合并或每种算法一套 Pool 子类。
能由普通函数、现有候选协议或实际 Unit 操作表达的部分，应继续复用。

### 17.8 下一轮应验证的连接，而不是统计新增方法数量

以下为审查时提出的验收组合；第 18 节已覆盖主/副结果相关子集，其余仍待验证，不能整体视为通过：

- 同一 choose 在 GA survivor 和维护 accepted 上消费同一份明确选择反馈，raw 始终不变。
- 从 GA 最终成员归档与从全部 accepted 归档产生不同但各自正确的结果，最后一步不晚一轮。
- 两个相同 ref 的不同父代槽位携带不同扩展字段，变化仍能定位实际来源。
- 两个不同 metadata 的父代生成两个语义孩子，显式 with_values 的语义与来源分别保持。
- 从旧解首次建集合、仅建空集合、重排/重复成员、同名冲突、创建后失败一起验证。
- 已存在 A/B 的成员迁移与目标解除均原子应用；失败时两个集合、保留根与 Unit 一起恢复。
- 预算截断、非前缀部分接纳、零接纳与空提案不得错误触发入池或制造搜索提交。
- 普通选择在各 purpose 上要么准确接入，要么在装配时明确拒绝，不能到求值之后才发现没有 Pool。
- 并行两个来源汇合到同一档案时使用明确所有者，失败不会丢任一分支或伪造全局 topN。
- VNS current/best、MOEA/D 原槽位/全局竞争、TR 区域与 A* 路径约束分别验证，不能用 GA 示例代替。
- Pareto 档案保留精确引用，多样性使用明确参考集合；禁忌按声明状态键识别新 token 的同状态候选，不能误用引用差集。
- 正式 checkpoint 保存已提交引用、成员顺序与所需请求进度；恢复不重选、不重评、不重复创建集合。

当这些连接能由少量稳定契约表达并得到行为验证时，Pool 的易用性才算继续收敛；
新增查询方法的数量不能代替这些场景。

## 18. 当前已实现：复杂选择一次交付主成员与命名副结果

接口沿用普通函数，不要求用户定义选择结果基类或额外运行组件：

```python
def choose(pool, *, rng):
    # 这些是用户定义的普通规则；中间结果继续是同作用域 Pool。
    members = choose_members(pool, rng=rng)
    elite = choose_elite(members, rng=rng)
    return members, {"elite": elite}


ga.set_selector(choose)
```

主 members 仍经过原 count/位置校验，交给所属 Adapter 和 PopulationUnit 更新。
命名副结果转成普通集合的精确成员计划；目标存在就替换，不存在就创建，可以交付空集合。
选择只执行一次；命名计划与 Unit 的更新、其他提案输出在原 Pool/Authority 事务中一起生效。

### 18.1 允许写复杂规则，返回边界保持明确

函数内部可多次筛选、重排、分组和嵌套调用纯规则，使用已有分数或明确参考输入。
它也可以把 remaining 交给 reserve，而不只归档 members 的子集。
目的池名字不赋予数学含义：叫 elite 不保证自动取最优，叫 tabu 不自动硬拒绝。

主结果和副结果都必须来自本次 offered 的同一 root/scope。
主选择保持原来的位置唯一性；普通副集合可显式保留重复位置和顺序。
不能返回另一次 read 的同引用 Pool 后要求框架猜坐标，也不能把新生成、未评估的值放进副结果。
不同调用或不同方向的 Pool 不能借此混成一种默认评分。

纯 `return members` 与原对象 selector 的索引接口保持有效。
partition 的 by 仍只返回 Pool；复杂交付由最外层实际 survivor 消费者处理。

### 18.2 所有命名结果随同一提交应用

规则返回后，先校验主数量、位置和所有副结果，再将它们脱离成既有 PoolEdit。
已存在目标冻结 view_id/revision 等完整 descriptor；缺失目标冻结 pool_id/name/absent。
创建过程使用现有普通集合与 pending-aware 成员 setter，不读取尚未提交的新公共 descriptor。
目标中途出现、同名重建、同目标不同 replace、append/replace 冲突均拒绝，不能默认最后写入者获胜。

普通副集合只保存原精确引用，不复制候选值、原始求值或另一份可写排名。
它不会直接改算法拥有的 population/方向视图。需要把副集合再交给其他算法，继续使用正式池任务。
所有活 Pool 在原调用结束后失效；checkpoint 只保存已提交集合、引用、Unit 和既有绑定状态。

### 18.4 易用性核查：局部选择已自然，输出到下一步还需闭环

2026-10-20 本节保留**上一轮静态源码核查与验收动机**。
随后用户已授权实施，精英实际消费与历史成员输入已继续落地，最新状态见第 18.5 节；
本节的“缺口”描述是改动前判断，不能当成最新实现状态。

目前一个所有者内部的写法是自然的：输入 Pool，按普通函数选最终成员，再从最终成员挑精英，
最后一次返回主成员与副集合。规则不需要知道事务、候选存储和 Unit 字段同步的实现。
复杂度主要留在跨调用、跨 Adapter 的输入和输出连接，不能以“已有这个方法”替代可用性验证。

**1. 同一个池的名称，在各入口还没有一致的解释。**

选择返回的 `{"elite": elite}` 使用精确公共池名；`change_sources=("elite",)` 也声明精确公共名。
但 `PoolTaskSpec("elite", ...)` 的字符串 select，以及任务的 `output="elite"`，
会加上该任务的命名空间。因此三处都写 elite，不保证读写的是同一个集合。
名字中包含 `/` 也不表示绝对寻址或自动建立父子拓扑，不能据此绕过任务的名称展开。

当前跨这两种入口连接时，可用正式 select 回调显式返回目标公共集合的精确 refs；
若选择任务相对名，则输出方也必须采用一致的实际名称。不能让用户靠猜前缀连接。
这是应优先收敛的寻址问题：先统一现有入口的解释或明确区分公共名与任务相对名，
并在已有装配报告中显示解析后的来源、目标和所有者。尚未实施新的名称解析规则，
不应把这段建议视作已经存在的绝对路径 API。

两个 GA 分别发布 elite 时，当前也没有隐式实例隔离；可以显式使用 `ga_a/elite`、`ga_b/elite`。
这些是约定的精确名称。若确实共享一个档案，仍须指定唯一维护所有者，不能自动合并两个 replace。

**2. 本轮快照、累计档案与不更新，需要让用户一眼分清。**

当前有三个不同动作：

- `return members, {"elite": elite}`：精确替换集合成员，缺失时创建。
- `return members, {}`：不更新任何副集合；上一轮 elite 仍然存在，不会自动清空。
- `return members, {"elite": members.take(())}`：显式清空 elite；缺失时创建空集合。

逐提案的 `PoolOutput` 则追加被接纳提案，与上述替换不同；它也不等于算法最终保留的成员。
这些动作都随原事务提交后才可读，不承诺同一次 update 内通过公开读接口读到刚返回的副结果。

尤其要区分“本轮最终成员中的精英”与“历代最终成员的累计 topN”。
普通选择只能返回本次 offered 根中的位置，不包含已经离开本次 offered 的历史档案成员。
现有 maintenance 可以读旧档案与本批 accepted，却没有本次最终 members 输入。
因此仅把副结果名字改为 archive，或把 choose 写得更复杂，都不能补出缺失的历史输入。

若要求同次提交、包括最后一步的完整累计，应在既有选择或维护边界明确交付所需的历史集合与最终结果；
这是输入交付缺口，不是缺少 merge，也不应通过捕获 Solver、扩大共享 context 或读取兄弟 pending 来绕过。
跨提交由单一所有者维护已有实现基础，但必须说明使用的是哪一次已发布结果，不能隐藏一轮延迟。

**3. 空池必须有启动路径，动态池必须有退役责任。**

当前示例第一轮 reserve 为空是正确结果：初始 offered 没有多出来的淘汰位置。
如果下一轮变化只从 reserve 抽样，就必须显式决定空时改从当前成员取解、等待明确的生产阶段，还是报错。
`sample(n)` 不自动补齐；没有产生提案时，不会自动进入一次新的生存选择来填满 reserve。
因此简单重试不能代替启动策略。

来源不存在与来源为空也不同；`on_insufficient` 处理分配不足，不能把不存在的命名来源变成已存在。
现有 `MixedPoolParentSelector` 要求外部集合已存在且非空，不能把它当作默认回退策略。
启动、缺额和阶段屏障应在具体配方里显式写出，不给所有算法统一加随机补解。

普通集合是候选保留根。每代创建 `elite_<generation>` 会持续保留历史成员，
垃圾回收不会因为它很久没被读就自动删除仍被集合引用的解。
常见精英快照优先使用稳定名称并替换；确需动态历史集合时，要明确退役责任。
普通 choose 当前没有通用 drop，不应宣称其历史集合会自动过期。

**4. 规则复用和参数来源应保持简单。**

`partition(..., by=rule)` 的 rule 继续是纯 Pool→Pool；
返回 `(members, outputs)` 的函数属于最外层 survivor 交付，不能直接当作任意 partition 的 by。
把可复用的成员规则与最终交付函数分开即可，不需要为此引入结果基类或通用工作流解释器。

普通 choose 现允许 `choose(pool, *, count[, rng])`，由实际 SelectionRequest 提供 count。
旧不带 count 的函数保持原调用；显式 partial(..., count=固定值) 仍表达固定数量。
初始化不足及部分接纳时优先使用自动 count，避免重复容量配置。详见 Pool API 手册的 2026-11-12 核查。


已有错误信息还应补充实际所有者、选择 purpose、副结果名称和期望/实际数量。
例如 `outputs['reserve']` 来源不对，应定位到 reserve；同目标冲突应指出具体目标与双方来源。
现有 `get_operation_contract` 也应说明实际支持的选择目的和返回形式，而不只列出 set_selector 绑定。
这些是现有诊断面的改进方向，目前仍待实施，不需要新增 Pool 操作方法。

**5. 接下来最有价值的三个验收故事。**

当前 `ga_partition` 已验证主成员及 elite/reserve 的生产、提交和恢复，
但 paired_change 只消费默认父代；装配中的 `change_sources=("elite",)` 只是读权限，
没有绑定外部父代选择器，reserve 也没有消费者。因此还不能把该例当作副池已经改变搜索行为的证据。

- **精英进入下一代变化。** 在现有 GA 装配中使用
  `ga.set_parent_selector(MixedPoolParentSelector("elite", pool_fraction=1.0))`，
  保留对应来源声明。检查下一代孩子的 source_refs/change_input_refs 来自上次提交的 elite，
  孩子获得新身份，读父代不增加求值。该连接使用已有组件，本节尚未执行这条新验收。
- **最终成员精英交给 VNS，再返回 GA 竞争。** 使用正式阶段屏障与精确输入名称，冻结实际精英引用。
  明确返回的是所有接纳提案，还是逐任务最终精选视图；二者不能都叫“精修后的最优解”。
  已有 GA→VNS→GA 示例覆盖其他来源，不能代替新命名副结果作为来源的连接验证。
- **并行分支汇入同一个档案，再被消费。** 先明确各分支结果和唯一档案所有者，以及跨提交汇合时点。
  若要求同批最终成员统一 topN、无额外求值提交，当前还缺正式的共同维护位置；
  两个叶各自 replace 同一个 archive 会冲突，不能把拒绝改成 last-wins 来声称已经支持。

本节依据：[精确副结果名称与来源](../../adapters/selection_pool.py)、
[任务相对名称与分配](../../adapters/pool_tasks.py)、[既有维护输入](../../adapters/pool_maintenance.py)、
[外部父代选择](../../adapters/parent_selection.py)、[当前示例装配](../../examples/cases/pool_workflow_pilot/cases/ga_partition/adapter/workflow.py)。
完善优先级是名称连通、真实消费、必要输入与诊断；暂不新增通用 compare、Pool 子类或更多同义查询方法。

### 18.5 已落地的三个用途：繁殖、精修与历史档案

**用途一：本轮精英决定下一轮父代。**

ga_partition 继续一次选择交付最终成员、elite 和 reserve；现在显式绑定
MixedPoolParentSelector("elite", pool_fraction=1.0)，下一轮变化实际消费上一提交的 elite。
来源权限仍由 change_sources 声明，不因为输出了副池就自动授权任意来源。
初始化 reserve 为空；后续数量取决于实际送评接纳数，不保证始终等于配置后代数。
只读观察核对每个孩子的 source_refs/change_input_refs 与新身份，不构造 Unit 或再求值。

**用途二：GA 的20个最终成员精英交给 VNS，再回 GA 竞争。**

[assembled_ga_vns](../../examples/cases/assembled_ga_vns/README.md) 保留原 population 默认模式，
新增显式 refinement_source="elite" 和独立 elite Project 分组。
GA 按原约束支配与拥挤度选成员，再从中发布普通 ga_elite；
VNS 用正式 select 回调读取其准确公共名，阶段开始时冻结引用，逐起点做基准和邻域搜索。
返回使用已接纳提案的聚合集合 refined，由 GA 正常重评竞争，不把聚合池说成逐任务最终精选。
阶段屏障、任务状态、L0、事务与正式 checkpoint 沿用现有路径。
这也给出名称差异的可用配方：公共副池显式按精确名取，任务相对输出和返回在同一 Router 命名空间内配对。
尚未修改底层名称解析，也不宣称字符串 select 与公共名已自动统一。

**用途三：历代最终成员档案，在本轮提交内更新。**

现有维护请求增加可选 request.members。它来自实际叶的有序人口引用与 (X,F,V)，
不读待发布的公开 population 视图，不从 retention roots 猜成员。
NSGA-II/III、SPEA2 与 MOEA/D 提供该输入；VNS 为 None，MOEA/D 保留重复槽位及多目标反馈。
accepted 和 members 各自携带只读选择反馈；跨 root 合并不自动拼评分，归档规则显式使用 raw 或统一键。

```python
def maintain(request, *, rng):
    if request.members is None:
        raise ValueError("population members required")
    names = request.pool.describe()["subpools"]
    old = request.pool.subpool("archive") if "archive" in names else request.members.take(())
    kept = old.merge(request.members).top(20, key=raw_archive_key)
    return (request.pool.replace_members("archive", kept.refs, create=True),)
```

raw_archive_key 是用户明确选择的归档规则；多目标不默认取和，也不默认全局套用某个 MOEA/D 方向。
同一调用内可以保留已离开当前种群的历史解，同时排除被接纳但未被算法留下的更好试探解。
create=True 冻结目标缺失，已有集合冻结身份/revision；计划和 Unit 一起提交，最后一步也不延迟归档。
受限任务须声明 archive 目标；授权自有最终成员不开放 main、未声明集合或兄弟 pending。
半支持的成员入口、错行数/值或其他分支未发布成员均失败，不能静默退回 accepted。

实际配方为脚手架 [maintain_member_archive](../../project/scaffold/case_template_solver/adapter/operator_example.py)，
以及 ga_search 的 [maintain_final_members](../../examples/cases/pool_workflow_pilot/cases/ga_search/adapter/workflow.py)：
同一标准 Case 使用 config={"archive_source": "members"}，默认 accepted 模式保持原档案含义。

当前仍不增加无求值独立维护提交、通用 drop、全局同批多分支 topN 或新的 Pool 子类。
这些用途复用已有普通函数、成员计划、Unit 更新与 Pool/Authority 事务。

本轮249项定向测试通过（各组互不重复；不与历史测试数累加），范围和环境重跑说明见接口手册第13节。
精英繁殖正式运行260次求值，逐项核对160个孩子来自上一提交elite；
20精英→VNS→GA的正式运行43步、128次求值，40个聚合提案实际返回竞争。
两模式历史档案标准Case各3步、14次真实求值，维护最后一次提交且不改变搜索轨迹。
两个受影响Project的严格build/catalog Doctor均0 error、0 warning，无skip；
报告见 [精英繁殖](../../examples/cases/pool_workflow_pilot/SELECTED_OUTPUTS_RESULTS.md)与
[精英精修](../../examples/cases/assembled_ga_vns/ELITE_RESULTS.md)。未运行全仓测试或算法性能benchmark。
