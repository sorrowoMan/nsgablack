## 1. 首先固定我们已经达成的核心认识

一个候选可以被多个算法使用。各算法围绕候选建立自己的结构信息，通常无需理解其他算法的完整状态，也无需逐对编写算法转换器。

例如同一个候选 `x`：

- 在 NSGA-II 中可以成为种群成员，参与排序和环境选择。
- 在 SA 中可以成为当前点或试探点，与当前评分、温度和接受规则一起工作。
- 在 MOEA/D 中可以被一个或多个子问题槽位使用，与权重和邻域建立关系。
- 在 A* 中可以成为搜索节点的状态值，但父路径和路径代价属于该节点所在的搜索结构。

我们可以用下面的记号讨论，不把它当作新增 API：

```text
候选语义值：             x
算法 A 的结构：          U_A = 候选或候选集合 + A 的特征、关系、必要状态
算法 B 的结构：          U_B = 候选或候选集合 + B 的特征、关系、必要状态
组合中的候选流转：       x 从可读来源交给 B；B 使用自己已有的结构操作
```

其中“增量”有三层含义：

1. **语义增量**：Unit 增加算法需要的信息，候选仍具有相同的问题含义。
2. **维护增量**：成员、反馈或关系变化时，所属 Unit 按自己的规则维护相关字段。
3. **实现增量**：新增算法尽量只增加独有结构和决策，复用候选处理与运行底座。

“增量”不意味着所有 Unit 必须共用同一个可变 Python 对象，不意味着所有特征都能独立于集合计算，也不意味着任意旧反馈都能直接复用。

## 2. 修正上一轮交流中两个说得过满的地方

### 2.1 不需要逐对转换，不等于接收行为已经自动实现

用户指出“不需要为 A 和 B 定义专用转换”，这一点成立：A 交付统一候选，B 按自己的结构操作接收即可。

上一轮回答进一步说“现有 Unit 操作可以直接完成交接”，这句话需要限制范围。源码里能看到结构构建、成员维护、候选 token 和反馈对齐；但这不等于每个现有 Adapter 都已经有相同的“接收外部候选并按本算法接纳”入口。

特别是：

- `StrategyChainAdapter` 的阶段推进主要改变活动阶段和清理队列，没有在 `_advance_phase()` 中自动把上一阶段的候选交给下一阶段。
- `StrategyRouterAdapter` 生成数值 seeds 和 `StrategyTask`，但种子被传入调用上下文，不代表任意叶 Adapter 都会消费它。
- `CompositeAdapter` 将反馈送回提案的原所有者，没有把一个孩子的候选自动广播给所有兄弟。

因此，正确表述是：**统一候选使通用交接成为可能，算法的接收规则只需定义一次；当前实现仍须逐类确认哪些路径已接上。**

### 2.2 原始求值可以有条件复用，选择反馈不能一概照搬

同一候选、同一 Problem 语义、同一有效评估条件下，原始目标和约束具有复用价值。这是设计方向。

不过当前正常求值路径会由 Problem 或 Provider 得到 raw feedback，再经 Bias 形成选择视图。不能据此宣称跨 Adapter 的求值复用服务已经自动存在。

此外，B 的多样性偏好如果依赖 B 的种群，A 的选择分数即使仍对应同一候选，也不能直接充当 B 的选择分数。

## 3. 增量信息具体分哪几种

### 3.1 仅依赖候选内容的派生特征

例如某个固定编码下的范数、固定距离空间中的坐标投影。候选内容和计算规则相同，结果可能共享或缓存；候选改变后须失效。

是否值得缓存取决于计算成本与存储成本，不能因为有 Unit 就默认保存所有可计算量。

### 3.2 依赖当前 Unit 集合的派生特征

例如排序、拥挤程度、候选相对某种群的距离。这些量依赖集合内容、反馈视图以及具体算法规则。

同一个 `x` 在两个种群里可以有不同的特征值。共享候选不能共享“我是该集合第几名”这种关系事实。

### 3.3 依赖位置和关系的结构信息

例如 MOEA/D 的槽位归属、权重邻域；A* 的父节点与边；某一区域的中心和半径。

这些字段的作用是让本算法正确操作候选。交接候选时接收方建立自己的关系，不要求发送方理解目标算法。

### 3.4 不可从当前候选重建的历史状态

例如连续存活次数、温度进程、禁忌记忆、累计路径代价、优化器动量。

这些事实必须有明确所有者和恢复规则。不能因为它们被存进 Unit，就将其当成可以随时丢弃的特征缓存。

### 3.5 原始求值证据

原始目标、约束、评估条件与事件引用表达已经发生的求值。它们与候选关联，但不由 Unit 特征计算重新创造。

同一批求值证据可以被不同策略解释。解释差异属于策略或偏好；证据本身不能被各方各写一份并声称相互等价。

### 3.6 活资源与外部状态

executor、锁、Provider session、全局 lease 不属于候选增量特征。`StateRef` 也需要遵守 Provider 的寻址与生存范围。

候选可传输与资源可复制是两件不同的事；Unit 的 codec 不应复制任意第三方对象图。

## 4. 编排首先分成三个层次

### 4.1 一个 Solver 内的搜索组合

主体是 Adapter、各自的 Unit 和统一候选评估通道。这里决定：谁提出候选、哪种策略活动、怎样分配搜索提案预算、怎样消费反馈、什么时候交换候选。

这些搜索语义归 nsgablack。组合 Adapter 可以拥有调度策略，但不能另建 Project 全局资源授权者。

### 4.2 求值的执行组合

主体是 Problem、Evaluation Provider、评估后端与有效资源上下文。这里决定：同一批候选如何批量求值，是否使用并行后端，如何处理取消和结果对齐。

求值并发不会自动让 Adapter 的 `propose/update` 并发，也不会改变其结构所有权。

### 4.3 多 Case / Project / 动态子调用

主体是完整 Solver/Trainer Case、Stage、Artifact、结果信封与 L0 grant。

这里的流程、依赖、并行和授权归 BlackBase。跨 Case 的结果可以继续为优化搜索提供输入，但 Case runner 不应猜测排序、温度、邻域或路径代价。

静态 Stage 图与动态调用树可以组合；二者均不要求优化 Adapter 获取 ML Trainer 内部字段。

## 5. 所有组合共同遵守的候选生命周期

### 5.1 普通提案

```text
所属 Adapter 操作自己的 Unit
  -> propose 候选
  -> 控制面形成 CandidateBatch / token / provenance
  -> 预算裁剪
  -> ProblemRepair，或显式共同修复
  -> ProposalRepair 沿原提案路径对账
  -> Problem / Provider 求值
  -> raw feedback + Bias 选择视图
  -> Evaluation Event
  -> BatchDisposition
  -> 原提案所有者 update
  -> Unit 执行成员或结构操作
  -> 权威 Snapshot 与逻辑步骤提交
```

### 5.2 候选在两个算法之间流转

这里建议默认使用 **已提交的候选来源与脱离后的调用输入**：A 的已提交状态可提供候选；B 用自己已有的操作决定把它用于什么。

可能的用途包括只读参考、变异父代、初始化种子、待比较试探点或种群入选候选。用途不同，B 的搜索行为就不同；用户应能从装配位置看出来。

这不要求建立 A-to-B 转换器。它要求 B 已定义自己的行为，组合时选取相应行为。

本轮不先增加统一接收基类或强制交换协议。先用具体组合辨认复用点；已有 `initialize_population/apply_selection/replace_evaluated_rows` 等操作应优先复用。

### 5.3 不能把外来候选随意塞进本轮 update

当前组合器的 `update()` 对应此前 `propose()` 的范围、pending 状态和最终处置。

如果未经提案登记就在某个孩子的 update 输入中追加兄弟候选，行数、token、原任务和 pending 可能同时错位。

设计上可以统一支持候选交换，但应让交换走明确的搜索操作和事务范围。不能把 `update()` 从“本轮提案反馈”偷换为“任何来源的矩阵入口”。

## 6. 同类型多实例：首先保证实例隔离

示例：两个 NSGA-II、三个 SA 或多个同配置的 MOEA/D，各自探索不同初值或区域。

### 6.1 哪些可共享

同一个 Problem、同一份问题 Pipeline、不可变配置、纯函数工具可以共享。具名 mutation operator 可以按消费者选择；无需每个实例复制完整问题管线。

### 6.2 哪些必须区分

可变 Adapter、Unit、策略 RNG、pending 提案、反馈关联、特征缓存、清理债务都必须按实例隔离。

同一个 Python Adapter 对象不能占据两个执行实例位置；相同类型和相同数值配置也不能代替实例身份。

### 6.3 四类“ID”不要混淆

1. 算法 Unit 的 `unit_id`：结构自身身份。
2. `StrategyInstanceSpec.unit_id`：控制器内的执行实例编号，历史上也叫 unit。
3. `owner_path`：完整组合路径，区分嵌套的实际所有者。
4. candidate token：候选身份，不能替代前三者。

源码中的 `UnitSpec = StrategyInstanceSpec` 已明确注明这是执行实例，不是算法 Unit。文档和用户界面也应保持这个区分。

### 6.4 默认讨论建议

多实例默认独立状态，共享 Problem 与可复用工具；需要互相影响时通过显式候选或只读信息交流，不共享可变 Unit。

已有实现：Router 实例验证拒绝重复可变 Adapter 对象；分区与任务包含实例路径。已有嵌套同类型测试源码。

## 7. 同轮多分支：合并提案，分别更新

示例：A 提出 3 个候选，B 提出 2 个候选；控制面统一求值，再分别回送。

### 7.1 Unit 的作用

A、B 可以使用完全不同的结构。汇总的只是本次候选提案，不是把两套算法权威种群拼成一个矩阵。

### 7.2 精确的索引例子

```text
A 的原提案：a0 a1 a2
B 的原提案：b0 b1
根提案：    a0 a1 a2 b0 b1
预算送评：  a0 a1 a2 b0
最终接纳：  a1 b0
A update： [a1]
B update： [b0]
```

孩子收到的局部 disposition 仍表达其原始提案空间；真正 update 的输入已经压缩。PopulationChange 则描述 update 内某次成员操作的局部 incoming，不可再用根索引取行。

### 7.3 不自然发生的事情

A 不会因为和 B 在同一轮求值，就自动获得 B 的候选。要交流，可以让下一次提案消费共享已提交候选，或增加经过定义的接收操作。

### 7.4 当前实现

`CompositeAdapter.propose()` 依次调用孩子并保存 ranges；disposition 调整范围，update 将对应 feedback 子集送回孩子。它是逻辑多分支组合，不是由此方法启动线程并发。

其种群权威为 `partitioned`。最后评估批次可以汇总；各孩子的权威结构仍分开保存。

### 7.5 待讨论

同轮是否一定要整组原子提交？现有 Solver 步骤事务按根步骤提交。若用户希望每个孩子独立提交并允许部分失败，那是另一种执行语义，应通过现有 Case 边界或明确扩展讨论，不能默认套上当前根事务。

## 8. Portfolio：分配预算和选择策略

示例：NSGA-II、SA、MOEA/D 共用一个求值预算，控制器按策略表现调整提案份额。

### 8.1 分配什么

提案数量、实际求值次数、逻辑提交数、墙钟耗时、资源 grant 是不同预算。Router 的任务预算首先表达本次提案配额，不等于全局 L0 授权。

### 8.2 候选少于或多于配额

少于配额是否把剩余额度给其他策略，需要明确是否在本轮重分配。多于配额必须形成裁剪证据，不能让子 Adapter 的 pending 仍认为所有候选都会进入 update。

当前 Router 保存子层 prefix disposition，并与后续预算/接纳映射组合。

### 8.3 评价策略表现

如果 A、B 使用不同 Bias 或标量化，它们自己的选择分数不能天然横向比较。

建议按明确的公共指标评价预算分配，例如统一 raw 目标指标、统一超体积评价配置，或明确声明控制器的标量化。不要仅因为都是 float 就直接相减。

这项公共指标是控制器的搜索思想；无需放进 Unit 构建器或运行底座。

### 8.4 公平性

根预算采用前缀裁剪时，排在后面的策略可能长期得不到送评机会。可通过已有排序、分配策略或轮转规则解决，必须区分“分到配额”与“实际被送评”。

失败、零接纳和高成本候选的统计也不能伪造为一次有效改善。

### 8.5 当前实现与边界

Router 已有角色/实例预算、阶段、区域、共享报告和自适应权重路径。统一比较的具体语义须看配置与 `_score()`，不是 Unit 增量设计自动保证的性质。

## 9. 串行阶段：A 完成一段，再执行 B

示例：先全局探索，再局部开发；先连续搜索，再离散精修。

### 9.1 仅切换执行阶段

A 和 B 各自拥有已有状态，阶段切换只决定谁活动。这种串行无须候选传输。

### 9.2 用 A 的结果启动 B

A 提供候选，B 按自己的初始化或接收规则使用。B 的已有 builder / Unit 操作负责结构增量，不需要了解 A 的排序、温度或路径队列。

需要明确选一个候选还是一组候选、哪个已提交版本、是否复用 raw 求值。这里的选择可以是普通配置或现成策略，无需为每一对算法写代码。

### 9.3 阶段完成的计数

使用逻辑提交数、物理尝试数、求值次数或耗时，含义不同。SA 的首个基准评分会消耗一个逻辑步骤，但不进行退火变异和降温；阶段步数不能假装它是一轮邻域搜索。

当前 Chain 的 `_step_in_phase` 在 update 后递增，属于该阶段反馈更新的计数；不要自动等同于任意领域算法的自然迭代数。

### 9.4 切换时的权威与清理

活动阶段已经变成 B 时，最后提交的种群仍可能属于 A。必须区分“当前活动策略”和“最后确认的 population owner”。

退出 A 的资源清理在调度决定生效后执行；清理失败保留债务，不能声称调度从未发生。恢复时先 setup，再恢复阶段状态。

### 9.5 当前实现与边界

Chain 已有阶段、条件推进、最后确认种群所有者和延后 teardown。`_advance_phase()` 本身没有自动执行候选 warm start。

因此“能串起来”已存在；“串起来后自动带上前阶段候选”须单独核对和设计。

## 10. 轮流执行与反复访问同一策略

示例：A 一步、B 一步，循环；或 A/B/C 按固定周期活动。

这与只向前推进的阶段链不同。反复回到 A 时必须决定：

- 继续 A 的私有 Unit 和历史，还是重新初始化？
- A 在不活动期间是否接收其他策略提交的候选？
- 各策略自己的步数是否只在实际活动并提交时推进？
- 停用是否保留资源，还是释放后重新建立？

建议默认继续各策略已有状态，切换不会隐式重置。候选交流单独配置，停用与最终 teardown 分开。

不能只把 Chain 的 `repeat_last` 理解为循环全部阶段；当前实现的它表示末阶段继续活动。

该拓扑可由现有调度策略表达，但本次未逐一验证任意轮转方案的恢复语义。不要为名称相似就宣称已经完整支持。

## 11. 条件路由：这一轮由哪个策略处理

示例：停滞时走局部搜索；高不确定性时走探索；不同区域使用不同策略。

### 11.1 路由条件读什么

建议读取已提交的指标与明确版本。条件不能读取一半更新的兄弟 Unit，再把本轮计算顺序当成“共同快照”。

若条件需要本轮求值后的结果，应该放在求值后的下一阶段决策；不能伪装成求值前已知。

### 11.2 唯一选择与同时选择

“只挑一个”与“激活多个并分配预算”是不同规则。优先级并列、无匹配、全部禁用都需要有确定结果。

无匹配可以显式 idle/stop/默认策略；不能通过捕获异常偷偷换另一个语义。

### 11.3 决策权限

决定搜索策略的是所属组合 Adapter 或声明领域的 Controller。观察 Plugin 不能通过修改共享键暗中改变路由。

### 11.4 任务绑定

repair、disposition、update 必须返回本次产生提案的策略。路由规则在评估期间发生变化，也不能把旧反馈交给新活动策略。

当前 Router 保存原始 task 和 proposal context；全局观测键不能反向覆盖这个事实。

## 12. 区域分工与多个同类型 Unit

示例：三个 SA 分别搜索三个区域，两个种群分工覆盖不同子空间。

### 12.1 区域的性质

区域可以是算法工作范围、软探索偏好或问题硬约束。这三种含义不能混用。

ProblemRepair 保障问题约束；算法区域边界由该 Adapter / Unit 的结构规则保障。只有装配明确声明后，才能启用共同修复和共同验收。

### 12.2 区域移动

区域改变会使局部距离、当前中心关联、采样有效性等特征失效。算法历史是否继续保留由算法规则决定，不能仅更新 bounds 就认为整个状态正确。

### 12.3 同一候选属于多个区域

允许同一候选被多个 Unit 使用；其区域归属是各自关系，不必生成假的新候选 token。不同 Unit 中的偏好值可以不同。

### 12.4 当前实现与边界

Router 把 region_id/bounds 放入 StrategyTask 和局部上下文；这只是正式任务输入。叶 Adapter 是否执行区域约束、接收外来点还是拒绝，仍要看其实现。

不能以“传了 bounds”作为“所有叶算法都在区域内搜索”的证明。

## 13. 候选共享：先说清接收方把它用于什么

这节是整个讨论最核心的接缝。用统一候选消除算法对之间的结构转换后，剩下的是接收方本来就有的搜索行为。

### 13.1 只读参考

B 读取 A 的候选作为参考中心或统计输入，不写入 B 的持久成员。无需 admission；但只读输入须脱离，不能让 B 的原地变异修改 A。

### 13.2 生成提案的种子或父代

B 基于外来候选生成 `y`，`y` 走普通提案、repair、evaluate、disposition、update。B 不需要为 A 的 Unit 提供 codec。

此模式最接近当前任务种子设计，适合作为简单组合的优先落点。

### 13.3 新算法或新实例的初始成员

B 在 fresh 初始化阶段用共享候选创建自己的 Unit。数量不够时补足、数量太多时选择、初始反馈是否存在，都可以复用 B 自己的初始化规则。

初始化行为应在 fresh/restore 顺序中保持明确，不能在 checkpoint 恢复后再次 warm start 覆盖恢复状态。

### 13.4 进入已有 Unit 参与比较

B 已有当前点或种群，外来候选参与替换或环境选择。由 B 的接受/选择规则决定是否进入结构，Unit 统一维护行字段和反馈关联。

若 B 是 SA，不能因为候选来自 A 就跳过本地比较；若 B 是 MOEA/D，则由 B 决定参与哪些子问题，不携带 A 的排序当作 B 的子问题答案。

### 13.5 替换整个结构

这是显式状态装载或重启，影响历史和关系，不能作为普通候选交流的默认行为。

`set_population_snapshot()` 是完整结构恢复/设置面，不自动等于算法的正常竞争接纳规则。

### 13.6 讨论建议

默认优先“参考/种子”，需要竞争替换时使用接收方一次定义的操作。不同用途从装配语义上区分，不强制用户学习六套新组件。

## 14. 岛模型与周期迁移

示例：多个种群独立运行，每若干提交交换少量成员。

### 14.1 发送方负责选择

发送全部成员、精英、随机样本或多样性样本是迁移策略。发送方应基于已提交版本提供只读候选和可用证据。

### 14.2 接收方负责使用

接收方按其既有初始化/竞争选择规则建立自己的增量信息。迁移策略不需要重写接收方未知成员字段的维护。

### 14.3 时机

建议先采用提交边界迁移：所有孩子从同一个可读版本取样，再各自处理。每隔 K 个逻辑提交、每隔 K 次求值和每隔固定时间并不等价，应在配置中表达真实含义。

### 14.4 token 与槽位

原候选身份可保留；接收方成员槽位是新关系。MOEA/D 中同一 token 可以占多个槽位，PopulationView 不能因此拒绝。

如果迁移后产生了新语义候选，来源与新候选身份需沿已有 provenance 规则表达；不能用数值相同自动推断继承。

### 14.5 重复迁移与恢复

“只读同一候选”可重复；“将它竞争插入并改变历史”通常需要确定是否重复生效。应优先依附已有步骤身份、来源版本和 checkpoint 状态判断，避免先新建第二套提交日志。

当前阅读没有发现所有 Adapter 通用的迁移执行面；已有 partition 和成员操作提供基础，但不构成任意岛模型已经完成的证明。

## 15. 共享 Archive、incumbent 与候选池

### 15.1 共享的是什么事实

可以共享已经提交的候选、raw 求值、Pareto 证据和出处。Archive 可以有明确维护者；各 Unit 消费其只读投影。

不要把“最后评估批次”“当前各算法种群”“全局 Pareto 集”和“全局 best”当成同一个集合。

### 15.2 谁维护

归哪个 Adapter、正式 Pareto 管理组件或声明参与能力所有，须以现有实现为准。同一集合不能在 context、Plugin、Adapter 中同时有三份可写权威。

### 15.3 谁决定保留

共享池可以按明确的全局规则保留候选；孩子保留哪些成员仍由孩子决定。共享池不替代每个 Unit 的生存选择。

### 15.4 新候选何时可见

建议本轮开始读提交版本 G；本轮更新后提交版本 G+1，供下一轮读取。这样兄弟遍历顺序不决定谁提前看到谁的新结果。

如果明确希望按 A 更新后 B 立即消费，直接表达为串行依赖，便于理解其算法含义。

### 15.5 当前边界

Router 使用共享 best/策略报告并可以从 Pareto 数值投影挑 seeds。本次未发现该种子路径完整携带语义 metadata/token 的保证：StrategyTask.seeds 当前保存数值元组。

当 metadata 会影响 Problem 或算子时，数值种子与完整语义候选交流必须分开描述。

## 16. 算子组合、候选精修与算法包装

示例：NSGA-II 的变异采用另一个算子；种群候选经过局部精修；已有策略外层增加精英提案。

### 16.1 算子复用

如果只是复用一个变异规则，优先装配具名 mutation operator，无需运行另一个完整 Adapter。算子可显式消费只读 UnitInputs，拿到其声明需要的父代或邻域数据。

算子不接管全局循环，不偷偷求值，不在共享 context 中反向寻找可变 Unit。

### 16.2 运行完整局部搜索

如果精修需要多次求值、多步接受和持久历史，它已经是搜索过程，应由相应 Adapter / Case 的正式执行路径表达。

把完整搜索藏进 `mutate()` 会使预算、取消、事件和恢复边界难以对应。无需把它称为“更复杂的变异”来绕过已有生命周期。

### 16.3 包装器改变提案

改变提案必须发生在普通评估与处置前，保留 repair 对账与提案索引关系。

已有 `EliteRetentionAdapter` 将精英派生候选作为正式提案注入，并检查内层是否允许提案替换。结构绑定的 A* 节点不能因外层“只是换一个值”就保留旧父边代价。

### 16.4 Unit 不变量仍然有效

增量结构让特征维护有明确所有者；它不能保证任何包装器变换都保持算法语义。所有者已经定义的修复或拒绝规则应被包装层复用，而非重新发明。

### 16.5 讨论建议

区分“装配一个算子”和“嵌入一个完整搜索过程”。二者都可组合，但其预算与提交粒度由真实行为决定。

## 17. 多个 Adapter 使用同一个 Unit

这与多个 Unit 使用同一个候选不同。前者涉及对同一可变结构的决策权。

### 17.1 一个写者，多个读者

一个 Adapter 决定种群成员，其他组件只读特征、提供建议或生成候选。写者统一进行选择；PopulationUnit 维护所有行字段。

这个模式可以保持一个结构权威，其他组件无需复制种群。

### 17.2 轮流写同一结构

两个 Adapter 轮流改变同一 Unit。只有它们共同满足该 Unit 的完整维护要求、反馈版本与历史含义时才成立。

Python 继承兼容或字段名相同不足以证明替换安全。可以明确选择同一个结构操作面，逐个验证策略写入，而不是任意共享对象。

### 17.3 同时写同一结构

会出现生存选择、反馈关联、成员字段和缓存的冲突。建议先采用独立 Unit + 候选交流；确有联合决策需求时，由一个共同 Adapter 形成一次决策。

把锁加在数组写入上只能避免部分并发写损坏，不能决定两个竞争选择谁具有语义权威。

### 17.4 对“增量”的限制说明

增量是信息和维护的组织方式。并非每份增量都可无条件拼接进一个共享可变对象；依赖集合和历史的字段仍需要清晰所有权。

本轮不建议为了泛化而新建共享可变 Unit 调度器。

## 18. 嵌套 Adapter：组合器可以继续作为孩子

示例：外层在探索与开发之间分配预算，探索内部是两个种群，开发内部是 SA 与信赖域。

### 18.1 每层只管自己这一段

外层决定孩子活动和预算；内层再分配给自己的孩子。候选反馈沿原提案范围逐层回送，外层不理解叶 Unit 的字段维护。

这种组合可递归，复用已有局部规则。无需为“Router 包 Chain 包 Router”单独定义转换协议。

### 18.2 三套路径分别表达什么

- 实例路径：哪一个实际孩子，供来源与作用范围使用。
- PopulationPartition 前缀路径：权威分区在哪个子树，供持久化与恢复使用。
- 本轮提案范围：哪些根提案属于该孩子，供 repair/disposition/update 使用。

它们互有关联，但字符串形式和生命周期不同；不能拿一个路径字符串直接猜另一种身份。

### 18.3 局部任务不可被全局观测覆盖

StrategyTask 保存本次调用的阶段、区域、配额与来源祖先；孩子回调使用原 task。

`candidate_roles`、`unit_tasks` 等观测摘要可以用于显示，不能成为另一个隐式调度权威。

### 18.4 预算逐层缩减

内层最多消费父层给出的配额。每层额外裁剪须保存映射，与控制面最终 disposition 合成，不能每层各自根据压缩后的 index 猜原提案。

### 18.5 回滚与 checkpoint

父级步骤快照保存自己的局部状态，子参与者由显式 children 注册；不能父快照又嵌入完整子 checkpoint，造成重复恢复同一所有者。

正式 checkpoint 可以完整记录拓扑与孩子状态，但恢复需要稳定身份和顺序校验。未知分区不能被忽略。

### 18.6 当前实现的来源边界

Router 生成 `StrategyOrigin` 并检查任务祖先关系。Composite、Chain 和事件驱动层不能仅因为能转发回调就被认为都会增加同样的正式 origin frame。

因此限定 `apply_to_paths` 时，需核对实际 origin，而不是凭可视化树推断路径一定存在。没有正式来源的候选按现有限定 Bias 规则不适用。

## 19. 事件驱动与真正异步完成

### 19.1 事件驱动调度

事件决定哪些策略提出候选、队列如何补充、完成后产生哪些新任务。可在普通同步 Solver 步骤里实现。

当前 `AsyncEventDrivenAdapter.propose()` 分组读取事件、依次调用策略并汇总候选；update 消费反馈后产生 completion 和 refill。

该命名与事件队列不等于本次源码已实现候选任意乱序到达、跨多个未提交步骤持续在途。

### 19.2 真正异步求值

候选 A、B、C 同时在途，B 先完成。必须明确：

1. B 是否独立提交，还是等整个批次？
2. B 更新 Unit 后，A 依据哪个 Unit 版本解释反馈？
3. 下一批能否在上一批未结算时继续提出？
4. 取消后迟到结果能否进入权威状态？
5. 多次完成通知是否会重复更新历史？

这些问题归异步执行和接纳时序，不能由候选的增量特征自动消除。

### 19.3 避免扩大默认复杂度

建议优先保留“事件决定下一次普通批次”的简单模式。需要候选级乱序提交时，再以具体算法给出提交单元和版本规则。

不要默认让全部 Adapter 同时维护多个在途 proposal；很多现有 pending 结构只对应一轮调用。

### 19.4 实际并发由何处提供

求值后端、Case 并行 runner 和外部 Worker 可以提供真实执行并发，均需消费有效 L0 grant。搜索事件队列不新增授权者。

## 20. 批量求值、并行求值与 Provider 仲裁

### 20.1 评估路径共享

多个 Unit 的候选进入同一控制面后，可汇成一批送给 Problem / Provider。每行保留语义状态、token、局部上下文与来源。

返回结果必须对齐原行；执行顺序不同不能用数值相等反查身份。

### 20.2 批量接口并不必然逐行等价

某些 Problem 的批量行为依赖整个 batch 或评估上下文。能否拆分求值、能否改变批次大小，需要由实际求值语义保证，不能仅以 shape 合法推断。

本轮不假设所有 Provider 都是无副作用纯函数。

### 20.3 仲裁权限

接管评估的 Plugin / Provider 须声明 evaluation decide。多个可处理者的选择是正式评估调度；已选中后失败不能未经声明变成另一种目标计算。

普通多算法组合不需要重新定义求值所有者。它们共享 Problem 含义，Unit 只增加算法结构。

### 20.4 每个候选自己的上下文

repair 与求值需要原提案的局部任务和语义状态，不能把某一个孩子的 role/region 套在全批上。

`individual_id/individual` 只对应当前调用。新候选不能继承上一轮共享 context 里的行身份。

### 20.5 部分执行和预算竞争

预算裁剪、预留竞争、取消可能让提案没有全部求值。所有者通过最终 disposition 对齐 pending；未评估不等于得到失败分数，更不等于参与过生存选择。

## 21. 多 Case 串行与多 Case 并行

### 21.1 独立运行单元

每个 Case 是完整 Solver 或 Trainer，有自己的生命周期与运行身份。Project 只编排这些单元、传递引用和发放资源。

一个 Solver 内的兄弟 Adapter 通常共享一个根步骤事务；两个完整 Case 通常各自有自己的发布闭环，不能自动视为同一代原子提交。

### 21.2 Case 串行

前一 Case 完成并发布权威 Artifact 后，后一 Case 消费声明的输入。数据依赖不能只靠“它写了某个磁盘路径”猜测成功。

例如优化 Case 发布候选结果，另一 Case 明确装载它作为初值。后者的 Unit 构建仍归自己的语义层。

### 21.3 Case 并行

各 Case 从已准备好的输入出发。它们的模型、种群、RNG、结果发布和失败信封相互隔离；有效资源由 Project L0 分配。

有一个 Case 失败时，是否取消兄弟、是否保留成功兄弟的结果，由 Stage 失败策略决定。已完成的外部工作不会因为上层失败自动逆转。

### 21.4 结果汇总

汇总可以比较 raw 指标、选择候选或构建新的 Artifact；不能把各 Case 的私有 Unit 状态反序列化后拼成“统一种群”而不经过语义层。

### 21.5 已有实现

nsgablack `project/project_runner.py` 是共享 BlackBase runner 的语义入口。底座识别 serial、parallel、external、dag 等策略；实际并行走受 L0 控制的执行后端。

子 Case 的 `CaseStage` 当前支持 serial/parallel 以及 fail_fast/continue，不等于 Project runner 的所有策略都可直接塞入该类。

## 22. DAG：依赖就绪才运行

示例：A、B 并行产出，C 等 A，D 等 A 和 B。

### 22.1 控制依赖与数据依赖

控制依赖说明执行先后；Artifact 输入说明数据从哪里来。两者可以共同形成 DAG 边。

BlackBase `DagStagePlan` 合并显式 `depends_on` 与可识别的同 Stage 权威 Artifact 生产者，运行前检查未知节点、自依赖和环。

### 22.2 普通循环不能伪装成 DAG

如果 D 结果又决定 A 下一轮，则表达为新的迭代批次、动态调用或已有循环控制。静态 DAG 本身不能包含环。

### 22.3 失败后代

依赖产物未发布的后代不能按“文件似乎已存在”继续执行。失败/跳过要保留对应依赖证据。

### 22.4 恢复

恢复已成功节点时，要核验其结果和 Artifact 仍属于有效权威发布；只看某条状态字符串不够。当前 runner 有 manifest 恢复与 Artifact 验证路径。

### 22.5 Unit 增量在这里的作用

各节点可以把统一候选或正式结果当成输入，各自构建结构。DAG 无须知道这些结构的内部字段，只须保证引用交付与节点依赖成立。

## 23. 动态嵌套：求值时调用另一个完整 Case

示例：外层优化候选定义模型参数；求值调用 Trainer；Trainer 再调用一个内层 Solver。

### 23.1 外层候选与内层候选可以属于不同 Problem

外层候选可能是超参数或设计变量；内层候选可能是模型状态或求解变量。它们不是因为都叫 candidate 就天然能互换。

这里应通过正式任务 payload、component_overrides、输入 Artifact 和结果 payload 表达问题关系。

Unit 增量减少同一候选语义下的算法转换；不同问题语义间的映射仍属于实际模型/业务含义。

### 23.2 嵌套调用的完整闭环

父 Case 派生子请求及预算/取消控制；子 Case setup、运行、teardown、发布；父方接收完整结果与权威引用，再解释为自己的评估反馈。

子 Case 失败、取消或发布失败不能变成一个没有出处的正常数值。

### 23.3 预算与资源

外层一次 evaluate 可能消耗大量内层工作。外层求值计数与内层 steps/evaluations 不相同，应由子调用预算与结算记录表达。

父来源的 ResourceContext 是有效授权依据；内层不能把 workers 或 GPU 数重置成自己的默认配置，再越过 grant。

### 23.4 恢复不会撤销已完成内层工作

外层步骤失败时，外层 Unit 可以回滚；内层已经发生的求值、已提交 Artifact 和预算消耗属于真实事实。

父方重试是否复用已成功结果，应依赖明确请求身份和权威引用，不能凭参数数值相同就猜内层运行可复用。

### 23.5 当前核对范围

BlackBase `ChildCaseCall/CaseStageRunner` 已有请求、ArtifactBinding、子调用结果、预算与取消结构。已有超级拓扑测试源码覆盖静态 DAG 和动态嵌套的组合；本次未运行。

## 24. 跨 nsgablack / MLBlack 与外部后端

### 24.1 不同语义层共享运行底座

nsgablack 负责优化搜索；MLBlack 负责训练、模型求值与 ML Artifact；BlackBase 负责共享 Project/Case/L0。

跨层编排不要求一个优化 Unit 拥有 Trainer 生命周期，也不要求优化 Adapter 知道某个模型的内部参数装载代码。

### 24.2 外部状态不能假定都是 array

CandidateBatch 可以保留数值投影与语义状态；StateRef 的可传输范围由 Provider 声明。跨进程、跨机器时须使用受支持的物化/寻址方式。

不同 Unit 可以扩展同一个语义候选，但不能把一个进程内 live 引用随意复制到另一个 Provider。

### 24.3 Artifact 交接

DataRef 指向产物，权威交付还需要发布绑定或收据。消费者按正式输入处理，而不是把路径字符串当成“训练已经完成”。

### 24.4 本文边界

本次没有阅读并运行全部 MLBlack 路径，也没有连接外部后端。这里只确认三仓职责与 BlackBase 已读入口，不替第三方服务承诺传输、并发或可复现性。

## 25. ProblemRepair 与 UnitRepair 如何影响组合

### 25.1 两个目的

ProblemRepair 维护问题约束；UnitRepair 维护所属算法结构，也可能改变候选。后者若改变候选，问题可行性要重新验证。

正常提案阶段不需要每个 Adapter 拥有一套完整问题 Pipeline。多个 Adapter 可共享问题管线，各自持有 Unit 与具名算子选择。

### 25.2 增量特征必须对应最终候选

若候选 `x` 被修为 `x'`，依赖 x 的派生特征不能继续声明有效。纯缓存按依赖版本失效；历史关系按所属算法的明确规则验证、重建或拒绝。

例如 A* 的父边代价并非普通可忽略缓存。保留节点身份不等于保留边代价正确性。

### 25.3 共同验收的范围

JointRepairPolicy 是显式开启的协调机制。它验证某个提案所属叶 Unit 与 Problem 的最终版本，不意味着该候选必须同时符合所有兄弟算法的结构关系。

如果 B 以后消费这个候选，B 再按自己的结构规则使用。否则要求 SA 点同时满足另一个信赖域半径，会把组合不必要地绑死。

### 25.4 多个兄弟改变同一个可变候选

建议各自获取候选草稿和独立语义关系。不同 UnitRepair 将数值改成不同版本时，它们是不同候选结果，必须按对应来源送评。

不可先让 A 修、再让 B 原地修、最后把同一行同时声称为两者已验证的版本。

### 25.5 失败处理

修复不能共同通过时默认 stop；retry/advance 必须显式选择。已发生的求值成本保留；未成功共同验收的草稿不能成为新权威。

组合根沿原范围和 owner path 路由失败，不广播，不吞掉某个孩子的失败行。

## 26. 准入、算法选择和成员维护是三个阶段

### 26.1 控制面的准入

BatchDisposition 决定哪些已评估提案允许进入 Adapter.update。FeasibleEvaluationAcceptance 按 raw 约束判断，不受 Bias 软化影响。

### 26.2 Adapter 的算法选择

进入 update 的候选可能仍被 NSGA-II 环境选择淘汰、被 SA 拒绝为当前点、或没能改善任何 MOEA/D 子问题。

**控制面 accepted 不等于最终 Unit 成员存活。** 这一区分也影响共享候选统计、策略奖励和禁忌记忆。

### 26.3 Unit 的成员维护

Adapter 决定保留哪些行或替换哪些槽位；PopulationUnit 维护候选、F/V/token 和声明的扩展字段。

on_members_changed 收到只读 incoming 候选、反馈、token、metadata、provenance 和来源索引。它不重新决定全局预算或策略路由。

### 26.4 当前历史定义不要被组合悄悄改变

现有 TabuSearchBias 的记忆是“已提交步骤中控制面接纳的提案”，不是“最终进入每个种群的成员”。想采用另一种历史含义，须明确声明并提供相应事实来源。

不能仅根据 member hook 是否调用，反推某个候选是否曾被送评、是否被准入、是否进入禁忌记忆。

### 26.5 零接纳与部分接纳

零接纳恢复相关修复子树，再让 disposition 清理本次 pending；部分接纳先整理索引，再投影 UnitRepair 草稿并重验。

成员操作里的 incoming index 是局部坐标，不重新裁剪原 ProposalRepair。Token 保持语义身份，索引保持阶段含义。

## 27. Raw 求值共享与 Unit Bias 的重新解释

### 27.1 原始值和选择值

```text
raw(x, evaluation_conditions)       已发生的 Problem / Provider 求值
selection_A(x, U_A, preference_A)    A 的选择解释
selection_B(x, U_B, preference_B)    B 的选择解释
```

这是解释模型，不是新增存储协议。raw 具有证据归属；两个 selection 可以不同。

尤其不能把某个 Unit 单独保存的 `objectives/violations` 自动认作 raw：当前种群 Adapter 的普通 update 解包的是选择反馈。需要复用原始求值时，应从保留 raw 字段的正式反馈或求值证据取值，核验候选关联和评估条件。

### 27.2 Raw 复用需要什么条件

至少应判断候选语义内容、Problem 版本和含义、数据/场景、评估配置、有效上下文、随机/时间条件以及 Provider 精度条件是否一致。

当前框架没有在本文范围内证明存在统一的“评估等价键”。这些项目是判定依据，不能当作自动完整缓存 key。

同一提案在 repair 前后可以保持 token，而内容版本发生变化；相同 token 也不能替代候选内容校验。历史求值必须对应最终送评版本，不能仅按 token 命中旧分数。

对于有副作用或随机评估，复用策略须由 Problem / Provider 显式支持；token 本身不是结果仍有效的证明。

### 27.3 对 Unit 的偏好

参考种群改变后，候选相对它的多样性分数需要重新形成；无需重新调用昂贵的 Problem，仅重新计算偏好是否可行要看当前反馈投影路径。

本文不宣称已有通用跨 Adapter 的“仅重投影偏好”入口。若需要实现，应复用现有 raw/selection 分离，不增加第二份求值权威。

### 27.4 偏好作用范围

UnitPreferenceBias.owner_path 表达参考 Unit；apply_to_paths 表达候选来源范围。二者独立。

“A 的候选相对 B 的种群打分”完全合理；“只有 B 的候选读取 B”也合理。算法使用哪个偏好取决于装配，不由 Unit 类型自动猜测。

### 27.5 迁移后 origin 的含义

当前 StrategyOrigin 描述本次提案的路由帧，不是永不变化的完整迁移历史。再次提出已有候选时，attach_strategy_origin 会按任务祖先处理旧路由。

如果需要记录长期发送方/接收方历史，应沿已有 provenance 的明确字段或证据来源处理，不能把旧 origin 假装成当前 proposal owner。

### 27.6 跨策略公平比较

不同选择视图在各自算法里有效，但 Portfolio 的公共评分、Pareto 交付和硬可行性必须采用声明的一致视图。

不要把已经加过 A 偏好的分数再当 raw 加 B 偏好，造成偏好叠加却丢失解释。

## 28. 事务、发布与失败的组合范围

### 28.1 一个根 Solver 步骤

根步骤捕获声明的参与者，执行修复、求值、准入和算法更新；提交前失败恢复可回滚结构。

默认不能因为 A 已更新完成，就在 B 失败后对外声称 A 的同根步骤已独立成功。

### 28.2 不回滚的事实

已发生的求值、预算消耗、物理尝试及持久事件保留。RunSession 对这些事实有显式步骤回滚豁免。

外部服务已写入的副作用是否能补偿属于服务的正式协议。Python Unit 快照不能撤销任意远程操作。

### 28.3 正常拒绝与异常不同

一个孩子正常零接纳时，其他孩子仍可能构成有效提交；被拒绝孩子的修复草稿应丢弃，pending 应按本次 disposition 清理。

孩子抛出未处理异常则进入根事务失败路径。正常局部拒绝不能被混同为根异常，也不能反过来把根异常降级成局部无改善。

### 28.4 提交后失败

Provider predecessor 清理、退出阶段 teardown、提交后投影或观察通知失败，应保留已经生效的提交事实，并记录可重试债务或报告。

不能把“已提交但清理失败”重命名为“这一代未提交”，否则重试会重复搜索或预算结算。

### 28.5 多 Case 的边界

各 Case 的权威结果与 Artifact 发布遵守自己的 finalization transaction。某个父 Case 失败，不自动删除兄弟或子 Case 已提交产物。

整组产物需要原子公开时，使用现有发布事务；不要靠后删文件模拟回滚。

### 28.6 当前实现证据

RuntimeParticipant / RuntimeTransaction 与发布底座归 BlackBase。Unit 成员维护保存在 Adapter 的显式 Unit codec 内，无需自己注册一个新事务所有者。

已有测试源码覆盖成员更新后失败、零接纳、部分接纳、Provider COW 和正式 checkpoint；本次未执行这些测试。

## 29. 恢复、拓扑稳定性与已在途工作

### 29.1 恢复顺序

```text
prepare -> setup -> Plugin.prepare_restore -> apply restore envelope
        -> ordinary init hooks -> initialize if fresh -> run
```

新进程先建立必要资源基线，再安装持久状态。不能某个子 Adapter 提前 set_state，随后被 setup 重置。

### 29.2 Unit codec 负责什么

还原候选、算法结构和声明历史；不重新求值，不重新随机构建几何，不调用成员维护钩子把一次旧更新再做一遍。

纯派生缓存按当前依赖重建；历史字段不能按“重新算一下”丢掉。

### 29.3 组合拓扑变了怎么办

孩子增加、减少、顺序改变、binding/schema 改变，都需要明确处理。默认不悄悄重解释旧 checkpoint。

未知分区、重复身份、丢失 owner 不能被静默忽略。一个 Unit ID 相同而 owner_path 不同的对象，仍是两个不同所有者。

### 29.4 候选交流的恢复

恢复已有 Unit 后不能再次执行 fresh warm start；已经生效的迁移不能因读到同一来源版本而重复增加成员年龄或历史。

周期迁移的周期游标属于持久策略状态；共享候选数据引用与接收结果仍沿现有步骤事实保存。

### 29.5 未决评估

事件恢复按 durable evidence 补结算或归档 abandoned，不重新跑 Problem、AcceptancePolicy、repair、Adapter 或成员维护。

如果将来实现跨多个步骤的在途异步任务，需要将任务生命周期接入正式证据与取消协议。本次事件队列检查不能证明该扩展已经存在。

### 29.6 结果恢复与 Unit 恢复不同

已发布最终结果通过正式引用与发布证据恢复；Unit checkpoint 用于继续搜索。不能把一份结果矩阵直接充当完整运行恢复信封。

## 30. 资源授权、并发层级与活性

### 30.1 多策略不是新资源授权层

角色数量、Unit 数量和提案预算不产生线程/GPU grant。只有 Project-level L0 分配有效 ResourceContext；Case runtime 声明需求和记录 audit。

### 30.2 三层并行可以嵌套，但额度不能重复消费

Project 运行多个 Case；某 Case 批量并行评估；一次评估又调用内层 Trainer。每层须服从父来源额度和取消控制。

不能每个孩子各拿“默认 4 workers”就认为总额度仍是 4。

### 30.3 等待中的父任务

父任务等待子任务时是否仍占用资源，涉及底座调度。若全部额度被等待者占据，子任务可能无法启动。

这类问题应通过现有 grant/lease/fanout 与具体调度行为核验，不在 Adapter 内私自增加线程池解决。

本次没有执行压力测试，不能宣称任意深度和额度组合均不会发生资源饥饿。

### 30.4 停止条件

逻辑步骤预算、物理尝试保护、求值预算、deadline 和取消是不同退出条件。全部候选拒绝时仍应受 attempts/deadline 限制，避免逻辑步数永远不增长而无限循环。

阶段切换、修复重试和子调用必须复用现有取消与 deadline，不能各自重置“剩余时间”。

### 30.5 超时后的清理

取消信号发出不代表所有线程/外部任务已停止。Late result、heartbeat 关闭和引用释放须有正式结果或清理证据。

算法 Unit 可恢复，不代表活 executor/session 能被 codec 恢复。

## 31. 观察、报告、成本与可复现性

### 31.1 观察权限不等于观察免费

日志、数据库写入、图导出、Snapshot 保存可能产生显著成本。ParticipationContract 区分作用域权限，不自动提供执行成本上限。

优先通过已有 Plugin 开关、采样频率、后端配置和资源需求控制成本，不因为成本问题立刻再建一套权限系统。

### 31.2 报告必须显示有效行为

应能看出本轮实际活动的策略、分到的配额、实际送评数量、控制面接纳数量、算法结构更新结果和权威分区。

算法成员最终存活数与控制面 accepted_count 不一定相同，应按已有正式事实区分。

### 31.3 Context 的位置

StrategyTask 和算子输入是一次调用的局部数据；ContextStore 是注册键的共享命名空间。完整种群、历史、长 trace 和全部语义候选应保存在所属状态或 Snapshot 中。

交流协议不能因“不想写桥接”就退化成任意共享大字典。读取一个正式候选投影仍应知道来源和版本。

### 31.4 RNG 与顺序

每个实例维护自己的 RNG 状态。共享一个可变随机算子对象会共享它的随机历史；需隔离时显式实例化。

逻辑分支顺序、实际并发完成顺序、预算裁剪顺序和集合遍历顺序都可能影响结果。配置固定不等于自动保证完全可复现。

### 31.5 应先选择什么保证

建议优先保证身份、反馈、任务、结构和恢复一致；再根据算法需要声明固定顺序或确定性执行。数学正确性、收敛和性能优势仍需要相应实验，不由 Doctor 证明。

## 32. 三个完整例子，把上面的规则连起来

### 32.1 NSGA-II -> SA -> MOEA/D：同一 Problem 下的候选流转

这里描述建议的装配行为；当前 Chain 不自动完成全部候选交接。

1. NSGA-II 运行自己的 PopulationUnit，得到已提交候选集合及求值证据。
2. 配置一个现成或明确选择规则，从该版本取一个候选 `x`，作为 SA 的初始参考/当前点来源。
3. SA 使用自己的 TrajectoryUnit 表达当前点和候选关联评分，不携带 NSGA-II 的 rank/crowding。
4. 按当前 SA 路径，未评分当前点通过普通步骤评估基准，不变异、不降温。若希望直接复用 raw，须有正式且已验证的求值复用/反馈安装路径，本文不假装它已经存在。
5. SA 提出邻居 `y`，ProblemRepair 和结构对账确认最终版本，求值后按 SA 规则比较。
6. SA 已提交的 `y` 可以提供给 MOEA/D；MOEA/D 的候选用途是竞争子问题，而非整组覆盖种群。
7. MOEA/D 使用自己的权重、邻域和理想点，决定替换哪些槽位；同一 `y` 可进入多个槽位而保留同一候选身份。
8. PopulationUnit 维护 X/F/V/token 与所有声明的扩展成员字段，接收方 Adapter 不猜 age/父代标签的含义。
9. 结果按自己的权威范围发布；接收失败不会反向破坏发送方已提交 Unit。

这条链不需要 NSGA-to-SA、SA-to-MOEAD 两个结构转换器。需要一次定义的候选选择与接收用途，以及普通运行闭环。

### 32.2 两个 NSGA-II 和一个 SA：同轮部分接纳

假设两个种群分别为 L/R，SA 为 S，全部是独立实例。

```text
根原提案：L0 L1 R0 S0
预算送评：L0 L1 R0
raw 准入：L1 R0
L update：[L1]
R update：[R0]
S：未送评，本次 pending 按 disposition 对齐
```

逐步判断：

1. L、R、S 的算法 Unit 可以相同 ID，但实例路径不同；不能复用同一可变 Adapter。
2. S 没有得到求值，不能安装分数或降温，也不能被记为一次退火比较。
3. L、R 收到准入候选后仍分别做环境选择；L1/R0 可能不成为最终成员。
4. 如 L 正常无改善，R 有有效结构更新，根步骤仍可以提交；是否推进 L 自己的活动计数按其策略定义。
5. 如 R 在结构更新后抛出异常，根事务恢复 L/R/S 的可回滚状态，保留 L0/L1/R0 的实际求值和预算消耗。
6. Snapshot 保存 L、R 的独立 partitions；S 的轨迹状态通过其 checkpoint 保存，不冒充 population。
7. 如果存在全局多样性偏好，应明确参考哪一个 Unit 或哪个正式共享集合；不能把 L/R 两个权威种群随便拼接后称为一个 Unit。

这里必须区分根逻辑提交、子策略活动、控制面准入和最终成员存活。它们不能全部显示成同一个 generation 数。

### 32.3 静态 DAG + 动态嵌套 Case

```text
Project DAG：基础优化 Case -----\
                              -> 外层优化 Case
             基础训练 Case ----/

外层的一次 evaluate：
  -> 动态训练子 Case
       -> 内层优化子 Case
  <- 模型/求解 Artifact 与正式结果
<- 外层 raw feedback
```

逐步判断：

1. 基础两个 Case 的执行关系与 Artifact 依赖由 Project DAG 表达，资源由共享 L0 发放。
2. 外层等待权威发布的输入，不能仅看到输出路径就开始。
3. 外层 Unit 围绕外层候选维护结构；它不保存 Trainer 的生命周期和 executor。
4. 动态子调用通过正式请求携带参数、override、ArtifactBinding、预算和取消控制。
5. 内层优化的候选属于内层 Problem；外层超参数不是同一个候选对象，无需强行套同一个 Unit。
6. 子结果通过正式语义映射成为外层 raw feedback；外层再形成自己的选择视图。
7. 外层 update 失败时，外层结构回滚，内层真实运行成本和已发布产物保留。
8. 外层恢复只对账 durable evidence，不盲目重新训练。需重试时按已定义请求与结果规则处理。

Unit 的增量设计保持各搜索结构清楚；共享 Case 底座保持跨运行单元的交付和授权清楚。两者相互配合，不承担对方职责。

## 33. 尽量保持用户装配简单，而不是让每种模式多出一套组件

### 33.1 使用已有算法

写 Problem 和问题 Pipeline；选择现成 Adapter；启用所需 Bias/Plugin；选择现成组合器与普通参数。

默认 UnitBinding 可由 Adapter 提供。用户没有自定义结构需求时，不必再写 Unit、builder、codec 或成员钩子。

### 33.2 新算法沿用现成结构

复用 PopulationUnit、TrajectoryUnit、CandidateUnit 等；实现自己的提案、反馈消费、决策与必要历史。

结构编解码和回滚优先复用 UnitBackedAdapter / 对应基类。不能承诺只写两个方法就完成所有有状态算法，但不应要求作者重写证据状态机。

### 33.3 扩展成员字段

声明 member_fields 和维护规则；让现有结构操作统一携带 incoming 证据。

一个 age/tag/父代字段的维护定义应能供 NSGA-II、DE、MOEA/D 的相应成员操作复用，无需在三个 Adapter 里分别猜它。

### 33.4 算法间候选交流

组合装配应尽量只需要表达：来源、选取方式、接收用途、发生时机。反馈复用条件由正式评估面处理。

这是配置含义的建议，不是要求新建四个类。简单情况可以用现成选择规则或显式调用；复杂情况再考虑抽公共面。

### 33.5 避免反向过度拆分

如果每增加一个算法就必须自定义 Problem、Pipeline、Unit、Adapter、Bias、Plugin 六套类，即使其中四套没有独有语义，也说明默认装配还需要收敛。

本轮不为每个章节创建一个协议，不为每种组合创建一个目录，也不要求全部用户理解事务底座后才能起步。

## 34. 当前实现可以确认什么，不能确认什么

### 34.1 可以确认的基础

- UnitBinding 绑定构建、schema、codec 与可选 runner；恢复通过 codec，不重新随机构建。
- PopulationUnit 维护成员及扩展行字段；DecompositionUnit 等复用基础种群结构。
- UnitBackedAdapter 将显式 Unit 状态接入 checkpoint 和步骤恢复。
- Composite 保留孩子提案范围，并转发 repair/disposition/feedback。
- Router 提供角色、多实例、预算、区域、阶段、任务与来源。
- Chain 提供阶段推进、最后确认种群所有者和提交后退出清理。
- PopulationPartition 提供嵌套命名空间与恢复校验，不强拼异质权威种群。
- Raw 与 selection 分离，硬可行性按 raw 约束接纳；Unit 偏好支持参考与候选范围分别绑定。
- BlackBase 提供 Project serial/parallel/external/DAG 和正式子 Case 调用面。

这些是源码观察，不能扩张为所有算法在所有组合下均已验证。

### 34.2 明确的实现边界

**边界 A：阶段切换没有自动候选 warm start。** Chain._advance_phase 负责索引和退出清理，不负责上一阶段结果注入。

**边界 B：数值 seeds 不是完整语义候选交付。** Router._select_seeds 从 Pareto/best 数值投影取值，StrategyTask.seeds 保存数值元组。

**边界 C：种子被传入，不代表叶 Adapter 消费。** 本次全文搜索标准 NSGA-II/SA/MOEA/D 路径，未看到它们读取 StrategyTask.seeds / KEY_SEEDS 的正式逻辑。自定义算子可能使用局部上下文，需按具体装配核对。

**边界 D：同轮反馈归原所有者，不自动跨所有者广播。** Composite/Router 的 update 分片属于原 proposal，不能直接追加外来行。

**边界 E：统一反馈复用与仅偏好重投影没有在本轮确认。** Raw/selection 分离提供正确基础，但不等于已有通用服务完成跨算法复用。

**边界 F：来源声明在各组合层的覆盖不完全等同。** Router 正式附加 origin；其他层的局部 context/partition 前缀不自动成为 origin frame。

**边界 G：逻辑多分支与事件队列不等于真实乱序异步提交。** 已读组合 propose 路径依次调用孩子，不能仅看类名做并发承诺。

### 34.3 源码与文字的张力

`multi_strategy/adapter.py` 顶部使用“parallel cooperation”表述；其 propose/update 路径在本进程依次调用孩子。准确解释应是同轮多策略合作；真实求值/Case 并发由执行后端提供。

用户与上一轮回答讨论的是“无逐对转换的统一候选交流”。当前组合器不都等于候选接收器；这属于设计目标与实现覆盖的差距，应明确报告。

这些边界不证明 Unit 思路错误，也不证明每项都必须改代码。若只要求独立组合，很多已有行为就足够；若要求默认自动协同，应以具体验收补接收路径。

## 35. 用行为例子作为收口判据

下面是建议验收清单，**本次没有执行**。优先把现有测试与具体场景复用起来，缺哪条才补哪条。

### 35.1 候选与实例

1. 同类型、同 Unit ID、不同 owner_path，成员和偏好互不污染。
2. 同值不同 token，不能按数值相等合并来源。
3. 同一 token 占多个 MOEA/D 槽位，视图和恢复合法。
4. metadata 不同但矩阵相同，送评和迁移仍保留语义差异。
5. 不同实例意外共用同一可变 Adapter，在装配时拒绝。

### 35.2 调度与来源

6. 父配额裁剪 + 根预算裁剪 + 非连续准入，孩子收到正确局部索引。
7. 已发送提案期间路由条件改变，旧反馈仍交给原任务。
8. 三层嵌套的同名角色/同类型孩子，origin、partition 和 callback 分别对齐。
9. 无匹配、全部停用、零提案有明确 idle/stop/默认行为。
10. 末阶段 repeat_last 不被误当作回到第一阶段。

### 35.3 候选交流

11. A 输出候选作为 B 的只读父代，B 原地变异不改变 A。
12. B 使用外来候选后正确维护未知成员字段，不让 Adapter 猜字段。
13. Fresh warm start 生效一次，checkpoint 恢复不会重复注入。
14. 部分迁移失败不污染发送方已提交 Unit。
15. 同一语义候选在 B 的 Unit 偏好与在 A 不同，raw 证据不被覆盖。

### 35.4 修复与事务

16. ProblemRepair 改值后，结构 owner 重建、验证或拒绝，未对账不求值。
17. 正常拒绝孩子与兄弟提交并存，拒绝子树不留下修复草稿。
18. 某孩子更新后另一个抛错，根结构回滚但求值和预算保留。
19. 提交后清理失败保留提交，不重放已发生的搜索。
20. 三种 index 空间分别正确，成员 incoming 不重复裁剪。

### 35.5 Case 与资源

21. DAG 只有依赖 Artifact 权威发布后才激活后代。
22. 并行 Stage 某孩子失败，兄弟结果按声明策略保留并完整 join。
23. 动态嵌套遵守父 grant/deadline，预算没有层层重置。
24. 外层回滚时不把内层真实成本抹掉，不擅自重新训练。
25. 迟到/重复结果不会重复更新 Unit 或伪造逻辑提交。

现有测试入口包括 test_strategy_task_contract、test_composite_population_authority、test_unit_member_composition、test_joint_repair_orchestration、test_unit_scope_and_member_inputs、test_sa_adapter，以及 BlackBase 的 test_project_dag/test_case_stages。存在测试不代表覆盖这 25 项的全部参数组合。

## 36. 和用户优先讨论的决定

### 问题一：普通协同的默认接收用途

建议默认提供参考/种子；需要让外来候选竞争进入现有 Unit 时，显式选择接收方已有接纳行为。

理由是它保持简单，也避免“只想参考一下”却隐式改变种群和历史。若用户希望默认就是竞争插入，可将其作为产品默认，但仍须清楚表达行为。

### 问题二：同轮孩子是否看见兄弟本轮更新

建议默认读取同一已提交版本，提交后下一轮可见。希望即时串联时，用明确串行依赖表达。

这样一次配置可以解释行为，避免 Python 遍历顺序变成隐藏算法思想。

### 问题三：是否默认保存完整语义候选作为 seeds

建议需要共享候选本体的路径保留语义/token/provenance；纯数值父代工具可以使用矩阵投影，但明确它不承诺完整语义交流。

应在现有 CandidateBatch/UnknownState 体系内讨论，无需先发明新的 SeedCandidate 类型。

### 问题四：Raw 复用如何定位

建议视为 Problem / Provider 的显式评估能力，在有效条件一致时复用。Unit 偏好继续按当前参考结构形成选择视图。

不要用算法之间的私有 shortcut 安装没有证据关联的 F/V。

### 问题五：组合提交的默认粒度

建议一个 Solver 保持现有根步骤事务；需要独立成功/独立失败的策略运行时，优先使用完整 Case 的边界。

候选级异步独立提交作为明确高级模式，等具体使用需求出现再决定接口。

### 问题六：结构状态是否默认跨算法转移

建议默认只交流候选及适用的求值证据，各自维护增量关系与历史。要共享路径、动量或子问题归属时，明确其算法含义。

这保持“接入一次、组合多次”的优势；不会强迫发送方学会所有接收算法的内部结构。

这六项并不是要求用户每次装配回答六道题。产品应提供可解释的默认值，用户只有偏离默认时才配置。

## 38. 后续确认：解池先创建，算法从具名区域访问候选

后续讨论确定了一个比第 13 节更统一的入口：初始解先有存放位置，每个 Adapter 从这个位置访问解，再用自己的 Unit 搜索。因此，“候选交接”收敛为池引用与选择时点，不再要求把前一个算法的完整 Unit 传给下一个算法。

本轮用户已明确授权实现与验证。下面描述实际落地；运行规则以 [解池契约](SOLUTION_POOL_CN.md) 为准，执行结果见 [本轮验收](SOLUTION_POOL_VALIDATION_CN.md)。

### 38.1 与 Context / Snapshot 的关系

解池是算法可读的存放区域，不另造一个大对象 context。SolutionPool 用共享 SnapshotStore 保存 CandidateBatch 和版本；context 只有 manifest、时间、input selection ID 与模式。Unit 的排序、温度、父路径、参考方向等增量信息仍属于各算法。

这样，用户只需知道“从哪个区域、哪个时点取得哪些候选”，不用管理底层对象图。每一种组合都能围绕同一个存取动作讨论；是否选择精英、分批、采样或按区域筛选，仍是明确的搜索策略。

### 38.2 再回答第 13 节

池提供的是候选值与来源版本。B 可以把它用于初始化或新提案，也可以让它参与自己的成员竞争；两种用途由输入模式明确表达。

- `initialize`：接收算法从指定 refs 建立自己的结构，候选仍经过 repair、评估、Bias 和接纳。
- `compete`：候选参加接收算法的现有成员选择，不强行替换整个 Unit。
- “把 A 的试探候选继续变异后送评”可由 B 的 propose 组合池读取与自身搜索算子表达；本轮 PoolSearchAdapter 不把所有用途自动揉进一个输入模式。

这没有要求 B 理解 A 的状态，也没有取消 B 自己的选择规则。

### 38.3 用户举出的 200→100×2→停滞唤醒

PoolSearchAdapter 以单解 producer 的接纳提案准备池内容；按 ready_stamp 锁定 200 个来源，两个种群各取 100 个，分别构建 Unit。producer 等待时不降温。两个种群的停滞观测触发显式 producer 重启；它从池中读取一个种子，继续搜索，再把新发布的候选分别提交给两边竞争。

同样的候选可在两边形成不同排名与关系。两个种群各有私有 Unit，不拼成 200 行的伪统一种群。停滞是指定指标的触发条件，不能解释为已经证明局部最优；“启动恢复”也不能解释为保证跳出局部最优。

上述 200→100×2 是一项示例计划，不是所有算法的统一大小契约。解池没有 `population_size`；编排的 `initial_count` 取解配额与各 Adapter 的成员容量独立。A 可以取 120 个选留 100 个，B 可以取 80 个保留 80 个；超额准备的候选仍留在池中。标准 `build_solver()` 不需要统一指定这个大小，详细行为见正式解池契约第 6 节。

### 38.4 变异和修复为什么不能直接改池里的旧解

候选来源版本应能被重读、checkpoint 对账，也可能正在被其他 Unit 使用。原位改写会让另一个算法的反馈与关系突然过期。

所以，读取保留身份；新调用的提案显式派生 token，并保留父 token 与源 SolutionRef；repair 同一提案保留该提案 token，但使用新的内容版本。Unit 使用脱离的工作数组；派生特征仍按已有版本与成员操作规则维护。

这不是改变候选的表示结构，也不是为槽位编造身份，而是区分“已有解”和“以它为来源的新搜索动作”。

### 38.5 本轮做到哪里

公共 Solver 候选帮助函数与控制面绑定已池化；池索引、输入游标和 manifest 纳入原步骤事务与正式 checkpoint。NSGA-II/III 声明初始化与竞争，SA 声明显式搜索重启。标准脚手架提供可选装配工厂，正式 Project 示例实际装上这些组件。

其他 Adapter 不能因有 Unit 就被假定支持这个特定策略。Unit 的内置数值工作投影也没有全部改成 ref-only。CPU 同时执行、多 Case 并行、资源和 Artifact 交付继续走 BlackBase；PoolSearchAdapter 只拥有优化阶段与搜索决定。

### 38.6 后续讨论应从行为出发

剩余组合可以用相同的几个具体问题讨论：候选来自哪个区域/时点，读已有值还是产生新提案，进入当前点还是成员竞争，未接纳时如何继续，什么观测触发下一阶段。先用可运行例子验证已有词汇是否能表达，再判断是否需要新概念。

每增加一种具体算法支持，补它的输入、结构不变量、接纳和恢复行为测试；不再仅凭“候选统一”宣称所有交接都已经验证。

### 38.7 长期淘汰且无人使用的候选可以回收

用户确认池只是一处抽象的存放区域，同时需要释放长期无人使用的解。实现用 PoolRetentionPolicy 显式开启按提交步数的闲置宽限期，并区分算法成员淘汰、退出当前池索引与底层 Snapshot 删除。

A、B 同时使用 x 时，只要一方还持有，x 就不能回收。未消费输入和已声明的未来阶段引用同样保护候选。释放所有引用后达到闲置阈值，池可压缩该批次的值；原始 row/token 保留。失败步骤恢复成员、池索引、年龄与引用，物理删除始终在提交之后。

初始化多少解和以后何时注入随机解，仍是初始化与搜索编排策略，不属于池容量。串行路由是否让 A 落选候选进入 B，也仍由路由声明决定；池保存不代表必定转交。并行分支分别持有来源，成员关系互不删除，结束后独立释放。

历史恢复同样需要明确寿命：最近发布窗口或显式 pin 保留完整值闭包；窗口外未固定的旧池 manifest 允许失效，可传输 checkpoint 自带候选值。未决权威提交临时固定 prepared 值闭包，到按持久证据确认恢复后再释放。完整接口、组件接入范围与存储限制见正式解池契约第 9 节。

### 38.8 子池把多角色精修接入既有路径

后续确认的“GA 找到 20 个起点，交给不同 VNS 精修，再返回成员竞争”已收敛为 `RoleSpec.pool_task=PoolTaskSpec(...)`。子池是引用集合，多角色 Router 继续决定阶段和预算；任务包装负责选择、输入游标、逐起点搜索重启、输出和恢复，不再要求为 GA/VNS 这一对另写专用组合器。

取解默认进一步明确：不指定 select 时使用母池，指定输入子池必须存在；初始化按各 Adapter 声明数量独立抽样，每群内部不重复、群间允许重叠。因此 300 个来源可以初始化 30 个 100 成员群体，Unit 仍各自独立；要求群间互斥时显式 partition，要求同批起点时显式 shared。SA/VNS 精修默认每实例一个起点，整批排队须 count="all"。不足时默认报错，也可声明 wait/available；不会暗中生成新解补足。已完成初始化的实例继续普通算法，不随每次调度重抽种群。具体参数与恢复约定统一见 SOLUTION_POOL_CN.md 第 10 节。

Unit 仍保存各算法增量结构；共享的是候选引用与来源。VNS 先评估起点再比较邻域，返回的是新候选本身及其反馈；返回种群自己决定成员替换。完整接口、阶段语义和支持边界见解池契约第 10 节，正式例子为 `pool_refinement`。这条通用路径尚不等于 MOEA/D 的子问题比较与槽位绑定已经完成。
