# Pool 与 Adapter 的最小完善方案

日期：2026-10-20。状态：**两个闭环已落地，本文保留最小范围与验收理由**。

当前签名见 [接口手册第 10–11 节](POOL_API_REFERENCE_CN.md)，
三 Case 真实运行及恢复验证见 [正式 Project](../../examples/cases/pool_workflow_pilot/README.md)。
下文的“需要补齐”描述设计动机，不代表这些接口现在仍未实现。

需要查看具体方法、返回值和用法时，先读 [Pool 与 Adapter 接口手册](POOL_API_REFERENCE_CN.md)。本文件保留实施范围与验收理由。

后续讨论进一步收敛了 [统一 Pool 数据结构与基础操作](POOL_DATA_MODEL_AND_OPERATIONS_CN.md)：
选择规则采用 Pool → Pool，本文的批量交付与事务内维护仍是实际接入闭环，不额外建立新运行体系。

本文承接 [Pool 集合操作](POOL_COLLECTION_OPERATIONS_CN.md) 与
[池驱动变化编排](POOL_CHANGE_ORCHESTRATION_CN.md)，回答一个问题：

> 为了让用户自然装配常见算法，接下来有哪些内容必须完善，哪些可以停止扩展？

本文不扩大 Problem → Pipeline → Unit → Adapter → Bias → Plugin 的职责体系。
Pool 保存候选版本与引用关系；Unit 保留算法结构；Adapter 拥有行为时序与搜索决策。
下一步集中补齐两个使用闭环，继续复用现有身份、修复、评估、接纳、事务和恢复机制。

## 1. 判断“必要”的标准

一项扩展至少要回答下面一个具体问题：

- 缺少它，用户表达普通算法时，是否必须修改框架源码或伪造一个无关动作？
- 缺少它，候选身份、反馈、接纳结果或算法状态是否会发生含义不明的交接？
- 同一需求是否正在多个 Adapter 中重复实现，且可以通过已有契约收敛？

只让代码短一点、为未来所有可能情况预留位置、给已有操作增加别名，暂不构成新增机制的理由。
已经存在的底层能力，应先补实际消费位置和使用示例，不再建立平行实现。

完成标准是能表达、能执行、能正确恢复，而不是每个 Adapter 都拥有相同的固定流程。
初始化、变化、选择、修复继续是行为类别；算法决定调用次数、条件与顺序。

## 2. 当前已实现什么

以下是本次静态核对的源码事实，不是本文的新增设计：

- `ChangePool/ChangeSelection` 已提供只读选解、筛选、显式排序、分组和集合运算。
- `SolutionPool` 已提供普通子池的成员替换、增删与裁剪，保留 view_id 并按实际变化推进 revision。
- `ChangeResult.edits` 已通过 `PoolEdit` 表达成员计划；`outputs` 把接纳提案交付到普通集合。
- VNS、MOEA/D 已支持完整的普通 change 函数；函数调用仍返回一个候选。
- NSGA-II 原有父代选择、mutator、生存选择等装配位置，本轮已接通完整 change 角色及派生的 NSGA-III/SPEA2。
- 子池、投影、逻辑时间、任务游标、步骤事务、保留策略与 checkpoint 已经存在。

主要实现入口：

- [普通变化函数桥接](../../adapters/change.py)。
- [调用内池访问、ChangeResult 与 PoolEdit](../../adapters/change_pool.py)。
- [接纳后输出与成员计划发布](../../adapters/change_outputs.py)。
- [SolutionPool 数据与成员操作](../../core/state/solution_pool.py)。
- [NSGA-II 实际行为装配](../../adapters/nsga2/adapter.py)。
- [控制面求值、update 与发布顺序](../../core/composable_solver.py)。

现有状态与目标之间的差距，集中在下面两个闭环。

## 3. 必要闭环一：在现有步骤事务内维护池

### 3.1 用户要表达什么

一个常见需求是：

1. 取出已有精英。
2. 加入本轮新评估且已通过硬接纳的候选。
3. 按明确比较规则选出最多 20 个。
4. 更新精英集合。

这份选择代码只决定成员，不需要自己生成候选、修复或调用 Problem。
它也不应该依赖“某个恰好携带编辑指令的新孩子被接纳”才有运行意义。

### 3.2 当前为什么不够自然

当前 `ChangeResult` 必须包含一个 candidate，成员计划附着于提案 token。
完整 change 在评估之前执行，只能读取调用开始时已发布的数据。
因此，现有示例可以整理上一已提交帧的精英，但不能在同一次普通 change 调用中使用随后才产生的反馈。

底层并非不能实现这些需求：自定义 Adapter.update 可维护本步成员，
`SolverSemanticExtension.before_step` 也能在事务内手写维护旧数据。
缺少的是普通选择函数的自然装配位置。
现有 `after_step_committed` 已晚于提交，不能用于补写同一 Authority Snapshot 的 Pool manifest。

### 3.3 最小改动范围

在实际拥有该行为的 Adapter 中，接通可装配的成员决策位置。
它接收只读数据与精确引用，返回成员计划，由原步骤事务发布。
正式方法名、请求类型和绑定签名在实施时确定；本文不提前规定新的公共 API。

已有算法选择位置应优先扩展，而不是再加一次选择：NSGA-II update 已有生存选择，
可复用 SelectionRequest/set_selector 并补精确引用、Pool 与位置映射。
历史档案与算法留存是不同决定；若需要每批维护档案，由真实 update 路径明确调用一次。
不能按 selector 调用次数触发，因为 VNS 基准阶段与 MOEA/D 多槽位竞争的次数并不一致。
这属于既有行为装配的接缝完善，不建立新的调度器。

必须满足：

- 维护旧数据时读取此前已发布的候选版本。
- 使用本步反馈时，由控制面显式交付本步已接纳的精确引用及其对应反馈。
- 交付内容只包含当前消费者实际归属的子集，仍服从 Adapter/PoolTask 输入声明、调用内可见范围和明确的目标集合声明；不得读取兄弟任务数据或扩大祖先授权。
- 不为此放开普通 ChangePool 对任意 pending 候选的读取。
- 比较规则由用户或实际算法明确提供，不能把“精英”解释成默认目标求和。
- 复用现有成员 API、PoolEdit、目标身份/revision 校验与事务。
- 函数本身不持有可写 Solver、共享 Unit 或 Provider/session。
- 维护失败时回滚本步算法状态、池成员和发布游标；已经发生的求值与预算消耗保留。

现有 selector 的生存选择、槽位替换等用途继续保留。
新位置负责普通集合成员决策，不获得修改任意算法结果视图的权限。
普通函数的身份、随机性和可恢复状态沿已有绑定机制管理，不引入隐藏可变闭包。

### 3.4 提交与计数边界

**本轮只提供附属于现有搜索步骤的维护。**

- 同一步维护一个或多个集合，都只按原 StepOutcome 计一次逻辑提交。
- 维护本身不增加求值次数，不另推进 generation，不重复触发代钩子。
- 本次没有提案、预算不足以评估或零接纳时，继续服从原步骤的 idle/rejected 语义，不单独发布维护结果。
- 正常搜索步骤提交失败，维护一并回滚。
- 已提交后观察通知失败，不能撤销已经发布的成员与逻辑计数。

这里的“独立”指选择代码独立于候选生成函数。
**任意时刻只整理池、没有可提交搜索步骤也能发布**，是另一项能力，本轮明确暂缓。
不能通过制造虚假候选、补一次无意义求值或改变 idle 的含义来模拟它。

### 3.5 同目标写入的边界

新维护位置可能与现有 `ChangeResult.edits/outputs` 同时存在。
实施时必须保持单一、可解释的成员决策：

- 同目标不同替换计划明确冲突。
- 同一步对同目标追加输出并替换成员，继续明确拒绝。
- 不使用隐式“后写覆盖”消除冲突。
- 若允许合并相同计划，必须按冻结目标和精确成员顺序判断一致。

不为精英、禁忌、候选档案分别建立新的生命周期或事务体系。
是否能共享成员决策位置，要由各自实际输入、时点和更新规则验证。

## 4. 必要闭环二：一次变化产生多个后代，并由 GA 实际消费

### 4.1 用户要表达什么

例如从池 A 取父解 a，从池 B 取父解 b，一次交叉产生 c1、c2，
随后分别变异，交给现有修复、评估和接纳流程。

两个孩子可以共享交叉时使用的随机选择，也可以分别保留不同的父来源。
把一次交叉拆成两次无关联函数调用，不能普遍保持这份含义。

### 4.2 当前接口的边界

当前普通 change 桥接一个候选的变化；`ChangeResult.outputs` 表示这个候选进入多个目的池。
它不表示一次返回多个孩子，也不能通过把二维矩阵塞入 candidate 来冒充批量提案。

Adapter.propose 本身可以提出多个候选。
需要补齐的是普通变化函数到已有批量提案路径的交接。

### 4.3 最小契约

批量返回必须明确：

- 每个后代的候选值。
- 每个后代各自的源引用；同一次调用不意味着每个孩子使用完全相同的父解。
- 每个后代的输出目的地及其原始提案坐标。
- 实际消费者允许的提案数量；不能因为普通函数返回更多就绕过算法预算。

每个后代派生自己的提案身份；repair 仍保留该提案 token。
反馈、来源、输出目的地与 Adapter pending 状态始终按同一原始坐标对齐。
需要保留重数的方向或槽位，不能因为候选引用相同就全局去重。

预算裁剪、评估、硬接纳和 BatchDisposition 继续走原控制面。
父来源证据复用既有约定，不自动变成永久保留根。

### 4.4 部分接纳的默认含义

**两个孩子默认独立接纳。**

例如 c1 被接纳、c2 被拒绝时：

- 只发布 c1 对应的接纳版本及其目的地交付。
- 不把 c2 的来源、反馈或输出指令错配到 c1。
- Adapter 根据最终处置对齐自己的待更新结构。
- 非前缀接纳与预算截断仍能追溯原提案位置。

本轮不新增通用的成组原子接纳协议。
已经具有配对、路径或几何依赖的算法继续使用原生校验，不能靠批量外观绕过这些约束。

### 4.5 GA 接入是消费位置完善

NSGA-II 需要实际消费完整变化函数，才能验证用户是否可以安排：

- 先交叉、后变异。
- 先变异、后交叉。
- 跨池取父代。
- 一次返回多个后代。

这项工作不要求再定义一种 GA 基类。
未装配新行为时保留原生配方；装配后不能又静默执行旧交叉或旧变异。
已有直属 mutator、具名 Pipeline mutation 与完整 change 的互斥语义需要同步保持。

不同 Adapter 仍有不同的输入参数、输出数量和合法操作。
统一输入输出与身份规则，不承诺任意函数可以无条件装进所有算法。
不适配的绑定应在装配或实际调用时明确拒绝。

## 5. 三条需要保护的已有语义

### 5.1 入池不等于被算法保留

通过硬接纳的试探解可以进入普通输出集合，但可能没有成为当前点或种群成员。
“母池可读取”“进入精英集合”“被算法保留”具有不同含义。
结果交付继续区分接纳提案集合与所属 Adapter 的最终选择，不新造一份权威结果。

### 5.2 改池成员不自动改所有 Unit

精英池删除 x，只改变该集合的成员关系。
另一个算法仍可以在自己的 Unit 中持有 x，也可以在后续明确取用更新后的精英集合。
不能通过自动广播，把一次集合维护变成多个算法未经自身决策的成员替换。
Unit 的扩展成员字段继续由既有 member_fields/on_members_changed 机制维护。

### 5.3 原始求值与任务比较分开

Problem 原始目标和约束保持不变；Bias 选择视图和任务投影具有明确作用域。
MOEA/D 方向精修仍使用当前任务冻结的权重、参考点和投影。
如果普通选择函数需要方向比较，应复用这份明确输入，不能从实时父视图重新猜测规则。
不为新入口复制一套评分权威，也不把方向标量写回母池 raw feedback。

## 6. 本轮暂缓的内容

- 更多筛选别名、便捷集合方法与复杂检索语法。
- 自动索引、增量 top-k、缓存和性能看板；先由具体规模与测量决定。
- 新 TTL、容量策略或物理回收体系；已有保留机制继续负责存储回收。
- 通用 map/beunit 流程语言、任意阶段图或新的池运行器。
- 所有 Adapter 强制共享一个四阶段循环。
- 独立于搜索步骤的维护事务与成组原子接纳。
- 因为池内已有分数就自动跳过接收算法的正式评估。

增量读取和按子池关系检索可能有价值，但已有逻辑时间、元数据与任务游标。
先让必要场景跑通；只有实际代码出现明显重复或测量显示瓶颈时，再补最小接口。

## 7. 验收：完成一条流程，而不是增加一组名词

主验收流程如下，属于目标行为描述，不是现有可运行 API：

```text
两个已提交来源池
  → 选择两个父解
  → 一次交叉得到两个孩子
  → 按用户指定顺序执行变异
  → 正式 ProblemRepair / ProposalRepair 对账
  → 正式求值、预算与硬接纳
  → 原 Adapter 完成自身选择
  → 普通函数用旧精英和本步接纳反馈维护精英池
  → 同一 Authority Snapshot / Pool manifest 提交
```

必须同时验证下面的行为：

1. 正常接纳：每个后代有独立身份和准确来源，精英选择可使用本步新反馈。
2. 部分接纳：只接纳其中一个孩子或非前缀子集，来源、反馈、输出和算法状态不串位。
3. 预算截断：未送评行不产生反馈或接纳输出，不虚增求值次数。
4. 零接纳或无提案：没有维护独立提交，没有幽灵代数。
5. 维护失败：算法更新、成员计划与发布游标回滚，已消耗求值预算保留。
6. 身份冲突：同名重建、revision 漂移、同目标冲突计划明确失败。
7. 恢复：候选版本、精英成员、Unit、RNG 和进度从 checkpoint 恢复，不重播初始化。
8. 算法对照：GA 验证批量变化；VNS 验证单后代仍自然；MOEA/D 验证冻结比较与 raw 不被改写。
9. 默认行为：未绑定新函数时，原算法配方和结构校验继续生效。

只对实际改动运行必要验证，不要求为文档中的每个表达另造一个机制或重复测试。
完成后更新对应契约、Catalog、脚手架与既有标准 Project，让用户能从装配入口找到真实用法。

## 8. 实施边界与当前证据

这两项属于 nsgablack 的优化行为装配与候选交付语义。
事务、共享存储、Plugin 生命周期和 Project/L0 继续复用 BlackBase，不在示例中私接控制循环。

实施次序建议：先固定批量后代的对齐与部分接纳，接通 GA；
再把成员决策接到既有提交前位置，最终用同一个标准 Project 验证完整流程。
正式 API 名称和具体调用位置以最小可实现方案为准。

本轮已实施上述最小扩展，并运行批量、部分接纳、Pool 选择、失败回滚、正式 checkpoint 与三 Case Project 验证。
当前证据见上述 Project 与接口手册；旧集合操作证据仍保留在 [Pool 集合操作](POOL_COLLECTION_OPERATIONS_CN.md)。
没有运行性能 benchmark，也未扩展独立维护事务或成组原子接纳。
