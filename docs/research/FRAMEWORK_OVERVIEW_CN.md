# NSGABlack：框架整体介绍

本文面向第一次了解项目的使用者和开发者。核对日期：2026-11-12。
它概括当前开发实现、可运行案例与研究问题；具体行为以运行契约和对应测试为准。
本次提交的测试范围及未通过的全仓检查见 [验证状态说明](VALIDATION_STATUS_20261112.md)。

## 1. 这个框架要解决什么问题

优化任务通常先有一个问题，例如生产排程中的产量、库存和到料约束，再选择搜索算法求解。
随着需求变化，开发者可能需要把种群搜索与局部精修结合、增加一个成员年龄字段、
修改父代选择、维护共享精英档案，或者将另一项求解任务作为当前问题的评估过程。

困难不只在实现某个算法公式，也在这些变化之后能否继续维护正确的候选身份、
成员关系、原始评估、反馈归属与恢复状态。NSGABlack 希望把这些公共维护工作集中起来，
让算法作者主要描述搜索规则、候选如何流动，以及各算法怎样使用自己的状态。

项目定位是面向优化实验与应用开发的可装配求解框架。组件化、混合算法和 checkpoint
本身都已有成熟研究与实现；本项目的研究价值需要通过具体任务和对照实验检验，不能仅靠命名宣称创新。

## 2. 核心分工

框架主线是 Problem → Pipeline → Unit → Adapter → Bias → Plugin。
这是职责关系，不是六个组件依次执行的固定流水线。Pool 则贯穿候选的存储与交接。

- **Problem**：定义原始目标、约束与评估含义。例如一个排程方案的产出、成本和违反量。
- **Pipeline**：处理候选的初始化、表示变换和问题侧修复等能力；搜索操作可以按算法需要显式装配。
- **SolutionPool / Pool**：前者管理候选版本及具名引用集合，后者提供调用期的选择、分组、合并和入池计划。
- **Unit**：保存所属算法的结构、成员属性及关系。例如种群、MOEA/D 方向关系、VNS 当前点和邻域状态。
- **Adapter**：拥有算法决策，决定怎样提出候选、调用变化规则、消费反馈和选择成员；需要时构建自己的 Unit。
- **Bias**：生成选择偏好，保留 Problem 的原始评估证据；软偏好不能擦除硬可行性判断。
- **Plugin**：提供日志、检查点、评估后端、观察与发布等生命周期能力。

Solver 是控制与装配门面。它安排预算、评估、接纳、更新和提交，不要求所有算法使用同一种内部结构。

### Pool 与 Unit 为什么要分开

Pool 回答“这个候选是什么版本、属于哪些区域、可以交给谁”。
Unit 回答“它在这个算法中是什么成员、位于哪个槽位、具有什么局部属性”。

同一个候选可以被多个算法引用，但它在不同算法中的年龄、排名或方向关系不应成为一份全局可写字段。
即使同一候选占据两个槽位，两个槽位的成员属性也可能不同。

因此，退出一个种群只解除该算法的成员关系；其它算法或历史记录仍持有引用时，不应顺带删除候选。
候选产生新版本与成员重排也分别处理，避免用数值相等代替身份。

Unit 由 Adapter 按需创建；装配 builder 不等于提前构造全部算法状态。

## 3. 用户怎样表达算法和组合

初始化、变化、选择和修复是可装配的行为类别，不是所有算法都必须执行的统一四阶段循环。
GA 的生存选择、SA 的接受决策、MOEA/D 的方向替换和 A* 的路径扩展仍保留各自含义。

### 选择、分组和聚合

Pool 的筛选结果仍是 Pool，可以继续分组、排序、抽样或合并。
算法作者提供规则，框架负责保持精确引用与位置关系。

例如：对最终成员按年龄分组，从每组取精英，再发布具名集合。
前提是 Unit 已声明并维护 age 字段；本例明确按第一目标取较小值，不冒充 Pareto 选择。

```python
from nsgablack.adapters import Pool, partition

def maintain_elite(request, *, rng):
    young, old = partition(request.members, by=lambda p: p.where(
        lambda q: q.member_field("age") < 2))
    young_elite = young.top(10, key=lambda p: p.objectives[:, 0])
    old_elite = old.top(10, key=lambda p: p.objectives[:, 0])
    elite = young_elite.concat(old_elite)
    Pool(parent=request.members, name="elite").inject(elite, replace=True)

ga.set_pool_maintenance(maintain_elite)
```

这段代码写在 Case 的算法模块里，ga 是 build_solver 中装配的种群 Adapter。
它声明入池计划，计划随原步骤提交；不在回调中另建求解器或数据库。

### 成员属性参与选择与变化

Unit 负责字段的增长、重排和替换规则。选择器读取本次已对齐的成员属性，
不需要为每个新增字段重新捕获 Solver、建立引用字典或编写独立恢复代码。

父代选择可返回 request.members 的派生 Pool，保留具体槽位。
完整变化函数通过 request.parent_pool 读取相应字段。
这些能力不意味着任意 Adapter 或任意变异器已经自动接入，逐族支持范围见接口手册。

### 多算法协作

内层用 Pool 操作表达解如何分流与聚合；外层用 Router、Chain 或 SearchPlan 表达执行次序、
局部步数、循环、并行分支与触发条件。Pool 存候选及集合关系，context 传运行阶段等轻量信息。

典型用途包括：

- GA 搜索后选出精英，VNS 从这些解开始精修，再由 GA 按原规则竞争接纳。
- MOEA/D 发布带创建者身份的方向投影视图，将方向比较规则交给精修算法，同时保留原始多目标反馈。
- 多个种群保留各自 Unit，在 Router 更新汇合后由一个维护回调统一更新共享档案。
- 使用 serial / multi / repeat 表达有限的多阶段搜索，避免手算全局代数与局部阶段的位置。

嵌套 Case 是另一种层次：外层候选的评估可以调用内层标准 Case。
内外层通常代表不同问题，通过正式输入、结果和 Artifact 引用交接，不直接共享任意可变状态。

## 4. 一次运行如何保持正确

Adapter 提出候选后，由控制面安排预算裁剪、必要的问题修复及 Unit 对账，再执行评估与接纳。
Adapter 只消费与接纳结果对齐的候选和反馈；最终成员、候选池与权威快照在同一步骤事务里发布。

失败时回滚算法工作状态和未提交的成员计划，已经发生的求值与预算消耗保留。
checkpoint 保存可恢复状态，恢复时按已有证据对账，不为了“补齐结果”而隐式重跑评估。

这些机制需要付出运行与学习成本。本项目已开展透明性、修改任务和性能开销实验，
但不能由局部测试推导出任意 Python 组件、算法公式和外部服务都正确。

## 5. 框架栈与工程形态

本项目与两个独立仓库协作：

- blackbase：共享 Project / Case / Scaffold、Context / Snapshot / Artifact、资源授权及公共事务协议。
- nsgablack：优化候选、算法状态、搜索决策、多目标选择及求解结果。
- mlblack：ML 数据、模型语义、训练与评估能力及模型 Artifact。

用户按 Project → Case → 标准脚手架组织代码。
每个 Case 以 build_solver.py 为装配入口，Problem、Pipeline、Adapter、Bias、Plugin 分目录维护。
跨 Case 顺序与资源授权由 Project 负责，算法不能绕过授权私自占用资源。

Catalog 用于发现组件、查看适用条件、装配位置和示例。
AI 辅助装配与工作区属于辅助工具，建议仍需通过实际契约和运行验证。

## 7. 设计如何验证

框架设计需要验证“算法状态维护与候选流转的显式分离，是否有助于局部修改和可靠组合”。
需要用实验回答，而不是直接宣称成立：

1. **修改成本**：增加状态、让状态参与选择、重排成员、重复槽位、替换精修器时，
   除必要算法规则外，还需编写多少对齐、状态维护和恢复代码？与成熟框架比较，不刻意写复杂对方实现。
2. **语义透明性**：同等随机输入与求值预算下，控制机制是否改变算法轨迹和评价结果？
   轨迹等价与“算法达到文献水平”是两个问题，应分别验收。
3. **运行代价**：在低成本评估、较昂贵评估和排程应用中，抽象带来多少时间和空间开销？
   将算法修复、证据记录、持久化和纯调度开销区分清楚。
4. **组合与恢复**：串行、逻辑并行、局部精修、嵌套求解中，部分接纳、取消和恢复能否保持相同含义？

已有年龄修改任务也暴露了成熟框架在简单场景下很简洁，不能据此主张本框架全面更少代码。
更有意义的是观察复杂度增加后，公共维护规则能否继续复用、额外成本是否值得。

## 8. 当前边界与下一步

目前可验证的事实是：核心框架已运行，已有多种算法组件、标准 Project 和具体修改/恢复测试。
最近的专项测试记录见 [Pool 接口手册](../architecture/POOL_API_REFERENCE_CN.md)，
其各批测试有重叠，不能简单相加作为总覆盖率。

仍需继续完善：跨独立 Case 的异步结果归并、部分高级组合的易用性、成员字段读取的独立成本测量、
完整安装与全量测试，以及更多与成熟框架相同任务的对照。

框架演进应选定明确的使用场景与验收范围，以真实实现和对照实验检验设计。
工程规模不是创新性的证明；明确边界、可复现的实验和诚实的对照才构成论据。
